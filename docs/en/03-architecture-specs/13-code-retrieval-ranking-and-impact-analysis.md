# Code Retrieval Ranking and Impact Analysis

[English](../../en/03-architecture-specs/13-code-retrieval-ranking-and-impact-analysis.md) | [中文](../../zh/03-architecture-specs/13-code-retrieval-ranking-and-impact-analysis.md)

## 1. Design Conclusion

Advanced code retrieval comes from fusing structural signals with lexical and semantic signals. Grep misses call relations, vector search weakens exact symbols, and pure AST search lacks natural-language intent. Ranking considers symbols, chunks, edges, paths, languages, query intent, and freshness together, and demotions must not turn the only valid candidate into a deletion.

## 2. Query Types

| Type | Primary signals |
| --- | --- |
| definition | Exact symbol, identifier segmentation, path/language filters |
| reference | Reference edge, target hint, confidence, callsite excerpt |
| caller/callee | Call edge, line containment, fan-out budget |
| import/dependency | Import edge, module path, resolution state |
| feature-flags | Config source, guards_code/read edge, source range, confidence |
| explanation | Doc comment, body chunk, semantic/vector similarity |
| impact | Changeset diff, reverse dependency, test edge, risk score |
| context | Bounded hybrid/definition/symbol seeds plus reference, call, and import expansion |

## 3. Ranking Signals

Signals include BM25, identifier-part matches, CamelCase/snake_case segmentation, normalized query-to-symbol name overlap, symbol-kind priors, path proximity, language filters, graph-edge confidence, call direction, non-test source path priority for caller/callee queries, a small symbol and hybrid-chunk test/benchmark path penalty when the query has no test intent, generated-code demotion when the query has no generated-code intent, class-member excerpt context and scoped member identity for qualified method hits, import surface/re-export files, declaration surface priority for header chunks that already match declaration-shape evidence, compact type-returning body priority for type-surface queries, chunk quality, freshness, semantic/vector rank, and rerank explanations. Ranking preserves original query casing for identifier segmentation and intent checks before lowercased lexical scoring. Test/benchmark path adjustments are disabled when the query itself asks for tests or benchmarks; generated-code intent must come from generic generated/codegen/generator terms or indexed generator/source terms in the current chunk's generated header rather than enumerating concrete generator names; generated-code demotion may be triggered by a chunk header or generic generated/autogenerated/codegen path segment; test/benchmark or generated-chunk demotions must preserve a positive score so the only candidate is not filtered out; and type-surface companion phrases such as component or metadata type names are added to FTS recall only as phrase groups, not as compound-identifier inputs, so broad single-token matches do not dilute exact API intent or block compact identifier recall. Inferred ambiguous-callee implementation expansion is supporting context for ambiguous call sites; direct call-site rows remain the preferred evidence when both are available.

Natural-language Hybrid queries may match a declaration through its persisted owner documentation. The same normalized `symbol.doc_comment` participates in symbol FTS, lexical scoring, and the returned excerpt, so concepts documented immediately above a class, interface, annotated Java declaration, or C/C++ declaration/template owner can recall that symbol without a repository-, path-, symbol-, or query-specific bonus. The owner anchor does not alter the symbol range or signature, and Rust inner block documentation is not treated as next-symbol context. For a broad Hybrid query with at least five effective terms, a type declaration receives a fixed bounded high-coverage type-surface bonus only when its name or signature matches at least two terms, its owner documentation matches at least three, and their union covers at least two thirds of the query; at most twelve deduplicated terms are examined. This bonus neither removes nor demotes Markdown or chunk results: structured types and documents remain in the same final ranking window. Documentation remains supporting evidence: an exact symbol or resolved edge keeps its structural priority, while ordinary block comments are excluded by the parser and cannot become owner context.

Broad Hybrid symbol recall also bridges conservative inflection and agent-noun differences before ranking. When the focused planner can select exactly three ASCII alphabetic high-signal terms of at least six characters from a query of more than four terms, it builds at most three pairwise FTS5 prefix groups; each candidate must match at least two prefixes. This supplemental probe is disabled for non-Hybrid and exact-file queries, filters to persisted type kinds with non-empty owner documentation before limiting, and reads at most 120 rows in addition to the unchanged 200-to-800 primary exact-symbol window. The two bounded sets are deduplicated by symbol snapshot identity before ordinary lexical and structural scoring, so the combined symbol window cannot exceed 920 rows. Prefix recall alone grants no score bonus: the existing type-surface documentation coverage gate must still promote the declaration, while Markdown and chunk results remain available through their unchanged retrieval layers.

Typed-query completion is based on evidence coverage rather than the mere presence of a hit. Definition source fallback accepts real declaration shapes after ordinary language modifiers and rejects comment/Javadoc and constructor-shaped mentions. Exact reference queries whose structured edge results do not fill the requested window may add bounded indexed-chunk usage evidence. Qualification scans only the already bounded candidate chunk and uses its persisted `language_id`: C/C++ declarations, function definitions, declaration-only typedef aliases, and logical continued same-name `#define` definitions are not uses; Python, Ruby, Bash, and configuration-language `#` comments, SQL line and block comments, JavaScript/TypeScript template and regex literals, Rust raw strings, quoted literals, and block comments are masked conservatively. Rust lifetime apostrophes remain code rather than opening a character literal. A chunk with a leading block-comment continuation delimiter or conventional `*` continuation shape stays masked until the closing delimiter, and a continuation with no closing delimiter in that chunk contributes no evidence. A mixed chunk remains eligible when it also contains a real code use, including a C/C++ macro body that references a different symbol. A full window and natural-language reference requests do not trigger that completion. Caller ranking applies the existing test-context demotion to embedded test symbols as well as test paths, while an explicit test query disables both adjustments. These rules retain valid lower-ranked evidence instead of deleting it and never expand the FTS candidate window.

Reference candidate admission excludes documentation and configuration languages before the bounded FTS limit so prose cannot displace code usage evidence. Grouped structured references order bounded candidates by repeated same-file identity evidence before lexical tie-breaks, expand them fairly within the unchanged occurrence budget, and apply a capped logarithmic repetition bonus after hydration. Large symbolized files also retain bounded uncovered top-level source windows outside symbol byte ranges; compile-time relationship assertions and similar file-level facts therefore remain searchable without widening every symbol chunk.

This reference admission rule is a bounded denylist of unambiguous documentation, data/configuration, and module-manifest surfaces, not a code-language allowlist. Executable build DSLs and template languages remain eligible for real usage evidence. An unknown or newly registered language is also eligible and is then checked by the ordinary language-aware usage validator, preventing registration drift from silently deleting code evidence.

For an exact single-name Hybrid type query, declaration role is a bounded tie-break: concrete classes, records, and structs rank above interfaces or traits with the same identity, while generic fake, mock, stub, and benchmark paths are demoted unless the query explicitly requests that intent. This role signal does not change candidate limits or override a stronger non-type lexical match.

Language-aware import projection preserves source-like syntax, including Go aliases as `import alias "module"`, while scoring derives the local binding from the normalized alias-plus-module representation. Exact import-path rows and path-constrained target-symbol rows reserve at most 700 edges before broad FTS merge and final top-k scoring; this fixed reserve keeps late-sorted exact importers reachable without making the query window unbounded. Importer-context FTS sampling uses one grouped scan and retains at most the earliest and latest matching chunk per selected path. This fair two-row cap prevents early paths from consuming the shared window; the existing 700-path, 2,048-chunk, byte, and SQLite-work bounds remain unchanged.

Import ranking derives local binding terms from named imports, namespace terminals, and conservative singular companions for wildcard bindings. Namespace prefixes, unrelated candidate terminals, and shorter CamelCase fragments are not importer-context terms when a more specific query-matching local binding is available. A target-symbol match authorizes context only when the matched symbol intersects a query-local binding term; the mere presence of matched-symbol metadata cannot admit an unrelated terminal. Same-file code-identifier usage, after language-aware comment and literal masking, is the primary importer-context signal. An explicit importer identity in a contextual query may also provide a bounded path-overlap signal after real same-file usage exists, but terms already explained by the import module, target hint, matched target symbol, or target-symbol surface are removed first. A target-only path or fully qualified name therefore receives no importer-identity path bonus. Matching non-wildcard production import edges may receive a small logarithmic source-size adjustment capped at 0.5; wildcard, generated, test, benchmark, and nonmatching edges receive none. This bounded secondary signal distinguishes substantive importer surfaces without treating file size as primary semantic relevance or changing any candidate bound. Importer context computes and caches each row's query-local terms before admitting paths; rows with no surviving term do not consume the limit of 700 selected importer paths. It then performs a direct `cap + 1` probe against the same-scope chunk FTS read model, using at most 128 distinct usage terms and 8 KiB of term bytes. Each path batch is additionally cancelled after 4,096 SQLite progress callbacks at 1,000 virtual-machine operations per callback, and the temporary handler is removed before later SQL uses the connection. Only an unsaturated, uninterrupted probe is grouped in memory, with at most 64 matching chunks per path, 2,048 matching chunks overall, and 16 MiB of raw matching chunk bytes overall. Chunk rows are accumulated incrementally; crossing the byte bound stops before grouping and disables all importer-context scoring for that candidate set. It must not rank an unbounded window before applying that probe. If the optional path, term, chunk, byte, or SQLite-work window saturates, context scoring is disabled for that candidate set rather than ranking only an ordered prefix. Importer context is optional enrichment: an unavailable target-symbol or chunk/import FTS read model disables the affected enrichment, while already available direct-path and identifier import-edge rows remain eligible and do not fail with the optional FTS layer.

When a target-symbol match is authorized, same-file usage sampling uses the matched symbol identity rather than every importer alias, so high-fanout packages cannot exhaust the term budget before evidence such as `alias.Type` is observed.

Target-symbol import expansion is permitted for an explicit `Imports` query whose input is either one unqualified identifier or an import path plus exactly one explicit upper-cased type identity. The mixed form is admitted only when the symbol's normalized target hint has the queried import path as an exact suffix; an importer class name beside an unrelated module path therefore cannot redirect expansion. Hybrid requests, ambiguous multi-identity forms, and qualified symbol/FQN forms containing `.`, `::`, `/`, or `\` stay on import-edge/direct-identifier/FTS paths and must not prepare unconstrained target-symbol expansion SQL. Every normalized repository path filter retains exact-or-descendant semantics; no dot or extension heuristic guesses whether it names a file or directory. Each filter compiles to a `BINARY` range `path >= ? AND path < ?`, with `filter + "0"` as its exclusive upper bound, plus the residual boundary check `substr(path, length(?) + 1, 1) IN ('', '/')`; this preserves a `(source_scope, path)` range seek without admitting punctuation-prefixed siblings. Import-edge group enrichment uses bounded row-value `IN (VALUES (?, ?, ?), ...)` keys and the durable `(source_scope, path, line_start, line_end)` index instead of an OR-expanded predicate. The leading-wildcard identifier scan is optional recall: it is interrupted after 4,096 SQLite progress callbacks at 1,000 virtual-machine operations each, returns an empty optional layer on `SQLITE_INTERRUPT`, always removes its temporary progress handler, and then allows the bounded FTS/direct layers to continue.

Industry code-search practice requires lexical, structural, and semantic layering: Zoekt/Google Code Search style trigram candidates are good for substring and regex screening, BM25 for natural language and documentation chunks, Tree-sitter captures for symbols and edges, and semantic/vector retrieval for conceptual explanation queries. Ranking must not let semantic scores override exact symbols or resolved edges, and broad regex results cannot bypass scope, path, language, or revision filters.

Code repository queries use AST-first cooperation with exact source fallback. Definition, reference, and hybrid queries first consult the versioned tree-sitter graph and SQLite FTS read model. Code-index workers may be parsing and finalizing another scope at the same time, but query execution reads only committed scopes through bounded read paths and never consumes a worker's partial index state. When the requested ref is still being full-indexed and the new scope has not finalized, `allow-stale` queries read the previous completed committed scope and explicitly mark stale/degraded state; they must not wait for the writer or read partial index data. `wait-until-fresh` is the mode that rejects an unfinished target scope. When that structured path has a specific recall gap, a bounded internal scanner may search materialized candidate files from the same indexed revision scope for exact text evidence. Import/dependency queries first derive the dependency set from import edges. If the dependency target has a code map or code graph target, retrieval uses structured dependency evidence; only when the dependency library is not indexed as a code graph target may the import query use the unresolved external dependency target hint as the source fallback term. Missing external dependency source is unresolved edge coverage metadata, not `degraded_reason`. For C and C++ preprocessor includes, an unresolved or ambiguous `edge_target_hint` is the normalized include specifier without the `#include` prefix, quotes, or angle brackets; a resolved hint remains the unique indexed target path, while the excerpt preserves the original source statement. Source fallback is a lexical layer only: it can recover precise source lines and improve recall, but it cannot report resolved graph edges or confidence that the AST graph did not establish.

Hybrid source-surface refresh preserves declaration strength when selecting the representative excerpt for an existing structured symbol range. A source line that declares a query identity may replace an ordinary summary or nested mention, but after that declaration is selected, a later and longer field initializer, logger statement, call, or other nested identity mention cannot replace it merely by length. Length remains a tie-break only between surfaces of the same declaration strength. Scores and retrieval provenance are still merged, and a distinct nested line may remain as a separately ranked lexical hit; this keeps the declaration in broad top-k results without discarding supporting evidence.

Agent-facing and maintainer-facing source inspection follows a separate tool policy. Use `rg` first for local repository search. If the local machine does not have `rg`, continue with bounded `grep -RIn --exclude-dir=.git --exclude-dir=target --exclude-dir=node_modules --exclude-dir=dist <pattern> <authorized-root>` commands. This manual grep path is allowed for investigation and self-iteration prompts, but it must not be wired into product query hot paths or used to bypass indexed scope, freshness, or authorization.

## 4. Candidate Window

FTS and source-fallback candidate windows apply scope/path/language filters before bounded scoring. High fan-out caller/callee queries are truncated by edge score and line containment so one call edge is not multiplied across unrelated chunks.

Layered Hybrid chunk retrieval separates probe precision from final recall. Structured, focused, lifecycle, compound, and strict probes keep the narrow 40-to-120 candidate window, while the final broad OR-FTS fallback uses the ordinary bounded Chunk window of 300 to 900 candidates; the combined set is still deduplicated, scored, and truncated at that broad bound. An exact-file filter permits a symbol-only early return only for a true single-symbol identity. Multi-term or contextual queries must execute the bounded chunk layer. Their exact-path source fallback is allowed only when two distinct structured identity anchors identify an incomplete source surface; it must not merely search again for one already-covered identity.

An unresolved external import edge is complete source evidence when its import-graph excerpt already contains a source-like statement whose parsed specifier equals the edge target. Missing source for that external package is not a source-text recall gap, so this complete surface does not materialize candidate blobs or run internal grep. Relative imports, dynamic-import intent, incomplete excerpts, and mixed complete/incomplete result sets still use the existing bounded fallback and authorization checks.

Internal exact-text source fallback runs behind the same blocking-worker boundary as Git snapshot reads. It is constrained by storage-side candidate-path limits, candidate-file, match, and line-length budgets. The current fallback budget is 256 candidate files, 8 MiB of materialized blobs, and 4096 bytes per line. It searches indexed commit content rather than the dirty working tree. For non-Git `filesystem:` commits, fallback must verify that the live source tree still resolves to the indexed scoped synthetic commit before reading any file; a mismatch is reported as fallback degradation and must not be hidden by reading current live bytes. Explicit stored `filesystem:` refs are allowed to reach storage lookup by identity, but source-byte materialization remains guarded by that live-tree verification. When fallback needs broad scope paths, storage first narrows candidate files through the indexed FTS read model using the query plus path and language filters, then falls back to bounded scope enumeration only if the query has no indexed candidate. If the FTS read model is temporarily unavailable during structured code search, the structured lexical layer may return an empty candidate set after retry so bounded source-text fallback can continue instead of failing the whole query; candidate-path lookup can also use indexed path and chunk content to keep fallback query-aware, and reports degradation instead of scanning lexicographic file prefixes when no query-aware candidates are available. This keeps late-sorted relevant files reachable without increasing the global candidate-file budget. The materialized search tree must include indexed dot-path candidates; the internal scanner performs fixed-string line matching, skips NUL-byte binary blobs, and returns bounded excerpts around long-line matches for non-definition queries. Oversized blobs are skipped without stopping later candidates that still fit the materialization budget, definition fallback filters candidate lines before enforcing the returned-hit limit, and import fallback may give executable dynamic `import(...)` source lines for local relative import queries a source-line shape bonus so runtime import uses can outrank normalized static import summaries without boosting comment-only mentions. If bounded candidate paths cannot be obtained, or candidate-file or materialized-byte budgets are exhausted, the query remains valid and surfaces a degraded reason instead of bypassing freshness or authorization. The product runtime does not depend on `rg` and does not shell out to recursive `grep`; `rg` and recursive `grep -RIn` are documented only as bounded agent/maintainer search tools when investigating the workspace.

Repository-set queries treat every member as an independent bounded retrieval workflow. Per-member SQLite access still goes through the storage boundary, member structured search, dependency-symbol fallback, and source-text fallback run behind small concurrency limits, and final overlay evidence, bridge bonuses, dedupe, diversity, and top-k selection are applied after member outcomes are merged so scheduling order cannot change cross-repository ranking semantics. A positive member priority may contribute a bounded domain-affinity bonus when the member and hit are fresh, priority is backed by resolved or ambiguous overlay evidence, and the query's non-generic domain terms are present in that member's result path or excerpt. Zero-priority members are not boosted, and the bonus cannot bypass freshness, member fanout, fallback, or final top-k budgets.

Codegraph context packing does not introduce a separate ranking model. Entry points keep the rank order from hybrid, definition, and symbol queries, while expansion hits inherit reference, caller, callee, and import ranking from their underlying query type. The packer applies only dedupe, diversity, and byte-budget truncation, and records the retrieval layer and score that caused each item to enter the pack.

Candidate windows expose observability fields: pre-filter count, post-filter count, scored count, truncation reason, and elapsed time for each layer. Impact, caller/callee, and import queries expand with changed paths, seed symbols, module hints, and edge confidence rather than full scope table size.

Feature-flag queries enumerate structured flag facts in the indexed scope by default. When `--query` is present, they filter only indexed flag names, source keys, paths, and excerpts. Ranking prioritizes guarded-code relationships, configuration definitions, ordinary reads and SDK evaluations, then query matches and path/language filters. The query must not use query-time grep to enumerate unknown flags, sync provider control-plane state, or hardcode known product, repository, or benchmark flag names to improve ranking.

Broad source fallback reserves at most two matches per bounded candidate path before final scoring (a maximum pool of 512), and the scanner distributes that pool across paths before reusing a path. Within one path, code-shaped references are retained ahead of comments and import-only mentions; final reference scoring also demotes explicit document/configuration languages and comment-only evidence below code usage. An explicitly narrow path set may use the requested result limit within the same ceiling. This prevents one match-dense file or documentation surface from consuming the entire recall pool while final top-k and all byte/file limits remain unchanged.

## 5. Impact Analysis

Impact analysis starts from changeset scope:

```text
changed files
  -> changed symbols
  -> direct references/calls/imports
  -> reverse dependency expansion
  -> tests/docs/config affected candidates
  -> risk groups with evidence
```

Impact output is not an absolute conclusion; it is a risk grouping with evidence, paths, edge confidence, and budget truncation. Non-Git impact path enumeration must use the same effective filesystem filters as the indexed scope, including explicit broad-directory opt-ins, instead of rescanning with the default non-Git policy.

## 6. Acceptance Criteria

- Query `foo_bar` can match `fooBar`, `FooBar`, and multipart symbol names, while typed edge queries stay narrower.
- Caller/callee results point to chunks containing the call line.
- Source fallback hits are marked with lexical/text-fallback provenance and never include resolved edge confidence; hybrid source fallback fills result windows without outranking existing structured hits.
- Unresolved external dependency coverage is reported through edge resolution metadata and does not set `degraded_reason` unless the bounded fallback itself fails.
- Self-iteration and maintainer prompts cover both product internal source fallback behavior and manual `rg`/`grep -RIn` inspection fallback so missing local ripgrep does not block source analysis.
- Impact output explains whether each result came from diff, call, reference, import, or test signals.
- Benchmarks are not improved by enumerating known queries, paths, or symbols; improvements come from general ranking signals, index structures, or candidate pushdown.

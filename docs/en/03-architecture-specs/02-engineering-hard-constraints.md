## 1. Design Conclusion

This chapter is the hard contract for Book 3. Implementation, documentation, tests, release, and operations changes must satisfy it; these rules are not optional guidance and cannot be postponed as follow-up work.

Advanced architecture is earned through clear boundaries, acyclic dependencies, recoverable state, bounded resources, and verifiable behavior.

## 2. Architecture Constraints

- **Async first**: I/O, graph database access, index refresh, ingestion, and service orchestration expose async APIs.
- **No blocking hot paths**: CPU-heavy, disk-heavy, or blocking work runs behind explicit workers, maintenance tasks, or blocking boundaries.
- **Bounded resources**: event pipelines, network entry points, index refresh, and background tasks have queue depth, budgets, timeouts, cancellation, backpressure, and overload behavior.
- **Facts separated from read models**: GraphStore is the source of truth; BM25, semantic, vector, summary, community, and code indexes are derived read models.
- Large-repository indexing must not treat the historical 180-second baseline as a universal hard timeout. Elastic mode is enabled by default; unless fixed/strict mode is explicitly selected, the budget must be derived from the authorized Git file count and recorded throughput baseline, then clamped by an explicit `max_index_budget_ms`; registration overhead must remain separately bounded. Elastic waiting must not bypass durable staging, the single writer, leases, checkpoints, edge/FTS finalization, or freshness state. See [Elastic Long Budgets for Large Repository Indexing](../05-benchmarks/12-elastic-index-budgets.md) for formulas and operational interpretation.
- **Acyclic dependencies**: crates, modules, traits, services, adapters, and configuration objects do not form cycles.
- **Clear code-source directory authority**: Git-managed code repositories use the tracked tree as the indexing directory authority, so tracked source must not be skipped only because it lives under names such as `build/`, `dist/`, `vendor/`, or `third_party/`; non-Git source directories default to source/config/documentation whitelist scanning so build products, caches, and dependency copies do not enter the index unless an explicit path opts into that broad directory. A narrow non-Git path such as `src` must not opt into sibling broad directories or walk unrelated filtered siblings before selection; an unfiltered non-Git scan must not walk directories that cannot contribute to the default whitelist; `--path .` is the explicit whole-root opt-in for broad directories. Git probe failures on real Git metadata must not silently fall back to filesystem indexing, and source fallback must not read live files for a stale scoped `filesystem:` commit. Non-Git synthetic hashes must be derived from the effective indexed scope after source-layout discovery, non-Git pre-scope hashing must not read files excluded by the file preset unless an explicit path filter opts into that file, non-Git ref resolution, source fallback verification, and impact path collection must include effective path and language filters, queued synthetic refs, synchronous full-snapshot reads, and full-index or delta live-byte reads must be verified before accepting bytes, non-Git file byte/hash/metadata materialization must reject final-path and ancestor-directory symlink replacements, explicit stored `filesystem:` refs plus source fallback verification, impact collection, impact partitioning, and deleted-symbol extraction must resolve through filesystem scope identity before dynamic source-kind or Git probes, repository-set members and freshness checks with narrower filters must reuse compatible broader non-Git scopes, incremental deletion must account for previous discovered roots, explicit non-Git incremental `base_ref` values must load that stored base scope, active non-Git task matching must compare with the task's effective filters for narrower stale reads, non-Git impact paths must return no changes when scoped base/head refs match, and Git ref normalization and fresh full-index checks must not perform full tree walks.
- **Performance must generalize**: improvements come from data structures, ranking signals, indexing strategy, query planning, batching, concurrency boundaries, or storage layout, not enumerated fixture cases.

A Rust-syntax architecture gate enforces acyclic dependencies. It expands grouped imports and qualified `crate::` paths into a top-level module graph, runs SCC detection across every node, and reports each layer violation with its source file and line. `bootstrap -> interfaces -> application` is the only CLI production direction; `interfaces` must not call back into `bootstrap`. The 1.x `interfaces::cli::{run,run_process}` functions remain only as deprecated compatibility entries implemented without that reverse dependency. `api` must not depend on `storage`: public cursor, index-refresh, file hit/summary, and health-diagnostic contracts belong to `domain`, while old `storage::*` paths remain compatibility re-exports. The architecture job uploads JSON and DOT graph artifacts; substring token checks that miss grouped imports are not dependency gates.

The application infrastructure migration budget is frozen by exact file, target module, and AST reference count and can only decrease. SQLite store construction, catalog topology probes, and lazy open run through an async `KnowledgeStoreFactory` injected by bootstrap. Embedding and external-worker outbound HTTP run through async `ports` contracts, with concrete reqwest/QoS adapters outside application. Every remote embedding request must acquire shared QoS admission before transport; the deprecated provider constructor without a QoS runtime may retain local echo behavior but must fail closed for remote providers and must never call `send`. Application must not construct SQLite stores or HTTP clients or invoke network transports directly. Large exact directory listings are not architecture evidence; the layout gate checks foundational ownership, nonempty production files, and the prohibition on production `#[path]` redirects, while a repository-wide gate enforces the 1,000-line limit for every tracked UTF-8 text source, test, document, script, configuration, and workflow. Binary files are outside a text-line metric, and `Cargo.lock` is the sole tracked-text exception. The syntax graph proves dependency direction.

## 3. Foundational Ownership

| Module | Sole responsibility | Forbidden |
| --- | --- | --- |
| `env` | Environment loading, parsing, validation, redacted diagnostics | Direct environment reads elsewhere |
| `paths` | Platform paths and runtime/data/log/cache directories | Runtime path construction elsewhere |
| `net` | Sockets, HTTP clients/servers, listeners, network loops | Network capability creation elsewhere |
| `net::http` | HTTP over a mature async runtime/library | Blocking sockets, thread-per-connection, busy polling |
| `net::qos` | Admission control, source/tenant limits, priority, budgets, overload metrics | Resource consumption before QoS |

Stable identity and wall-clock primitives also have one lower-layer owner. `identity` exclusively owns the persisted FNV-1a algorithm and its incremental hasher; domain, application, watcher, path, and storage owners consume that contract instead of copying constants. `clock` owns the narrow `Clock` contract, `SystemClock`, Unix-millisecond conversion, and pre-epoch/overflow errors; callers may map those errors at their boundary but must not read `SystemTime::now()` independently. Neither owner may become a generic `utils` bucket.

Ontology schema primitives follow the same single-owner rule. `domain::core::ontology` exclusively owns the storage-independent bounded contracts for class identity, RDF local names, OWL object properties, domain/range relation shapes, and schema validation; `domain::operations::software::vocabulary` only registers the software-domain class/property catalog, version, and namespace. Software entities, statements, shape validation, and RDF/JSON-LD export consume that catalog. Storage adapters, read models, and exporters must not copy the ontology namespace or define a second domain/range match. Business-term identity may consume core primitives but must not depend back on the software vocabulary; LPG/RDF store choice, materialization, and querying do not belong to the core ontology owner.

Named platform process inputs follow the same boundary. During process bootstrap, `env::windows_system_root_from_process` captures Windows `SystemRoot`, bootstrap captures `std::env::current_exe` once, `paths::windows_tasklist_command` resolves the Windows process-list executable, and `RuntimeConfiguration::process` injects both values into service recovery and lifecycle planning/execution. Binary preflight, copy, upgrade, rollback, and checkpoint recovery use that same captured executable path. Application workflows must neither call `std::env`/`current_exe` nor construct platform executable paths while recovering workers or invoking service managers.

The foundational HTTP boundary is physically contained in `net/http/`: `mod.rs` owns validated configuration, server runtime, request context, timeouts, cancellation, and graceful shutdown; `outbound.rs` exclusively owns reqwest client construction, bounded raw JSON transport, URL parsing, response validation, and outbound QoS accounting; `qos_admission.rs` isolates inbound request admission; and `qos_client.rs` owns reqwest permit/body lifetime and timeout accounting. `outbound_tests.rs` and `qos_client_tests.rs` attach directly to their owners, while `mod_tests.rs` retains configuration, server, and cross-client/server request-context integration contracts. The `net/` parent must not regain `http.rs` or `http_tests.rs`.

The foundational QoS boundary is physically contained in `net/qos/`: `mod.rs` owns validated resource budgets, admission decisions, runtime counters, and release-on-drop permits, while `mod_tests.rs` is its direct white-box contract. `net::http::qos_client` owns remote embedding transport admission and keeps the permit plus cancellation guard alive until the response body is consumed or dropped; rejection happens before socket work, timeouts remain observable, and a cancelled send/body increments cancellation metrics and releases the permit. No remote embedding path may call reqwest `send` outside this owner. The `net/` parent contains only its facade pair and the named `http/` and `qos/` subdomains; it must not regain flat `qos.rs` or `qos_tests.rs` siblings.

### 3.1 Environment Variable Boundary

The internals of `env` maintain a one-way data flow: `variables` only owns accepted variable names; `error` and `overrides` own the stable error model and typed override data; `value_parser` extracts and validates paths, strings, booleans, and positive integers from an already normalized snapshot; `platform` owns platform detection, key case normalization, platform directory inputs, and the process `SystemRoot` read; and only `config` may capture the complete process environment and assemble the public configuration. `mod.rs` preserves the existing `env::*` facade and must not accumulate parsing rules again. Corresponding unit tests live in sibling `config_tests`, `platform_tests`, and `value_parser_tests` files and are attached by their matching implementation owners, not by the facade, so configuration assembly, platform rules, and scalar validation fail independently.

The dependency direction is fixed as `error`/`variables` → `value_parser` → `platform`; `overrides` only composes those typed platform values, and outermost `config` depends on the other modules. Error, override, and variable-catalog modules must not depend back on configuration assembly, and `std::env` reads must not spread outside the `env` directory.

### 3.2 Code Repository Application Workflows

Knowledge Map uses narrow physical owners: `map/query.rs` exclusively owns show, filtered show, routes, and read-model loading; `map/validation.rs` owns map-contract and business-glossary route validation; and `map/mod.rs` retains only the stable `KnowledgeMapService` facade, command workflows, migration, and atomic-publication coordination. The external facade and artifact format remain compatible. Read, validation, and publication responsibilities must not reaggregate into one near-limit owner.

The live process environment is captured once at the bootstrap composition root. For CLI update notices, `bootstrap::cli` evaluates notice policy first and injects `RuntimeConfiguration` into the interface. The interface must not depend back on bootstrap to read configuration, and application and `net` runtime must not expose live-process refresh shortcuts. Deterministic tests inject `EnvironmentConfig`, `ProcessRuntimeConfig`, and typed runtime snapshots.

`application::code_repository` partitions internal ownership by use case: the `repository/` directory owns registration, removal, status, reports, staleness annotation, and worktree-overlay validation; `repository_graph/` owns fresh indexed-snapshot admission, bounded document loading, and OKF neighborhood response assembly; `indexing/` owns index execution, durable task leases, checkpoints, scope previews, and worker administration; `update/` owns optional base/head resolution and durable commit-to-commit update submission; `query/` owns versioned-scope retrieval and feature flags; `impact/` owns diff impact analysis; `context/` owns bounded graph-aware context packs; `freshness/` owns result/index reconciliation; `scope/` owns indexed-ref and filter compatibility; `software_projection/` owns global software reads; and `source_surface/` owns complete-declaration checks. Inside `indexing/`, `start` owns admission and durable task seeding, `worker` owns claim/lease/retry/terminal transitions, `session` owns checkpointed bounded parse/write execution, and `preview` owns read-only scope previews. The stateful `workflow` is split into `recovery` for fence/checkpoint reconciliation, `snapshot` for full/incremental snapshot generation behind blocking and lease boundaries, `publication` for durable clone/finalization/fallback publication, and `projection` for workspace plus business/software derived projections and terminal status. Dependencies flow from the workflow coordinator into these stages; the stages must preserve one active writer per repository, attempt-scoped leases, checkpoint replay/idempotency, bounded retry/backoff, and publication-fence validation. The physical `blocking/`, `clock/`, `errors/`, and `worktree_ref/` primitives isolate their boundary policy without sharing an ambiguous support bucket. `blocking` keeps CPU-heavy indexed-document projection behind four global concurrency permits, a bounded admission wait, a response-wait deadline, and `spawn_blocking`, so OKF YAML/graph work never executes on an async runtime worker. A response deadline stops waiting; it cannot forcibly cancel a running blocking closure, which may finish in the background while retaining its permit. The permit remains attached to that worker so total active projection work stays bounded by four. Context, repository graph, scope, and update attach direct `mod_tests.rs`; the root contains only its declaration facade and named subdomains and must not regain flat implementations or owner-specific tests. These modules expose stable APIs through the same `RelayKnowledgeService` and depend inward only on `domain`, `code`, and `storage` contracts; they must not duplicate workflows or depend back on CLI, Web, MCP, or other adapters.

Within `application::code_repository::repository_set`, physical `membership/` owns create/add/member-scope APIs; `status/` owns required-status lookup, fact-version replacement, moving-ref checks, and set freshness aggregation; `member_freshness/` owns fact-version scope reconciliation; `errors/` owns set-specific storage error mapping; `lifecycle/` owns removal coordination; and `refresh/` owns synchronous overlay rebuilds plus durable queue, lease, completion, retry, and dead-letter transitions. Each focused behavior owner directly attaches `mod_tests.rs` when it has unit contracts. The physical `query/` domain owns set retrieval: `mod.rs` owns pure overlay evidence, scoring, deduplication, diversification, and truncation; `workflow` owns concurrent member retrieval, dependency-symbol fallback, deferred bounded source fallback, and wait-until-fresh admission; `plan` owns bounded dependency API query planning and hit merging; `domain_affinity` and `identity_coverage` own their focused ranking signals. Every behavior owner attaches a directly paired sibling test; `test_support` is test-only data construction for the ranking owner. Dependencies flow `workflow -> query root/plan` plus the parent freshness/error owners, `query root -> domain_affinity/identity_coverage`, and `identity_coverage -> plan`; reverse dependencies are forbidden. The repository-set root declares only these physical domain owners and must not restore flat implementations, owner `*_tests.rs`, `query_workflow`, `query_test_support`, `domain_affinity`, `identity_coverage`, or `plan` siblings. Do not reintroduce a general repository-set service that combines membership, storage-backed member query state machines, source fallback coordination, freshness state transitions, or leased refresh workflows.

`application::update` is a strict version-check workflow boundary. Root `mod.rs` only declares modules and re-exports the stable configuration, response, check, and notice API. `config` owns source aliases, environment policy, interval conversion, and GitHub repository validation; `version` owns stable/prerelease SemVer parsing and ordering; `result` owns serialized response/diagnostic contracts; `candidate` owns highest-release selection and update-availability projection; `cache` owns configuration-keyed async cache reads, freshness, and writes; `release` owns release-metadata session preparation, source iteration, and source dispatch; `workflow` owns cache-first checks, force refresh, best-effort cache persistence, time capture, and user notices; and `diagnostics` owns stable diagnostic envelopes. Each of those owners is a physical responsibility-named directory whose `mod.rs` directly attaches `mod_tests.rs`; the update root must not regain flat implementation or `*_tests.rs` siblings. The physical `sources/` subdomain uses a declaration-only `mod.rs`; `github` and `crates_io` own their URLs, payloads, and candidate mapping, while `metadata` exclusively maps technology-neutral port results into bounded JSON payloads and stable source diagnostics. `ports::release_metadata` owns the request, session, future, and failure contracts; `adapters::release_metadata` is the only concrete release transport owner and delegates client construction, QoS admission, timeouts, status validation, and bounded streaming response reads to `net::http`/`net::qos`. Every behavior owner attaches a same-level test. Dependencies flow `workflow -> cache/release`, `release -> ports/sources/candidate/version`, source payload owners -> `metadata/candidate/version`, `metadata -> ports/diagnostics`, and the outer adapter -> `ports/net`; reverse dependencies, application references to `reqwest` or `net`, and release-specific network code outside the concrete adapter are forbidden.

Local-file application workflows are physically grouped under `application::knowledge::file_index`: `mod.rs` owns the shared async service APIs, request/root validation, freshness response assembly, and storage error mapping. The physical `scanner/` domain owns the bounded blocking filesystem walk, global scan permits, timeout/backpressure outcomes, and file-entry workflow in `mod.rs`, with its direct white-box contract in `mod_tests.rs`. The physical `content/` domain owns bounded content ingestion: its declaration-only `mod.rs` re-exports only the scanner surface, `budget` owns attempted-read byte accounting, `extract` owns eligibility, hashing, and chunking, and `read` owns capability-root authorization plus snapshot verification. Each content owner attaches a directly paired sibling test. Dependencies flow `scanner -> content::{budget,extract,read}` and `extract -> read`; reverse dependencies are forbidden. `workflow_tests` remains with the facade because it verifies request validation and runtime-root composition. Do not restore `file_index.rs`, flat `scanner.rs`, `scanner_tests.rs`, `file_content_*` siblings, compatibility aliases, or production path redirects, and do not move blocking filesystem work into async service methods.

The `application::knowledge` root contains only its stable facade and physical `file_freshness/`, `file_index/`, `index_refresh/`, `ingest/`, `map/`, and `multimodal/` domains. Each responsibility-named `mod.rs` owns its workflow and directly attaches `mod_tests.rs`: freshness aggregation, durable refresh coordination, request-to-mutation conversion and evidence identity, file-backed knowledge-map lifecycle, and bounded multimodal conversion remain separate. Within `map/`, `error.rs` is the lowest shared error contract; `artifact.rs` owns current v4 manifest/topic-shard/recent-history serialization and integrity plus read-only v2/v3 archive compatibility; `contracts.rs` owns public request/response contracts and bounded mutation state and may depend one-way on `artifact` and `error`; `history.rs` owns bounded public history-page reads and legacy archive traversal; `lock.rs` exclusively owns cross-process writer-lock no-follow opening, legacy compatibility, prepared-inode durability, atomic publication, crash recovery, and bounded cleanup; and `mod.rs` retains only migration, bounded show/route reads, artifact/root atomic publication, and Knowledge Map lifecycle coordination. `mod.rs` must not reabsorb the writer-lock implementation or exceed the 1,000-line file cap. `artifact` must not depend back on `contracts`; types shared by both belong in a lower contract such as `error`. `map/mod_tests.rs` delegates path-confinement and history/writer-lock scenarios to the same-directory `path_tests.rs` and `history_tests.rs`, respectively; `history_tests.rs` is the focused behavior owner for history/archive and writer-lock protocol scenarios, and all three test owners plus every production owner must remain below the 1,000-line cap. Do not delete `lock.rs` and merge locking back into `mod.rs`, or scatter writer-lock scenarios into a responsibility-free test bucket. Evidence-identity tests belong to `ingest`, not the wider application service facade. Do not restore flat knowledge implementation or responsibility-free `*_tests.rs` siblings, or make `application::service` import an ingest helper only to host its unit tests.

The shared application service groups workflow ownership into physical `health/`, `lifecycle_plan/`, `retrieval/`, `service_status/`, `storage_diagnostics/`, `storage_provider/`, and `watcher/` subdomains. Retrieval exclusively owns source-scope validation, freshness/index reconciliation, backend degradation, bounded search/rerank, provenance budgets, and response assembly; storage-provider and watcher owners attach direct `mod_tests.rs` contracts. Root `mod.rs` owns service construction, shared state, stable helper contracts, and cross-workflow composition. Root `*_tests.rs` files remain only when they exercise the assembled facade across multiple owners or external storage/runtime boundaries. Do not restore flat service implementations, owner-specific tests in the facade, or storage/watcher lifecycle logic in `mod.rs`.

The Web adapter is physically grouped under `interfaces::web`: `mod.rs` owns router composition and shared response/error boundaries, while the `assets/`, `files/`, `model_config/`, `operation_request/`, and `code/` subdomains own their named HTTP contracts. `operation_request/mod.rs` owns Web-operation payload field/type/range validation, enum parsing, and domain/API request construction; `assets/mod.rs` owns path normalization, traversal rejection, asynchronous reads, content types, SPA fallback, and missing-build responses; `files/mod.rs` owns file-operation dispatch and request mapping; `model_config/mod.rs` owns model-provider configuration routes. Each of these four owners attaches direct `mod_tests.rs` coverage. The physical `code/` domain owns repository-code HTTP behavior: `mod.rs` owns versioned routes and attaches the assembled code-router integration tests, `index_request` owns CLI-shaped index payload mapping, and `view_request` owns code-view payload mapping; both request owners attach direct sibling unit tests. The facade composes these named route domains and imports only their narrow helpers. The Web root contains only these subdomains, `mod.rs`, and facade-level `control_tests.rs`, `mod_tests.rs`, and `router_files_integration_tests.rs`; the last remains attached to the Web facade because it exercises the assembled router across file and application boundaries. Flat `assets.rs`, `files.rs`, `model_config.rs`, `operation_request.rs`, `code_api`, `code_index_request`, `code_view_request`, other flat feature siblings, compatibility aliases, production `#[path]` redirects, and sockets opened from this adapter are forbidden.

Cross-adapter code-index mode semantics are physically contained in `interfaces/code_index_mode/`: `mod.rs` exclusively maps the exact `worktree` ref to overlay mode, rewrites overlay selectors to their `HEAD` base without losing scope filters, and normalizes assembled requests; `mod_tests.rs` is its direct contract. CLI local/remote and Web adapters consume this owner instead of duplicating worktree rules. The `interfaces/` root contains only its facade and the named `agent/`, `cli/`, `code_index_mode/`, and `web/` subdomains; it must not regain flat `code_index_mode.rs`.

The MCP adapter is physically grouped under `interfaces::agent::mcp`: root `mod.rs` contains only module declarations, protocol constants, stable public state/transport re-exports, and assembled integration-test declarations. The physical `runtime/` subdomain has a narrow re-exporting `mod.rs`; `runtime::server` owns shared state plus audit/QoS construction; `runtime::transport` owns router/listener lifecycle and startup errors; `runtime::dispatch` owns Streamable-HTTP request validation, JSON-RPC/session method dispatch, request-level QoS admission, and response/audit completion; `runtime::tool_runtime` owns typed tool-call input, timeout, cancellation, and tool-family routing; `runtime::builtin_tools` owns retrieval, graph inspection, health, service-status, and index-status execution; and `runtime::method_error` owns the shared resource/prompt/metrics error mapping. Their same-level `server_tests`, `transport_tests`, `dispatch_tests`, `tool_runtime_tests`, `builtin_tools_tests`, and `method_error_tests` pair directly with those behaviors. `json_rpc` owns protocol initialization validation, session/error envelopes, response encoding, and typed request-ID identity; `tool_contract` owns freshness parsing, argument/domain error mapping, MCP request context, and stable tool result envelopes; named child modules own audit, HTTP contract, resources, prompts, state, authorization, registry, and code-tool behavior. `json_rpc_tests` and `tool_contract_tests` stay paired with those owners. The `code_tools` subtree keeps only tool-name dispatch and stable definition re-exports in `mod.rs`; `retrieval_handlers` owns code, context, repository-graph, and repository-set retrieval workflows; `insight_handlers` owns software projection, feature-flag, and impact workflows; `request_contracts` owns serde argument contracts, kind normalization, and context request bounds; `tool_definitions` owns MCP schema construction and advertised kind aliases; `agent_budget` owns bounded agent-output policy, including repository-graph serialization and near-linear trimming to the complete compact-JSON `structuredContent` `max_context_bytes` cap; and `codebase_view` owns derived codebase-view execution. Repository-graph node and edge limits must each pass the shared MCP access-policy `max_limit` before service execution. Repository-graph output work runs behind a separate four-permit `spawn_blocking` boundary. The outer tool deadline or cancellation stops waiting but cannot forcibly cancel a running blocking worker; that worker may finish in the background while retaining its permit, so total active output work remains bounded by four. Request, schema, and budget tests stay beside those owners as `request_contracts_tests`, `tool_definitions_tests`, and `agent_budget_tests`; assembled handler workflows remain covered through the colocated `mod_tests`, `protocol_tests`, `tool_tests`, `software_tool_tests`, `feature_flag_tool_tests`, `repository_graph_tool_tests`, and `runtime_guardrail_tests` rather than a facade unit-test bucket. Reusable test storage and HTTP transport fixtures are explicitly named `test_support` and `transport_harness`. Dependencies flow one way from transport into server and dispatch, from dispatch into server plus focused protocol/tool owners, from tool runtime into server plus built-in/code tools, from the code-tool facade into handlers, and from retrieval/insight handlers into request or budget owners; server does not depend back on transport or dispatch, and focused tool owners do not depend on transport or dispatch. Do not restore handler/runtime logic to either `mod.rs`, create a server/dispatch dependency cycle, flatten runtime owners back into the MCP root, restore root-level `mcp_*` files, add a sibling `code_tools.rs`, or use issue-number test module names outside these ownership boundaries.

The CLI adapter is grouped under `interfaces::cli`: `mod.rs` owns only the stable public process facade, module assembly, and re-exports; it directly declares the physical `command`, `files`, `grammar`, `knowledge`, `map`, `operations`, `remote`, `render`, `repo`, `repo_set`, `runtime`, `service`, `setup`, `spec`, and `version` owners without production `#[path]` redirects or `*_cli`/`cli_*` aliases. `command`, `runtime`, and command-family owners keep parsing, environment selection, and service dispatch outside that root. The physical `repo::view` child owns the repository-view contract, parsing, request mapping, and execution; it must not be lifted into the CLI root as an alias sibling. `spec` owns machine-readable command contracts through the physical `spec::{data, files, repo, repo_set}` module tree: `spec/mod.rs` declares these modules directly, and each module lives in its same-named directory. Within `spec/data`, `core` owns knowledge/graph/diagnostic/setup/version/help records, `map` owns knowledge-map records and source-option requirements, `operations` owns worker/proposal/audit records, and `service` owns lifecycle/operator/service-worker/foreground records; every owner attaches a direct same-level test, while `data/mod.rs` only preserves the stable aggregate display order and verifies global path uniqueness. Flat `data.rs`, files that mix these command domains, `files.rs`, `repo.rs`, or `repo_set.rs` siblings, `cli_spec_*` aliases, and `#[path]` redirects that simulate this tree are forbidden. `render` owns output serialization; `repo`, `repo_set`, and `setup` own their command families; and focused parsing, naming, remote, service, map, and version tests live under `tests`. Root-level `*_cli` prefix buckets are forbidden.

Codebase understanding views are grouped under `application::code_repository::views`: `service` only orchestrates scope selection, freshness, and responses; `architecture`, `business_domains`, `dependency_tour`, `process_flow`, and `affected_scope` each own one derivation algorithm; and `builder` plus `rules` provide bounded construction and deterministic classification. Focused unit tests pair with their implementation owner, while the facade explicitly owns `affected_scope_integration_tests` and `dependency_tour_integration_tests` because those scenarios exercise service dispatch, builders, rules, and derivation algorithms together. View tests remain colocated with this directory instead of using ambiguous flat `views_*` filenames.

Source fallback retrieval is grouped under `application::code_repository::source_fallback`: `execution` is the sole I/O orchestrator; `plan` decides whether and how bounded fallback runs; `identity`, `filters`, `scoring`, and `results` own coverage, request constraints, ranking, and result merging; and `imports`, `surface`, and `worktree` isolate evidence-specific boundaries. The facade explicitly owns `surface_integration_tests` because those scenarios exercise the `plan` + `results` + `surface` composition rather than one implementation unit; focused tests remain paired with their exact implementation owners. Modules outside this directory must not depend directly on these internal algorithm helpers.

The `indexing` directory is a strict workflow boundary: `mod.rs` coordinates full and incremental execution, `state` owns persisted index inspection and reuse, `task` owns durable leases and worker recovery, `queue` owns bounded overlay task submission, `fast_path` owns validated fresh-index reuse and directly attaches `fast_path_tests.rs`, and `tasks` owns task administration. Its exact physical inventory is `fast_path.rs`, `fast_path_tests.rs`, `mod.rs`, `queue.rs`, `resume_tests.rs`, `state.rs`, `state_tests.rs`, `task.rs`, `task_tests.rs`, and `tasks.rs`; no production owner may embed a test module implementation. Only the lease-recovery operation needed during repository registration is exposed to its parent; internal indexing helpers must not leak into query or adapter code. The `repository` directory similarly keeps its service implementation in `mod.rs`, registered status and checkpoint selection in `status`, result freshness annotation in `staleness`, worktree-overlay validation in `worktree`, and white-box fixtures beside the owned behavior. Shared `scope` retains scope resolution and filter compatibility, while `blocking`, `errors`, `clock`, and `worktree_ref` isolate runtime, error, persisted-time, and overlay-identity boundaries. Do not restore root-level `repository_*`, `worktree_freshness`, `index_*`, `fast_index`, `queue`, or `tasks` buckets.

The physical `code::source::repository` subdomain separates repository-source primitives. Final visibility for a fenced code index must pass through the software-projection publication barrier. In a single SQLite database, completing code facts may only leave the new scope `stale/indexing` and its checkpoint at `finalizing:software_projection`, while the previous active scope remains readable. After software facts build successfully and the attempt fence is revalidated, software status, staged code scope/repository freshness, checkpoint completion, and the publication receipt activate in one SQLite transaction. Partitioned SQLite does not claim cross-database atomicity. It routes by `fence.repository_id` to the existing checkpoint shard, fails explicitly if that shard is absent, and never falls back to control. The shard transaction commits code and software facts but leaves the target catalog route `staged`, records its durable `staged_task_id` owner, and holds the checkpoint at `finalizing:partitioned_publish`; active-only routing keeps the previous active scope readable. Only the owning durable task under a valid fence may activate that staged target. After the shard commit, one control-database transaction revalidates the fence and exact staged owner/target, changes repository and scope routes to `active`, mirrors repository freshness/status, and inserts the publication receipt. Rolling back that transaction exposes none of those control-plane changes. A crash before it retries from the staged shard; a crash after it reuses the durable receipt instead of rebuilding or republishing.

The durable task's `succeeded` transition is a separate fenced completion transaction after publication. Completion requires the task's publication receipt, the matching fresh repository/scope, and a completed checkpoint when a checkpoint exists for that target; a mode without a checkpoint does not fabricate one. A stale attempt or lease generation cannot claim success. Receipt ownership is task-scoped, so an expired attempt may be reclaimed and converge on the already published result without allowing the stale attempt to complete. The external worker response must wait for this terminal task transition.

## 5. Code Quality Constraints

- No tracked source, test, documentation, script, or workflow file may exceed 1000 lines. Generated release lockfiles required by locked builds, currently `Cargo.lock`, are exempt and must stay machine-generated.
- Root README files are concise entry and navigation surfaces. Detailed implementation ownership and operational contracts belong in the responsibility-specific architecture, capability, or user-guide documents linked from those READMEs; README growth must not bypass the same 1000-line limit.
- Do not add shallow functions; functions must validate, transform, isolate boundaries, manage resources, map errors, add observability, or coordinate real workflows.
- Do not keep dead code, TODO stubs, unused public APIs, untested speculative extension points, or commented-out implementations. A unit test is not a production caller: shared retrieval term normalization keeps only the operations consumed by reranking and must not retain identifier classifiers, stemmers, or public data shapes behind `#[allow(dead_code)]`.
- Project identity constants live in the `project` module; module-local operational defaults stay with the owning module.
- `unsafe` is prohibited by default unless the boundary, reason, and tests are explicit.

## 5.1 File Watcher (fs.watch) Constraints

- File watching uses the `notify` crate for cross-platform support (Linux inotify, macOS FSEvents, Windows ReadDirectoryChangesW).
- Watch events must be debounced within a configurable window to prevent unbounded task generation from high-frequency file changes.
- Content hash filtering (`ContentHashCache`) must skip save operations with no actual content change.
- `max_watch_dirs` must cap the maximum watched directory count to prevent fd/inotify watch resource exhaustion.
- Watch failures must auto-degrade (Degraded state) and must not affect query hot paths or the async runtime.
- Watcher configuration must load through the `env` module environment variable override mechanism; no other module may read watcher environment variables directly.
- Watcher state and diagnostics must be exposed through the `service status` API.
- Incremental index tasks (`CodeIndexTaskSeed`) must enter the durable task queue; durable task leases, checkpoints, and bounded retry must not be skipped.
- The watcher root contains only its facade and the physical `config/`, `event_filter/`, `hash_cache/`, `task_seed/`, and `engine/` subdomains. The first four owners respectively own typed runtime configuration, path/language event admission, bounded content-hash observations, and durable overlay task-seed construction, each with direct `mod_tests.rs`; task-seed invariants must not drift into engine integration tests. The real `watcher::engine` subtree keeps `mod.rs` for public handles and startup, while `event_loop`, `repository_registry`, `index_queue`, and `diagnostics` own OS events, dynamic watch roots, durable-task projection, and status updates respectively. Dependencies flow from engine into the four focused root owners, never in reverse. Cross-owner async behavior is protected by the colocated engine integration harness; do not restore flat `config.rs`, `event_filter.rs`, `hash_cache.rs`, or `task_seed.rs`, or flatten engine responsibilities back into one file.

## 6. Documentation and Test Constraints

- Code, configuration, behavior, tests, workflows, benchmarks, installation, and operations changes include matching documentation refreshes.
- Unit-test, Rust-integration, benchmark, browser-integration, and architecture gates remain distinct; the architecture graph/report artifact is retained for failure diagnosis.
- Rust line coverage stays above 90%, including invariants, error branches, boundaries, async cancellation, and backpressure.
- Browser integration gates install Playwright Chromium, for example `uv run --extra dev python -m playwright install --with-deps chromium`.
- Documentation changes check links, numbering, line limits, and stale state.
- Knowledge Map writer schemas use staged rollout. CI always validates `knowledge/knowledge-map.yaml` and `codespec/codespec-map.yaml` with the current source CLI and installs the latest stable crates.io CLI for a second validation. When stable is older than the declared minimum v4 reader, `1.1.17`, incompatibility is emitted as a `staged_pending_reader_release` artifact only when the source version is newer; the same-version mismatch is an `incompatible_same_version` hard failure. Once stable reaches the minimum reader version, any incompatibility fails the gate. The default writer schema must not advance again before a compatible reader release exists.

## 7. Acceptance Criteria

- A new module can name its ownership boundary and show why it does not create a dependency cycle.
- New background or network behavior states budgets, failure modes, cancellation, and observability metrics.
- New retrieval or performance work explains a general mechanism, not only why one example passes.

Repository Map v4 must retain at most 16 contiguous recent history entries in each root and must not create or reference repository-local history archives. `omitted_through` records the last intentionally discarded version; requests at or before that checkpoint fail explicitly, and long-term audit relies on Git or repository backups. Migration must validate the complete authorized legacy archive chain before publishing v4, publish both current and fallback roots in v4 before cleanup, and remove only recognized generated archive files through a bounded, resumable, path-confined cleanup. Symlinks, unknown entries, and integrity failures stop cleanup without deleting unrecognized data.

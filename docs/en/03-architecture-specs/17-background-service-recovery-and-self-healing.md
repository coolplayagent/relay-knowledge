# Background Service, Recovery, and Self-Healing

## 1. Design Conclusion

Background service operation is not an unmanaged CLI loop. Long-running refresh, indexing, maintenance, diagnostics, and silent updates run under platform service managers with bounded resources, persistent leases, startup reconciliation, and dead-letter recovery.

## 2. Runtime Modes

| Platform | Manager |
| --- | --- |
| Linux | systemd |
| macOS | launchd |
| Windows | Windows Service |

CLI may generate service definitions and run doctor checks, but it does not pretend to be the resident service manager.

Service deployment supports `resident_single_process` and future `split_worker_preview`. In single-process mode, the control-plane API, startup reconciler, operator, and workers run in one process. In split-worker mode, independent workers may work only after claiming durable tasks from the control plane; they must not create unmanaged scheduling loops, directly read or write shards, skip QoS, or bypass application services.

## 3. Work Queues

Every background task has kind, scope, priority, budget, attempt, lease owner, lease expiry, target graph version, payload hash, and last error. Queue capacity is a hard ceiling; enqueue failure returns overload or retryable errors.

A cross-process worker lease is authorization for data-plane writes. Renewal, completion, failure, and targeted orphan recovery compare the observed owner, attempt, and monotonically increasing publication generation; orphan recovery also compares the observed expiry so a delayed scan cannot revoke a lease that was renewed meanwhile. A worker cannot complete, fail, renew, or commit data-plane writes when it does not hold a valid lease, the lease expired, any attempt token does not match, the task was reset, the task was reclaimed, or the task entered dead-letter. Expiry remains irrevocable for that attempt: recovery and a new claim must advance the attempt and generation before checkpoint replay. Control-plane status must explain active, running, retrying, and dead-letter sources; process existence is not evidence of task success.

## 4. Reconciler

The startup reconciler:

- Replays mutation-log refresh work that was missed.
- Recovers expired leases.
- Preserves dead-letter isolation.
- Reports index lag, queue depth, stale scopes, and failed cursors.
- Corrects cursor state when graph version advances while a task is running.

## 5. Silent Updates

Silent updates are user-configurable, pausable, observable, and reversible. They refresh graph data and derived indexes only within authorized scopes and expose fresh, stale, paused, degraded, and failed states.
Resident local file indexing follows the same rule: scanners run only on
configured absolute roots, reject relative root configuration before scanning,
persist cursors and diagnostics, enforce scan/query timeout budgets, and report
truncated roots, scan errors, freshness, and lag instead of blocking query paths
or silently expanding to unapproved disks.

File-system watchers and scan workers degrade by platform capability: Windows may use USN cursors, macOS may use FSEvents cursors, and Linux may use inotify/fanotify or periodic bounded rescans. Event overflow, journal reset, permission changes, missing roots, and cursor invalidation become recoverable diagnostic states instead of unbounded whole-disk scans.

Cold code-repository full indexing uses the same recovery shape. `repo index` performs tracked source-layout discovery and then persists a code-index task with a source scope, input fingerprint, payload, resource budget, attempt count, retry cursor, and lease fields; foreground CLI starts only a bounded single-shot worker, and resident `service run` acts as the master that recovers expired code-index leases and orphaned `code-index-worker-<pid>` leases at startup before draining the durable queue with a bounded repository index worker pool controlled by `RELAY_KNOWLEDGE_CODE_INDEX_MAX_IN_FLIGHT`. Distinct fingerprints can queue concurrently, but claim enforces at most one live writer per repository; different repositories can still claim independent leases, checkpoints, and retry state. Identical full-index fingerprints reuse unfinished work so the same source scope is not rebuilt twice. Expired running leases are recovered before claim and status paths report active work: recoverable attempts move to retry with `lease_expired` diagnostics, attempt-exhausted tasks move to dead-letter, and late workers cannot complete or fail a task after their lease has expired, been reclaimed, orphaned, or explicitly reset. Service startup checks `code-index-worker-<pid>` lease owners and recovers running tasks whose owner process has exited with `lease_orphaned`, while preserving leases for workers that are still alive. An explicit repository index reset may requeue unfinished code-index tasks by clearing lease owner, lease expiry, attempt count, retry cursor, and last-error fields, but it must not run while another task has an unexpired running lease for the same repository, delete completed indexed scopes, revive terminal dead-letter history, or bypass lease-guarded completion. Active workers renew the lease before expensive batch parsing, after each committed checkpoint batch, around finalization, and before task completion; stores that do not implement the optional recovery or renewal hooks keep those hooks as no-ops. Git blob materialization for cold batches uses bounded `git cat-file` commands with explicit stdin close and timeout handling; a stalled Git child returns a task failure for retry/dead-letter handling instead of keeping the lease forever. Checkpoint `updated_at_ms` remains visible for stuck-task diagnosis. Repository-set overlay refresh tasks use the same resident-service model: every CLI/Web default-synchronous or async request first persists into one bounded durable queue. A local default-synchronous request drains only when its exact task is claimable; otherwise it returns queued, and `service run` drains the queue with one repository-set overlay refresh worker. Admission transactionally supersedes older queued/retrying work for the same set, caps unfinished work at 2 tasks per set and 128 globally, and claim permits only one live writer per set. Overlay edges and member replacements publish together in one attempt-scoped live-lease transaction; takeover makes the stale attempt roll back. Queue and completion maintenance retain 64 successes per set and 32 rows for each failed, dead-letter, or cancelled state, with each audit-prune delete capped at 64 rows. The workers mark retry or dead-letter on failure. This overlay capability remains unsupported by `partitioned_sqlite` until cross-shard import/export aggregation exists; successful code-index publication starts the protected durable-retention workflow described below.

Manual repository-set overlay capacity is fixed at 64 members and 64 fact-version replacements per publication. Across all members, one refresh shares ceilings of 4,096 manifest chunks, 16 MiB of manifest path/content bytes, and 32,768 manifest-derived items. The durable leased task scans immutable import rows from member scopes with a `(source_scope, import_id)` primary-key cursor in 512-row pages, admits at most 262,144 scanned rows, and filters unresolved external candidates in memory; resolved and local rows consume the same scan budget. It separately caps file/symbol export targets at 131,072, cross-member candidate edges at 8,192, and combined origin/target selector keys at 512. Imports without a member export candidate remain unresolved source-scope facts instead of being duplicated into the overlay. Matching inspects at most 11 exports per import and records at most 10 candidate IDs, so `candidate_count` is a bounded observation. Every scan, persisted collection, and read path uses cap-plus-one detection and returns `CapacityExceeded`/`qos_rejected` rather than truncating and publishing a false `fresh` result; the final transaction revalidates the task lease and member-version snapshot before publication. Direct and selector reads inspect at most 8,193 edges and filter either retiring endpoint. Refresh, add, and member removal also inspect at most 8,193 existing edges before any delete. Whole-repository removal admits at most 64 affected sets and preflights each overlay; more sets or any overlay above 8,192 edges rejects the transaction unchanged. A legacy over-cap manual overlay is rejected unchanged rather than issuing an unbounded `DELETE`; this release has no bounded repair entry point, so remediation requires an upgrade-provided repair tool and is not a closed cleanup loop. These ceilings do not yet govern the opt-in automatic-workspace cross-edge materialization path: phased scope GC bounds deletion of its obsolete state, but one build remains a documented resource-boundedness gap and workspace detection stays disabled by default.

A reclaimed full-index attempt prepares the source plan again and restores its cursor only from a checkpoint that proves the same repository/scope/commit/tree/filter identity, the task's durable resource budget, equal parsed and committed counts, a bounded deterministic path prefix, a valid state/batch count, and the exact prefix last path. Any in-memory parse overflow belongs to the expired attempt and is never considered durable. Read-only plan validation captures the complete expected checkpoint, including the missing-checkpoint case; session `begin` compares that token inside its write transaction before changing repository status or checkpoint rows, so a checkpoint inserted or advanced between preflight and `begin` fails without making the previous fresh scope stale. Corruption returns an internal 5xx-class consistency error, immediately moves the claimed task to durable dead-letter with `checkpoint_invariant`, and leaves repository/checkpoint state observable rather than turning it into user input or silently retrying from a guessed cursor. A distinct completed same-content checkpoint may carry an older commit alias. If that content scope is still published, non-retiring, software-current, and query-index-current, fenced reconciliation reactivates it in one metadata-only transaction, preserves the previous active commit alias, updates the target checkpoint/receipt, and never runs finalization pages against queryable facts; partitioned reconciliation may locate the retained scope through the repository shard before atomically changing the catalog route. Otherwise the plan classifies the exact checkpoint case as `ContentEquivalentRestart`, never `Resume`, and SQLite and partitioned SQLite compare the full preflight token. When the partitioned API projects an active shard's raw `finalizing:partitioned_publish` state as `completed`, it first materializes that completed state under the exact raw-token CAS and current publication fence without changing the checkpoint timestamp, then starts the CAS-guarded restart. Storage returns a new-commit, zero-progress `indexing` checkpoint that the application validates before work continues. This exception requires completed state plus matching repository/scope/tree/filters/path count/resource budget; partial or finalizing commit mismatches and every other mismatch remain `checkpoint_invariant` and immediately dead-letter. Every recognized `finalizing:*` checkpoint preserves facts and resumes after its last committed phase. Under a fence, scope staging and workspace-import resolution commit as separate stale phases before software projection, so either can resume without early publication; software-projection, partitioned-publication, and completed states retain their publication shortcut, and a recovered receipt response reports the task's durable resource budget. Batch gaps fail before staging. A batch index already covered by the checkpoint is a fence-validated pure no-op: even a conflicting duplicate cannot reset its published staging manifest, replace facts, or regress progress. Consequently retries avoid repeated parsing of committed work while retaining leases, single-writer fencing, bounded batches, FTS writes, finalization, and freshness. This recovery optimization has no effect on the duration of a first cold-index attempt.

A task queued solely to repair an active completed scope first attempts the same exact publication reconciliation. If reconciliation fails because the software projection is missing or stale, a public `completed` checkpoint continues through fenced automatic-workspace cleanup and software projection refresh rather than being reported as a partitioned handoff failure. A genuinely raw `finalizing:partitioned_publish` checkpoint that cannot reconcile still fails closed. This distinction keeps active-scope derived repair leased and replayable without weakening the raw shard-to-catalog publication barrier.

Commit-driven indexing is a reconciled durable workflow, not a best-effort hook. With the watcher enabled, narrow `.git` ref notifications trigger low-latency checks and the resident loop also performs bounded `HEAD` reconciliation at startup and every configured interval. The periodic check is the recovery cursor for linked worktrees, lost events, and restarts. It compares resolved HEAD with the last published clean commit, pins the immutable base/head/tree, and queues Incremental work under a stable per-ref fingerprint. Repeat hints coalesce, while the existing queue claim still enforces one active writer per repository. The manual `repo update` entry point uses the same immutable resolution and durable task path. If no clean base exists, the operator must full-index first; if the commit-pair delta exceeds 512 changed paths before registered filters, the task fails with guidance to full-index.

Partitioned SQLite does not treat an `ATTACH` transaction across independent WAL files as power-loss atomic. Before a worktree snapshot enters its shard transaction, a control-only `BEGIN IMMEDIATE` transaction validates the live lease, attempt, publication generation, content-derived target identity, and 64-slot capacity, then durably replaces the provisional task target with the real scope. The shard publication subsequently sees an exact idempotent target; the remaining attached authority update is only the attempt lock and carries no rebind state. A crash on either side leaves the bounded task row as the handoff record, so startup lease recovery and the normal retry path replay the same target, while a takeover generation cannot prepare or publish through the old fence. Single-SQLite mode keeps its original same-transaction rebind.

A partitioned checkpoint route is staged idempotently under the current task fence before the shard commits session begin or a batch. The staged route is a crash-recovery locator, not a publication claim: active-only reads ignore it, while checkpoint lookup can locate the shard after reopen. A crash before the shard commit leaves no checkpoint; a crash after it exposes the exact checkpoint so the same task and fence can resume by compare-and-swap.

Successful code-index publication then runs durable retention. It preserves the union of active and a rolling window of the two latest successes (normally including active), the latest successful incremental predecessor, the clean base of any active worktree overlay, plus unfinished task target/base scopes and repository-set pins. One transaction atomically marks one old scope `retiring` and records a GC job; later maintenance transactions advance one scope-GC phase whose physical deletion is capped at 512 rows in aggregate across affected application tables, including facts, FTS/search rows, software projections, checkpoints, workspace state, or scope metadata. Separate fixed quotas permit at most 512 succeeded task-audit rows, 512 failure-class task-audit rows, and 512 commit-alias rows in the same pass, capping primary cleanup at 2,048 physical rows plus at most one terminal GC-job bookkeeping row. Retiring scopes are unavailable to readers and incremental bases, and the managed worker retries jobs while idle. Admission refuses a new target when one repository already has 64 distinct published, checkpointed, or unfinished scope identities, returning maintenance backpressure until GC releases a slot. This bounds retained live generations and lets SQLite reuse freed pages, but does not promise immediate OS-visible database-file shrink; reclaiming that physical high-water mark requires a separate explicit, bounded maintenance compaction. Retained/prunable scope arrays expose at most 64 entries each; `scope_listing_truncated=true` marks their arrays and displayed counts as bounded diagnostic projections and observable lower bounds rather than an exhaustive protection set, and partitioned shard maintenance pauses if control-plane pins are truncated. Before a shard enters its final `scope_metadata` phase, maintenance removes the control-plane route; a crash can replay the deterministic shard job without exposing a stale route. Same-tree commits share content through a bounded 256-row commit-alias window; when an upgraded legacy scope has no alias row yet, its previous commit is preserved lazily in the next same-content publication transaction instead of running an unbounded database-open backfill. Finished task history is capped at 128 successful and 64 failed/dead-letter/cancelled rows per repository, retaining the latest success for each protected scope. `repo status` exposes job progress and errors. A pruned ref requires full indexing.

The search cleanup state machine removes metadata-owned rows first, then advances a durable `search_orphans` phase through the global FTS rowid space in pages of at most 512. It never performs an unbounded predicate scan on the FTS `UNINDEXED` scope field: each bounded page is materialized by rowid, and only rows belonging to the retiring scope with no exact rowid/scope/kind/record/path metadata owner are deleted. A remaining target metadata owner fails the page closed without deletion or cursor movement. The job checkpoints the last inspected rowid even for a zero-match interleaved page. Data deletion, deleted-row accounting, cursor movement, and phase transition share one transaction; rollback/reopen replays the same cursor, and EOF clears it before later fact phases continue. Installation of this phase atomically rewinds only pre-capability jobs that had already advanced beyond it, so a crash cannot strand legacy FTS orphans after scope metadata disappears.

The nginx-style split of responsibilities is explicit even in `resident_single_process`: the master owns runtime configuration, worker pool sizing, startup recovery, queue supervision, service-manager shutdown, and diagnostics; workers own only leased task execution and cannot bypass the application service or storage trait. This gives the local runtime the main operational advantages of master-worker architecture without adding process-level deployment cost: bounded parallelism, fast rejection or degraded status under overload, deterministic recovery after crashes, observable queue depth and worker slots, and predictable query behavior while indexing is running. `service status` must expose code-index master-worker diagnostics including configured worker count, active worker slots, queue depth, queued/running/retrying/dead-letter task counts, running leases, and last error.

Large repository indexing must not block service liveness or ordinary read queries. SQLite writes must pass through a single writer lane with bounded transient busy/locked retry; health, graph/status/report, file query, and code query paths should prefer bounded read-only connections over committed snapshots. Lock contention must be surfaced through task status/checkpoints and bounded busy diagnostics, not by asking operators to kill competing `relay-knowledge` processes or by adding unbounded SQLite waits. `health` does not run diagnostic reconcile writes, does not queue refresh work, and returns stale/degraded `storage_busy` when it exceeds its short budget. Code queries with `allow-stale` read the previous completed scope while the requested ref is indexing and mark the response stale/degraded; `wait-until-fresh` is the mode that may reject an unfinished target scope.

Overload handling follows SRE and adaptive-concurrency principles: when queue, IO, CPU, or provider budgets saturate, the system rejects new background work first, delays low-priority content indexing, preserves query hot-path budget, and returns retryable, paused, or degraded states.

The older “active plus the two newest” shorthand above denotes a set union: the latest-two window normally already includes active, so it normally retains two clean successful scopes rather than three.

For local operation without the resident service, `repo index-worker` is also the explicit bounded maintenance recovery entry point: each invocation advances at most one retention pass and exposes `maintenance_active` plus optional `maintenance_error`. A captured error makes a false activity value inconclusive, while the code-index task result remains separately represented. This lets a repository rejected at the 64-scope admission boundary drain GC and retry without direct database edits. In partitioned storage, a control catalog route remains a counted capacity reservation throughout bounded shard fact deletion; the coordinator, rather than generic control GC, removes the route immediately before the final `scope_metadata` shard transaction. A crash after route removal replays the deterministic shard job without restoring a stale route.

Leased code-index finalization uses an explicit step-boundary protocol rather than relying on a concurrent heartbeat to win the SQLite writer mutex. After the parser and writer drain, the application reloads the durable checkpoint, requires its complete repository/scope/commit/tree/filter/budget identity and committed file prefix, and derives the hard step bound from that reloaded reference count rather than the begin-time count; a missing or drifted checkpoint fails before the first quantum. The application then performs strict authoritative-time renewal, advances exactly one durable finalization quantum, and renews again before observing `Pending` or `Ready`; every `Pending` token must differ from the preceding token, and the derived hard step bound prevents an unbounded loop. SQLite releases its writer mutex after every quantum, and partitioned storage delegates the same one-step contract to the staged shard. Each quantum validates its publication fence before and after its operation; validation first acquires the exact authority writer lock and only then samples execution time. If even one index build exceeds the lease, the post-operation validation rejects the expired attempt and rolls back that index and its checkpoint cursor together instead of reviving the lease or publishing partial progress. Lease claim, global expiry recovery, operator reset, renewal, completion, and failure transitions likewise sample execution time only after `BEGIN IMMEDIATE` obtains the writer lock. Their caller `now_ms` values are observations only and a future observation fails closed; all live/expired predicates, lease deadlines, retry deadlines, and write timestamps use authoritative execution time. Failure to read or represent that authoritative time is an invariant error that aborts the publication transaction; publication fencing must never substitute epoch zero or a clamped value for a failed clock sample. Expiry is irrevocable, and owner/attempt/generation/authority CAS remains strict. Post-index optimize/checkpoint maintenance runs best-effort only after task completion is terminal, records diagnostics, and cannot reverse the completed result.

Software-global projection follows the same writer-quantum rule. The legacy `finalizing:software_projection` checkpoint decodes as reset, then durably advances through `finalizing:software_projection:v1:{reset|dependencies|sdk_usages|lifecycle|files|topics|relationships|publish}`. Each phase commits at most one deterministic derivation boundary, with phase rows and the next token in the same transaction; both transaction entry and pre-commit validate the source scope, repository, and live publication fence. SQLite releases its writer between phases so the outer lease heartbeat gets a deterministic renewal opportunity. Recovery resumes after the last committed token without restarting the parser or a completed phase. Intermediate projection rows remain `stale=1` and their target scope is not queryable. Only the final publish phase atomically updates business mapping, software status, scope publication, terminal checkpoint, and the local receipt. Single SQLite and partitioned shards share this protocol; a partitioned store still performs its control-fenced catalog handoff after the shard reaches its terminal state.

Large staged finalization applies that same one-step contract first to ordinary-reference resolution and then to grouped-v2 reference-search cleanup, discovery, and build pages. Ordinary resolution records `finalizing:resolve_references:v1:resolve:{page}:{count}:{cursor_digest}`; its progress row carries the exact cursor and resource-derived limits, and direct or nested query-index-repair reopen must match page, count, digest, frozen committed count, and cursor before any write. Grouped cleanup keysets exact metadata owners by record ID; discovery keysets reference facts and persists one owner plus occurrence count per exact identity; build keysets group IDs and uses the canonical encoder. Its checkpoint token carries protocol version, stage, and completed page ordinal, while record/reference/group cursors and frozen totals remain in a checkpoint-owned progress row until the exact group total completes and a current manifest is published. Both protocols reserve progress and checkpoint control mutations, bill their conservative complete records against the same byte quantum, and use length-only lazy scans that stop before fetching an over-budget cursor or building large payload text. A rollback or reopen therefore replays the same keyset page without inferring progress from FTS metadata or restarting parser/blob work. Before and after every page, the shard must still be locally non-queryable and, for partitioned storage, the catalog route must still be staged for the same task under the same live fence. An append-only query-index repair encountered between pages wraps and preserves the exact inner token, advances one descriptor per transaction, and restores that token only after complete current-plan validation. A stale fence, changed route, query-index collision, count/cursor mismatch, malformed token, oversized first row, or exhausted checked `CODE_INDEX_FINALIZATION_MAX_STEPS + 4 * references + 6` bound fails closed without advancing a cursor. Retained grouped v1 cleanup/build state is restarted under the live fence at v2 cleanup page zero after its durable budget is revalidated and its page limits are clamped to the stricter v2 bounds. Publication and fresh serving require a current grouped manifest; legacy post-progress scopes without one fail closed and require a new fact-versioned full task.

The version-3 query-index finalization plan retains the same 17 ordinal identities established by versions 1 and 2. Ordinal 16 remains the v2-appended import `(source_scope, path, line_start, line_end)` lookup; ordinal 1 keeps its legacy name, owner, and columns but is now a retired stable slot whose index is never newly created or automatically dropped. An absent ordinal 1 is complete only under a v3 cursor or a current coarse scan. The parser preserves canonical v1/v2 token versions across every writer quantum, so a legacy cursor cannot advance through ordinal 1 unless its exact physical shape exists; regular and reference-search v2 repair wrappers obey the same rule. Current formatters emit `finalizing:build_query_indexes:v3:N`, `finalizing:query_index_repair:v3:N:resume:P`, and the corresponding v3 reference-search wrapper. Every nonterminal coarse checkpoint is revalidated against the complete current plan before later work or Ready, with one missing required descriptor repaired per quantum. Repair checkpoints retain the complete file prefix and skip parser/blob/batch restart; the stable `P` code restores the exact prior coarse state, and partitioned repair remains raw/pending. A terminal `completed` checkpoint validates existing shapes but permits a required descriptor to remain missing and is not mutated by this compatibility path. Startup performs read-only exact-shape validation only. Every fresh Restart precreates only chunk ordinals 13 and 14 when their complete owner table is empty, without inferring batch count from path count; resume and populated-owner paths create neither, while every other missing heavy descriptor remains deferred.

Receipt recovery is subordinate to raw/public checkpoint eligibility and the exact software projection. A receipt never bypasses repository/scope identity or software-projection freshness checks; a missing or stale projection returns pending so the same unfinished worker task performs the fenced refresh before recovering its response. After the raw/query-plan, scope-status, exact fresh projection, and final checkpoint gates all pass, an exact task/repository/scope receipt returns success without republishing the catalog; only an absent receipt performs that idempotent publication. Raw repair tokens and raw partitioned-publication tokens with an incomplete current plan likewise return pending even when a receipt exists. A catalog-inactive, task-owned staged partition with legacy raw `completed` may be CAS-restored to raw partitioned publication only by exact begin under its current live fence and control-authority lock; this enables durable repair without weakening the catalog-active historical terminal exception.

A durable incremental delta additionally stores canonical `incremental_summary_json` in its scope checkpoint before it hands off to `indexing`. The receipt is bounded by the frozen byte/file/row budget and binds the task, base commit, changed/skipped/deleted/affected counts, blob/parse/write/degraded counts, and the single delta batch. The same task may consume it only after repository, scope, commit, tree, filters, resource budget, live fence, and checkpoint state all match; a completed checkpoint with a stale software projection therefore resumes the receipt-owned finalizer and returns the original delta metrics after fenced projection repair. Another task may adopt the same terminal content scope, but it must never reuse the first task's metrics: the terminal checkpoint CAS clears the old receipt in the same fenced adoption or generic-repair transaction, and the adopting response uses the established no-work summary. A nonterminal task mismatch fails without mutation. Storage enforces this ownership again inside each finalizer transaction; only a terminal `completed` or raw partitioned-publication checkpoint may transfer to a session with no incremental base, and its CAS binds the exact old state and canonical receipt. A crash before the CAS leaves the old receipt intact; a crash after it leaves a generic terminal checkpoint, so neither path can forge or replay another task's delta summary.

Ad hoc direct writers cannot bypass recovery ownership. Single-database direct checkpoints are durable queue reservations: another target cannot queue past an unowned nonterminal checkpoint, while same-scope adoption immediately fences subsequent direct batch, finalization, and automatic-workspace cleanup quanta. Partitioned data-plane mutation has no unfenced recovery mode; snapshot, checkpoint, batch, finalization, and workspace cleanup must carry the current durable task fence so control authority and shard progress cannot diverge across cancellation, takeover, or restart.

The optional no-op renewal compatibility applies only to stores that do not advertise fenced single-step finalization. A store that implements the single-step contract must also implement strict renewal; otherwise the leased task fails closed before its next writer quantum.

## 6. Acceptance Criteria

- Crashes and restarts do not lose required refresh work.
- Diagnostic paths do not automatically revive dead-letter tasks.
- CPU/IO-heavy background work does not block query hot paths.
- Watcher lag, scan backlog, cursor invalidation, and overload decisions are explainable through health and service doctor.
- Missed Git notifications, linked-worktree metadata, and service restarts converge through bounded periodic HEAD reconciliation.
- Scope and completed-task retention stays bounded without deleting bases or targets referenced by unfinished tasks or repository sets.
- Repository-level retention preserves registration and concurrent index work, and never selects a user-managed repository-set member.
- Repository-level retention preserves registration and concurrent index work, and never selects a user-managed repository-set member.
- Split-worker deployments preserve durable task leases, bounded retry/backoff, checkpoint replay, dead-letter isolation, and per-repository active writer constraints.
- Partial full-index retries skip only a strictly validated committed prefix; they never infer progress from an invalid checkpoint and do not claim first-attempt cold-index speedups.

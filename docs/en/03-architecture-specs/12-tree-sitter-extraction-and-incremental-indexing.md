## 1. Design Conclusion

Tree-sitter is the entry point for code structure, not a complete semantic analyzer. The architecture connects grammar registration, query capture, error degradation, incremental candidate narrowing, and index refresh into a recoverable pipeline. Unsupported languages or unrecoverable parse errors degrade local capability only and do not break retrieval; recoverable C/C++ macro, preprocessor, and decorator parse errors should keep structured facts available when extraction remains reliable.

## 2. Language Registry

Each language registration includes language id, file extensions, tree-sitter grammar, capture queries, comment rules, identifier segmentation, and fallback chunker. When grammar is missing, files still enter text chunk and BM25 paths. Query-time source fallback is not a grammar substitute; it only adds exact-text evidence from indexed source candidates and cannot create graph facts.

Configuration, build, and template grammars are registered under the code configuration module rather than runtime configuration. The supported surface includes Markdown, XML, Bazel/Starlark, Make, CMake, Dockerfile/Containerfile, Java properties, TOML, INI/`.conf`, YAML, JSON, Go module files, Ninja, Jinja2, and Go templates. These formats emit ordinary file, symbol, reference, import, dependency, feature-flag, and chunk facts so query APIs do not need a separate schema for configuration search. SQL is registered as a code grammar for `.sql` files; it emits schema object symbols for tables, views and materialized views, functions and procedures, triggers, and types, plus SQL object references and call references through the same repository code graph tables. Hierarchical configuration formats must emit stable dot-separated paths; arrays and array tables use `[]` instead of numeric indexes, for example `server.port`, `containers[].name`, and `bin[].name`.

Structured documentation and configuration files combine Tree-sitter AST extraction with product rules. Tree-sitter identifies Markdown headings, link definitions, inline links, JSON pair/array nodes, and INI section/setting nodes with ranges and error nodes; product rules normalize JSON arrays into `[]` paths, join INI sections and settings into dot-separated names, filter external or anchor-only Markdown links, and write local Markdown links as unresolved import metadata. Markdown and configuration files must keep a file-level chunk even when symbol-level chunks exist so body text, config values, and local parse failures remain retrievable through BM25/hybrid search.

Parser implementation must keep language-specific rules under cohesive language directories. Node-kind classification, language-specific import extraction, and C/C++ manual recovery belong under `src/relay_knowledge/code/parser/languages/<language>/`; shared parsing flow, syntax helpers, text validation, dependency manifest parsing, and chunk construction remain in parser-level modules.

Bash import extraction treats the shell-escaped dot builtin `\.` as semantically equivalent to `.`. Recognition is limited to the exact command token followed by whitespace and a non-empty operand, so prefixes such as `\.helper` are not imports. The parser preserves the original source spelling and range, while local target resolution applies the same bounded path rules as the ordinary dot builtin.

Rust trait implementation items use a language-local structured supplement: `impl Trait for Type` emits one `implementation` symbol named for the target type and spanning the complete implementation item. Inherent `impl Type` blocks do not emit this supplemental symbol, because their contained methods already provide structured facts and duplicating every inherent block would expand definition candidates without adding a trait relationship surface.

## 3. Capture Contract

Query captures emit a common structure: definitions, references, calls, imports, feature flag/config usage, documentation comments, symbol spans, body spans, and chunk spans. Capture output is validated for scope, path, line/column, and content hash before write.

Symbol documentation includes both existing language-specific line-doc forms and an immediately adjacent documentation block. `/** ... */` is the symbol-level block form; `/*! ... */` is accepted only for languages where it denotes owner documentation. In Rust it is an inner module/crate document and is deliberately not attached to the next declaration while module-owner facts are not modeled. Block normalization removes delimiters, CRLF residue, surrounding blank lines, and each line's leading `*`; an ordinary `/* ... */` comment is never promoted to documentation. Ordinary symbols retain a 4,096-byte owner lookback. Type declarations such as classes, interfaces, structs, and traits may use a UTF-8-safe scan window of at most 16,384 bytes so valid long type-level Javadoc remains discoverable. The scan and persistence budgets are separate: regardless of scan size, only a UTF-8-safe leading summary of at most 4,096 bytes and 64 lines is persisted. Whitespace between the block and owner consumes the same scan budget, an older block cannot appear adjacent, and the summary binds only to the immediately following declaration.

Documentation ownership and symbol extent are separate capture facts. A C/C++ tag may expose only a `function_declarator`; its documentation anchor therefore rises to the containing declaration or function definition and then through an enclosing template declaration. Java annotations remain inside their declaration owner. This anchor is used only to locate adjacent documentation: it does not expand the symbol byte/line range, signature, or stable identity. When a wider manual symbol representation replaces the same capture, already extracted owner documentation is retained. These semantics are persisted under the `doc-block-owner-anchor-v2` and `bounded-type-doc-summary-v1` code-fact components and require a fresh, recoverable index build.

## 4. Full Build

```text
resolve snapshot
  -> enumerate authorized files
  -> batch parse and chunk
  -> write file/symbol/reference/feature-flag/chunk facts
  -> finalize cross-batch edges
  -> refresh scoped code search documents and software projection
  -> mark scope fresh
```

The old fresh scope continues serving queries during full builds; the new scope becomes fresh only after finalize succeeds.

Fresh full-index reuse is a read-only eligibility path, not a derived-index refresh path. It may return immediate completion only when the exact content/workspace scope's compatibility checkpoint is absent or terminal `completed`, its software projection is present and explicitly non-stale for the same repository and scope, and a disabled workspace request has no repository-owned automatic workspace state left to remove. It must not compare the projection with the unrelated global graph version. A nonterminal checkpoint, missing or stale projection, or required disabled-workspace cleanup queues the ordinary durable code-index task; the live attempt fence then covers cleanup, projection rebuild, receipt publication, and the partitioned catalog handoff. Reusing a genuinely fresh scope performs no SQLite write and truthfully reports zero write progress.

SQLite finalization advances in durable writer quanta. Query-index construction now formats `finalizing:build_query_indexes:v3:N`, where `N` is the ordinal of the last completed slot in the 17-slot version-3 plan. Version 2 had preserved version-1 ordinals 0 through 15 and appended `code_repository_imports_scope_path_line_lookup` as ordinal 16; version 3 preserves all of those ordinal identities and retires only the creation action for ordinal 1, `code_repository_symbols_lookup (source_scope, name, qualified_name, path)`. The retired slot is never newly created or automatically dropped. If the same name exists, startup, cursor validation, repair, and publication still require its exact owner, non-unique/non-partial form, ordered columns, ascending direction, and `BINARY` collation. If it is absent, only a version-3 cursor or a current-plan coarse scan treats it as a stable skip. Canonical version-1 and version-2 tokens remain readable with their version attached and preserved across every writer quantum: a legacy cursor cannot advance through ordinal 1 unless that exact physical index exists, so neither a completed prefix nor a later suffix is reinterpreted. Malformed, out-of-range, and unknown-version tokens fail closed.

One transaction validates the complete file prefix and fence, creates at most one required non-unique/non-partial index with its exact owner table and column order, CAS-advances the checkpoint, validates the fence again, and commits. A crash therefore leaves either both the index and token or neither; restart resumes at the next ordinal. Incomplete current construction records the created version-3 ordinal, while completion records coarse `finalizing:build_query_indexes`. Any retained nonterminal coarse state from build through partitioned publication proves only that the former plan committed, so the worker validates the complete current plan before later work or Ready. A missing required descriptor is repaired one per transaction and records `finalizing:query_index_repair:v3:N:resume:P`; version-2 repair and reference-search wrapper tokens remain readable and retain legacy-prefix strictness. The explicit stable `P` code preserves the exact completed coarse phase across reopen. A terminal `completed` checkpoint validates only existing index shapes, permits a required descriptor to remain missing, and is never rewritten opportunistically; automatic terminal repair requires a separately leased durable migration task. Any future ordinal reinterpretation requires another plan-version bump and an explicit recovery rule.

The terminal exception applies only to a catalog-active historical `completed` checkpoint. If an inactive staged partition retains a legacy raw `completed` token while its public projection is still `finalizing:partitioned_publish` and the current query plan is incomplete, exact begin may reopen it only under the current task fence: one shard transaction CAS-checks the full raw token, locks and validates the control authority, proves the catalog route is still staged by that task, and restores raw `finalizing:partitioned_publish`. Durable one-index repair then proceeds normally. An existing receipt cannot bypass this eligibility gate.

The version-3 query-index plan contains 17 stable slots: 16 required descriptors and the retired ordinal 1. Database startup never creates or drops a descriptor and validates every same-name index already present. After clearing its target scope, every fresh `Restart` follows one conservative policy regardless of path count or eventual byte/row batch partitioning: while the shared `code_repository_chunks` owner is still globally empty it precreates only ordinals 13 and 14, `(source_scope, path)` and `(source_scope, symbol_snapshot_id)`, so content-bearing chunk rows never need a later full-table CREATE INDEX scan. Every other missing required descriptor remains deferred, and any populated chunks owner disables both early builds. Resume sessions precreate nothing. Snapshot/import publication may prepare required empty-owner indexes before any fact mutation, then requires every required slot; a populated owner with a missing required index fails closed and leaves the old active scope unchanged. A missing retired slot is complete, while an existing retired-name index must still have the exact legacy shape.

Reference-search finalization uses the staged-only grouped v2 protocol `finalizing:rebuild_reference_search:v2:{cleanup|discover|build}:N`. Cleanup keysets exact metadata owners by `(source_scope, document_kind, record_id)` and deletes the corresponding group, FTS, and metadata rows. Discovery keysets base facts by `reference_id` and UPSERTs one durable owner for each exact `(name, kind, path, coalesce(target_hint, ''))` identity, retaining `MIN(reference_id)` and an occurrence count. Build keysets those group IDs and runs the canonical search-document encoder over the normalized reference fields; it never executes one unbounded scope-wide `DISTINCT`. Each page reserves both the progress CAS and checkpoint CAS, so the conservative three-owner charge admits at most `min((max_rows_per_batch - 2) / 3, 32768)` input rows. The byte limit is `min(max_bytes_per_batch, 16 MiB)` for the whole writer quantum, including conservative full records for the owner rows, progress, checkpoint, and EOF manifest. A single lazy primary-key scan exposes only an integer lookup key, cursor length, and owner-byte bound; Rust stops after the first over-budget candidate and fetches cursor text only after admission. Build sizing adds field lengths algebraically instead of concatenating an arbitrarily large search document. EOF is proven from frozen counts maintained by each bounded page, then atomically publishes a v2 manifest and removes progress. Every page validates the live lease/fence, unpublished route, exact query-index plan, checkpoint token, and partitioned `staged_task_id`. Query-index v3 repair wrappers preserve the exact inner protocol version and page. Retained v1 cleanup/build rows remain readable only for leased recovery: the same transaction validates their exact v1 token and frozen checkpoint count, re-derives the stricter v2 row/byte limits from the durable resource budget, and restarts at v2 cleanup page zero. Publication and fresh serving require the current manifest, while malformed or post-v1 legacy scopes fail closed and are replaced by a new fact-versioned full task.

Ordinary-reference resolution for a fenced, unpublished full-replacement scope uses `finalizing:resolve_references:v1:resolve:{completed_page_ordinal}:{completed_reference_count}:{cursor_digest}`. The progress row persists the exact cursor and limits; every reopen requires the token page/count/digest, frozen checkpoint `committed_reference_count`, progress count, and cursor identity to agree. Page zero has no cursor, continuation proves the cursor row by indexed lookup, completed count cannot exceed `page * page_document_limit`, zero-count initialization proves that no fact exists, and EOF proves both the frozen total and exact maximum reference ID without a prefix count scan. Each page scans at most `min(max_rows_per_batch - 2, 32768)` reference positions after reserving progress and checkpoint CAS mutations. Its lazy keyset scan first reads row identity and lengths, then fetches bounded path/name text only for non-call references; per-page name and `(name,path)` caches use at most two indexed owner-length probes and never retain an ambiguous symbol ID. Call references still count toward the durable cursor and frozen total, but this phase neither fetches their payload nor updates them because the dedicated call-target phase owns both stale-binding validation and callable resolution. The admitted non-call range is resolved by one static first-page or continuation UPDATE, preserving page-local de-duplication, and the page point-fetches only its final admitted cursor. Byte admission charges the conservative complete owner mutations plus progress and checkpoint records before mutation. Direct and nested query-index-repair states both reopen without fetching blobs or restarting parsing. Queryable/unfenced and direct-incremental scopes retain their existing bounded coarse admission and cannot enter this staged protocol; coarse normalization follows the same call-target ownership boundary. The combined checked finalization bound remains the conservative `CODE_INDEX_FINALIZATION_MAX_STEPS + 4 * committed_reference_count + 6`; no row, byte, timeout, lease, FTS, or freshness budget is enlarged.

Reference-search initialization is constant work: it freezes the checkpoint reference count and creates an empty progress row without scanning facts or FTS. Transactional search persistence derives each new FTS interval after its bounded insert instead of scanning the virtual table for `max(rowid)`, and uses non-replacing metadata inserts, so every committed group document has one exact owner or the page rolls back. Database open never scans runtime facts to backfill groups. Exact schema validation requires the group primary/unique keys, binary text identity, path index, manifest/progress `NOT NULL` and `CHECK` constraints, and owner capability markers; an empty malformed owner is transactionally recreated, while a nonempty incompatible owner fails closed. Metadata is the enumeration authority: durable staged writers, bounded direct copies, and explicit recovery imports enumerate indexed owners and never reverse-count FTS through its `UNINDEXED` scope/kind columns. A raw FTS row without metadata is neither copied nor served and remains isolated for bounded `search_orphans` GC; a metadata row without an exact FTS peer fails closed. A direct full snapshot is admitted only for a target with neither a scope nor a checkpoint reservation; it first rejects an oversized all-fact/search-double-write row count, then uses a non-allocating bounded serializer to stop at the byte budget. A direct incremental snapshot first proves a fresh, non-retiring, current-fact-version base with no GC job. Before any mutation it enumerates base facts and grouped owners only through `source_scope`-leading indexes, enumerates FTS through exact metadata rowid ownership, and charges the clone, worst-case path replacement, new facts, search ownership, and publication bookkeeping to one row/byte quantum. Only an admitted snapshot may clone exact owned rows and replace changed paths atomically. Oversized incremental work returns typed `DurableStagingRequired` without target writes; existing targets and workspace projection also require the checkpointed pipeline. Serving first gates the whole fresh scope on its manifest, then MATCHes a bounded group candidate set and expands occurrences with capped water-filling quotas. The representative occurrence is retained, remaining members are deterministically ordered by reference ID, and a fixed SQLite VM-step guard returns observable `CapacityExceeded` rather than silently truncating a hot or residual-heavy group; the handler is always cleared before connection reuse.

Incremental base selection is a fail-closed storage boundary. Queue admission proves the clean base before parsing, and the single-SQLite writer repeats freshness, retirement, GC, filters, fact-version, index-shape, and projection-ownership checks inside the publication transaction. Fenced clean incremental work always uses the durable clone protocol. A worktree overlay without auto-workspace projection first attempts the direct transaction only when its complete clone/delete/insert surface fits the authoritative budget; otherwise the same task and fence stage the content-addressed overlay, clone the immutable clean base in bounded pages, and apply the unchanged dirty delta in deterministic file-owned batches. This preserves the synthetic worktree identity and never converts the request to a semantically different clean full index. Worktree requests with auto-workspace projection remain an explicit fail-closed boundary until a persisted bounded workspace manifest can survive clone/finalization recovery. The application catches `DurableStagingRequired` for a leased clean `Incremental` request whose built target exactly matches the task fence, then reuses the same task, fence, target scope, and resource budget in the durable full pipeline. Existing clone or batch checkpoints resume immediately. Missing or incompatible worktree bases, unfenced authority conflicts, and target mismatches fail closed. Partitioned control-to-shard synchronization copies only the canonical repository row and current alias; it never imports scope facts without a budget. A missing shard base returns the same typed staging signal before fact publication.

Each buffered search-document flush treats its pending-document count as authoritative. Before the FTS mutation, one indexed rowid-equality probe rejects `INT64_MAX`, where SQLite would switch automatic rowid allocation to a non-consecutive random search. After the bounded insert, `last_insert_rowid - pending_count` defines the exclusive interval start; the FTS affected-row count, interval count, and metadata affected-row count must all equal the pending count. A high or same-transaction raw FTS row written before a flush remains below the newly derived interval and stays unowned instead of being scanned or claimed.

## 5. Incremental Update

Incremental indexing first narrows the work set:

1. Use Git diff/status and blob hashes to find changed files.
2. Include deleted, renamed, and moved files.
3. Expand affected files through reverse dependencies and import/call/reference edges.
4. Refresh only affected code facts, chunks, and index families.

Manual `repo update` and resident commit reconciliation both resolve the selected base/head refs to immutable commits and submit the resulting `Incremental` request to the durable code-index task queue. Omitting the manual base chooses the last published clean snapshot, including the clean commit inside a worktree-overlay identity; omitting the head chooses `HEAD`. A repository without that base must complete a full index first. The Git diff is hard-capped at 512 changed paths across the commit pair before registered path filters. Exceeding the cap requires a full index; it is not permission to make the queue, parse set, or write transaction unbounded.

The resident FileWatcher treats `.git/HEAD`, ref, packed-ref, and HEAD-log events as low-latency hints. At startup and on a bounded periodic interval (default 5000 ms), it independently resolves the checked-out HEAD/tree; this reconciliation covers linked worktrees and missed/coalesced events. An advanced HEAD is pinned with the last published clean base into a durable task. A stable fingerprint per repository, checked-out ref, and filter set coalesces repeat hints while the slot is unfinished. Queue admission is transactional and capped at 32 unfinished tasks per repository and 256 globally. The attempt-scoped lease and a monotonically advancing publication generation remain the single-writer authority; every snapshot, batch, workspace, and software-projection transaction validates the live generation before commit, so commit events and detached expired attempts cannot bypass bounded retry/backoff, recovery, or dead-letter state. Full rebuilds retain their batch checkpoints; a clean incremental request is converted under the same task and fence into that checkpointed full pipeline before any direct fact write.

Read-only Git subprocesses in the product source boundary and the self-iteration file-count observer set `GIT_OPTIONAL_LOCKS=0`. This prevents optional index refresh and its incidental `.git/index.lock` during ref, status, diff, tree, and blob inspection; it does not make a mutating Git command read-only and does not replace the durable task lease, publication fence, or fixture writer coordination. Any workflow that intentionally mutates refs, the index, or the worktree requires its own explicit mutation boundary rather than relying on this environment flag.

Import dependency expansion prioritizes indexed code maps and versioned import edges. If an import points to an external dependency or cross-repository target without a code map, the indexer records only the unresolved target hint, resolution reason, and affected current-repository facts; it does not trigger an unauthorized full scan to fill that dependency. This coverage gap is not parser, file, scope, or response degradation. The query layer may use the hint inside the same scope to trigger bounded internal source fallback.

Local configuration relationships resolve only inside the same indexed source scope. Finalization may resolve deterministic local file references, template includes, and build-target references after all files in that scope have been written. Ambiguous local matches and external images, packages, remote labels, or templates remain unresolved or ambiguous metadata rather than degraded parser state.

Feature-flag extraction is an indexing-stage responsibility. Runtime config reads, boolean config declarations, and guarded-code relationships are written as versioned facts under the file scope; the query layer reads only those facts and their FTS documents. Boolean declarations in TOML, YAML, JSON, INI, Java properties, and related config formats reuse the configuration extractor's structured config-key facts instead of a separate feature-flag source. Changes to extractor rules, config files, or guarded branches require a full or incremental index refresh for the affected scope.

Successful publication runs bounded retention only after the new scope and software projection complete. The protected set is the union of active and a rolling window of the two latest successful publications (normally including active), the latest successful incremental predecessor, the clean base of any active worktree overlay, plus all unfinished task targets/bases and repository-set pins. Cleanup atomically marks one older scope `retiring`, removing it from read/base resolution, and persists a restart-safe job. Each subsequent maintenance transaction advances at most one scope-GC phase, whose physical deletion is capped at 512 rows in aggregate across affected application tables, including facts, code FTS/search documents, software projections, checkpoints, workspace state, or scope metadata. The same pass separately deletes at most 512 succeeded task-audit rows, 512 failure-class task-audit rows, and 512 commit-alias rows, capping primary cleanup at 2,048 physical rows plus at most one terminal GC-job bookkeeping row. Same-tree commits reuse the content scope through a bounded 256-row commit-alias window. In partitioned SQLite, an activated shard keeps its raw checkpoint at `finalizing:partitioned_publish`; the catalog-backed public checkpoint projection reports `completed`. A raw query-index repair token remains pending even when its catalog scope is active and is never projected as `completed`; catalog activation or completed-state materialization resumes only after repair restores the exact raw partitioned-publication state. Same-tree adoption may update commit metadata in either a local `completed` checkpoint or that raw partitioned state, but must preserve the raw state so the control catalog and publication receipt remain the cross-database authority. Finished task history is bounded to 128 successful and 64 failed/dead-letter/cancelled rows per repository, preserving the newest success for each retained scope. Status reports pending/job phase/deleted rows/error, and the managed maintenance worker resumes after failure. Pruned commits require full indexing. This scoped code/software contract is not an atomic publication claim for the generic Knowledge Graph or independent semantic/vector generations.

Search retention first removes at most 256 metadata-owned documents, counting the paired FTS and metadata deletes against the 512-physical-row budget. It then enters `search_orphans` and scans the global FTS table by increasing intrinsic rowid in pages of at most 512, rather than filtering the `UNINDEXED` scope column across the whole table. A page deletes only remaining FTS rows for the already-retiring scope that have no exact metadata owner matching rowid, scope, kind, record, and path. If any target row still has a metadata owner, the page preserves both sides and fails closed without advancing, rather than creating a metadata-to-FTS orphan. Its nullable `search_rowid_cursor` advances in the same transaction even when an interleaved page contains no target row; rollback or reopen therefore replays the same page, and the cursor is cleared atomically when EOF advances the job to the next phase.

Every explicit- or implicit-scope-resolving code read must use one deferred SQLite read snapshot from initial scope/`retiring` resolution through all dependent SELECTs. This includes code fact/search reads, repository status/list/scope-status/latest-scope-status, and repository-set status/cross-edge reads; it does not generalize to unrelated single-SELECT reporting. Concurrent phased cleanup may expose the complete old snapshot to that request or a clear retiring error to a later request, never a mixture of partially deleted scope state.

## 6. High-Performance Boundaries

Every grouped reference-search cleanup, discovery, and build range has separate static SQL for its first page and continuation pages. Continuations express a direct indexed `id > cursor` bound instead of a nullable-parameter `OR`, while first pages omit the cursor predicate entirely. Length-only lazy scans stop at the first candidate outside the byte budget and retain only the final admitted lookup key; each page point-fetches exactly that one durable cursor instead of fetching every admitted cursor payload. A discovery page's grouped UPSERT returns the final group IDs and derives both page-group and newly created-group counts from that result; it no longer repeats a separate grouped count scan over the same page. Monotonic `reference_id` keysets make `returned_group_id > previous_group_cursor` the exact new-owner test. This plan change does not increase the page row/byte limits, progress mutation count, writer quantum, or replay surface.

After a grouped build page passes those existing row and byte limits, one ordered `INSERT ... SELECT` projects all admitted groups directly into the FTS owner instead of materializing six strings per group in Rust and issuing repeated `VALUES` statements. The projection uses the canonical reference content field order and blank-field rules. It rejects a pre-existing `INT64_MAX` rowid before writing, derives the new contiguous interval from `last_insert_rowid`, verifies that interval exactly, and creates metadata owners with one scoped `INSERT ... SELECT`. FTS, metadata, page progress, checkpoint CAS, and fence validation remain in the same transaction. The named performance gate requires a 1,025-group page to execute exactly one main FTS insert and one metadata insert, while separate regressions cover blank fields and maximum-rowid rejection. These are statement-amplification and atomicity guarantees, not real-repository wall-time evidence.

The 12-column `code_repository_chunks` base facts use bounded multi-values statements with at most 1,024 input-ordered rows and 12,288 binds, below the bundled SQLite 32,766-variable ceiling. The runtime SQLite variable limit further clamps the group or fails closed below the inclusive 12-variable one-row boundary. The fixed full-group SQL is initialized once and uses the connection statement cache; at most one smaller tail shape is prepared per call. Chunk search documents still pass to `SearchDocumentInserter` in their original order after the base groups. Base facts, FTS ownership, checkpoint advancement, staging publication, and fence validation remain in the same caller-owned transaction, so a tail failure rolls back the earlier full group and leaves the durable staged manifest replayable.

Code indexing follows the shared principles behind Sourcegraph/Zoekt, GitHub Code Search, ripgrep, and Tree-sitter based systems: narrow candidates through path, language, trigram, symbol name, and blob hash before AST capture, edge resolution, or semantic/vector refresh. AST chunks should follow function, type, module, documentation comment, and import-block boundaries; fallback text chunks take over only when structural parsing is unavailable.

For a non-dense symbolized source file that is too large for one file chunk, indexing may retain source windows from gaps outside symbol byte ranges so top-level relationship facts remain searchable. Each window keeps the ordinary 8,000-byte and 200-line limits, and a file may add at most 64 uncovered-source chunks. Therefore the non-dense result is bounded by `symbol_chunk_count + min(uncovered_window_count, 64)`; this cap is a write-amplification and FTS-footprint contract and must not be widened to repair repository-specific recall.

Cold full indexing, semantic embedding, cross-batch edge finalization, large-file skip/hash, and parser-heavy work belong behind master-supervised background worker or maintenance boundaries and do not block query hot paths. Code-index workers claim durable tasks through application services, hold attempt-scoped leases, and execute bounded parse/write batches; interface layers and query paths must not invoke tree-sitter full indexing directly. Incremental indexing records changed file count, affected file count, parse throughput, write batch count, candidate windows, and stale lag so hidden full scans are visible.

Tree-sitter parsing and tag-query extraction use deterministic progress-callback work budgets rather than elapsed wall-clock deadlines. Each callback consumes one work quantum; each stage receives a 4,096-quantum base plus one quantum per 24 source bytes, capped at 32,768. Tree-sitter 0.26.9 checks these callbacks after each 100-operation batch. The valid 28,701-byte, 2,048-level JavaScript regression consumes 430 parser and 450 query callbacks, leaving an order-of-magnitude base margin; the 24-byte scale reaches the hard cap near the old budget's roughly 688 KiB saturation point. A zero budget cancels at the first callback check. This keeps malformed or unexpectedly expensive grammar work hard-bounded without treating scheduler preemption as parser work. Exhaustion records the stage and callback-work limit in the file diagnostic, marks the syntax parse as failed, and preserves the existing text-chunk fallback.

Compiled tag queries are immutable process-scoped parser artifacts. The parser caches at most 64 queries by static language id, language-factory identity, and query identity; a failed compilation is not inserted. Cache misses compile outside the global cache lock, then acquire the lock again and double-check before bounded insertion. A grammar or query-construction panic therefore remains isolated to that file instead of poisoning unrelated languages; a previously poisoned guard is recovered only around the lookup and bounded insertion, where no grammar callback or query compilation runs. Each file still creates its own `QueryCursor`, callback budget, capture collection, and diagnostic context, so cache reuse neither shares mutable traversal state nor weakens cancellation. The explicit cap remains above the statically registered grammar surface and prevents tests or future registration mistakes from growing parser memory without bound.

Mutable Tree-sitter `Parser` instances may be reused only inside the current OS parser worker thread. They are isolated by static language id and language-factory identity, with at most 64 instances per thread; a new identity after that cap uses an uncached one-shot instance. Every parse calls `Parser::reset` first, including a fresh instance and reuse after success, callback cancellation, or error, so Tree-sitter cannot resume the suspended state of a previous document. The instance is borrowed exclusively for one parse and is never shared across threads. Reuse does not change per-file work quanta, parse status, facts, batch/checkpoint behavior, or path order. It is expected to remove repeated `Parser::new`/`set_language` fixed cost when one worker processes several files, but end-to-end wall time still requires release-binary performance evaluation and cannot be inferred from owner tests.

Full-index batches are bounded simultaneously by file count, byte count, and write-row count. Large-repository cold-index throughput may improve through larger bounded batches, parser-worker parallelism, removal of redundant SQLite probes on empty scopes, prepared-statement reuse, indexed FTS metadata cleanup, or phase-level finalization checkpoints, but it must not skip FTS/search-document writes, edge finalization, checkpoints, freshness checks, or degraded/status reporting. Any register-to-index performance optimization must leave a regression budget or guardrail for `index_ms`, `register_index_ms`, and post-finalization ref queryability in self-iteration `fast` or `--categories performance`.

The batch-persistence owner writes the 16-column `code_repository_references` base facts with at most 1,024 input-ordered rows per multi-values statement: at most 16,384 bind parameters, within the bundled SQLite 32,766-variable ceiling. The effective row group shrinks further when a connection exposes a lower variable limit and rejects a limit smaller than one row; SQLite's maximum host-parameter index is inclusive. Parameters borrow the existing record fields through `ToSql`; persistence does not clone each reference string. The fixed full-group SQL is initialized once and uses the connection statement cache, while the single tail shape is prepared separately. Every group remains inside the existing fact transaction after durable staging and before checkpoint, staging-state, and fence validation commit. Failure in any group rolls back the file facts, all preceding reference groups, and intermediate search documents together, while the already durable `staged` manifest remains replayable. Active-scope `SearchDocumentInserter` input retains the original reference order. This batching does not change any other fact owner or the reference-search finalizer.

The same owner writes the 17-column `code_repository_symbols` base facts in input-ordered multi-values groups of at most 1,024 rows and 17,408 bind parameters, below the bundled SQLite ceiling. The runtime variable limit clamps the group size and may equal the 17 binds required by one row; a smaller limit fails closed. Bind parameters borrow existing symbol record fields; only optional role JSON is materialized once for the current bounded group and then borrowed by that statement. The fixed full-group SQL is initialized once and uses the connection statement cache, while the single bounded tail shape is prepared separately. Symbol search documents retain their previous content and input order through the existing `SearchDocumentInserter`. All fact groups and search documents stay inside the caller-owned transaction, fence, and checkpoint boundary, so a group error or caller rollback removes them together. This batching does not alter reference persistence or finalization.

`SearchDocumentInserter` applies the same bounded statement-reuse policy to its six-column FTS projection. A full flush is clamped by the runtime SQLite variable limit and contains at most 1,024 input-ordered documents and 6,144 binds; the default full-shape SQL text is initialized once process-wide and prepared through the connection cache, while a lower runtime full shape is also connection-cached. A smaller final tail is prepared once for that flush and is deliberately not added to a cache keyed by row count. Fewer than six available variables fails before any write. The fixed maximum-rowid point probe, rowid-interval count, and metadata `INSERT ... SELECT` statements also use the connection cache. The constructor performs no FTS aggregate. Each flush rejects an existing `INT64_MAX` row before insertion, then derives its exclusive interval start from `last_insert_rowid - pending_count`; FTS affected rows, interval rows, and metadata affected rows must all equal the pending count. A high unowned orphan and earlier same-transaction raw writes remain outside the derived interval. Any owner conflict or interval mismatch remains an error inside the caller transaction, so rollback removes both a preceding full flush and its tail. The fast performance gate crosses the 1,024-document boundary with a high orphan, requires exactly two main FTS inserts and two exact point probes, rejects any `max(rowid)` statement, and verifies the equality-constrained FTS virtual-table plan. These checks establish statement-amplification and recovery semantics; release-binary performance evaluation remains the wall-time authority.

A successful source fetch/parse advances the plan's fetch cursor once for the complete bounded group. If the write-row cap makes only part of that group eligible for the current batch, the remaining parsed per-file builds stay in an ordered FIFO and are drained by later batches without another blob read or parse. The FIFO holds at most one fetch group and remains subject to the configured file and byte limits; a single file remains indivisible and may make one batch exceed the row cap, as before. Failures before a group is fully fetched, verified, and parsed do not advance the cursor. Crash recovery may replay uncommitted work from the durable checkpoint, but a successful in-memory plan attempt reads and parses each selected path only once.

On a durable partial-index retry, a newly prepared plan may restore its parser cursor to the committed file prefix and continue at `batch_count + 1`. The worker uses the resource budget persisted with its claimed task, including receipt-shortcut response metadata; only a non-task direct invocation uses the default. Restoration is fail-closed: repository, source scope, resolved commit, tree, filters, total path count, resource budget, resumable state, equal parsed/committed counts, count bounds, batch count, and the exact last path must all match the deterministic plan. Finalizing or completed checkpoints require the entire path prefix, and in-memory parsed overflow must be empty. Read-only validation captures the complete checkpoint or its absence, and `begin` compares that expected token inside the write transaction before any repository/checkpoint mutation. A missing-to-present or changed-token race and ordinary corruption are internal consistency failures, not user `InvalidArgument`; a claimed task immediately enters durable `checkpoint_invariant` dead-letter. Recovery classifies the validated token explicitly: identical resolved commits use `Resume`, while only a `completed` checkpoint with the same repository, content-addressed scope, tree, filters, path count, and resource budget but a different resolved commit may use `ContentEquivalentRestart`. The latter never reuses the old completed cursor: storage compares the exact completed token by CAS, replaces it with an `indexing` checkpoint for the new commit whose file/fact/batch counters are all zero and whose last path is absent, and the application validates that returned checkpoint before parsing. A commit mismatch in indexing or finalizing state, or any other identity, budget, progress, or token mismatch, remains an invariant and follows the same immediate dead-letter path. Batch publication accepts exactly the next index and rejects gaps before staging. An index already covered by checkpoint progress is a fence-validated pure no-op, so conflicting duplicate content cannot alter its manifest, facts, counts, or last path. Once the checkpoint leaves `indexing`, every not-yet-covered batch is rejected before staging, including while a durable reference-search page or query-index repair cursor exists. Checkpoint advancement CASes the exact prior batch count in `indexing`, and manifest publication CASes exactly one `staged` row; a failed transition rolls back all fact and FTS changes while preserving already committed progress. This avoids reparsing an already committed prefix after retry; it does not accelerate the first cold-index attempt or skip any indexing stage.

Every fenced clean incremental snapshot, plus every workspace-free worktree overlay that exceeds direct admission, uses one durable clone protocol. Before the first target write, the task freezes repository/base/target/tree/filter identity, the affected-path set, row/byte limits, exact grouped-reference totals, and the base checkpoint's nonzero `committed_fact_row_count`. A missing checkpoint or zero legacy proof returns typed full-staging fallback with no target progress; a worktree task cannot reinterpret that fallback as a clean snapshot. The proof is the actual cumulative batch fact count, remains zero for partially upgraded legacy sessions, is adjusted by the exact Maven dependency delete/insert delta, and yields the checked clone bound `5F + table_count + 4`; current row and byte quanta may not be smaller than the immutable base's frozen quanta. Each clone transaction advances one metadata-indexed keyset page with progress/checkpoint CAS and fence checks before and after mutation. Affected owners are skipped while still consuming scan budget and advancing the cursor. Search copying enumerates exact metadata owners, admits lengths before fetching payload, validates canonical content after admission, and bulk-writes one contiguous FTS/metadata interval; it never reverse-scans unindexed FTS scope fields. The dirty delta is partitioned deterministically by file ownership under the frozen file, byte, and row budgets and commits at most one replay-safe batch per worker step. Calls are charged to their file batch and rebuilt from call-shaped references during finalization. The terminal control transaction separately budgets affected-owner cascade cleanup, tombstones, fence/checkpoint bookkeeping, and the task-bound multi-batch receipt; it restores `last_path` to the true maximum path of the completed scope before handing the unpublished target to `indexing`. Lease takeover between delta batches resumes from the exact batch count without replaying committed work. The existing full finalizer then runs query-index repair, reference/import/call resolution, Maven effective dependency refresh with `F' = F - D + I`, grouped reference search, call rebuilding, publication, workspace, and software projection; no phase is skipped. A lost response resumes from the checkpoint without recloning or reparsing. Partitioned storage persists the task-owned staged catalog route before the first shard page so that every committed shard checkpoint remains discoverable after a crash.

Writer authority is part of that checkpoint protocol. In `single_sqlite`, an unfenced snapshot, checkpoint, or automatic-workspace cleanup transaction first performs an exact no-op update of the registered repository authority row, thereby obtaining the same-database writer lock before it checks for `queued`, `running`, or `retrying` tasks. An unfinished direct checkpoint blocks a different queued target unless an unfinished task already owns that checkpoint; a task for the same scope may adopt it, after which every unfenced batch-staging transaction, fact transaction, finalization quantum, and workspace-cleanup transaction rechecks authority and fails before writing. Terminal tasks and their retained audit fence rows do not block a new direct snapshot or workspace cleanup. In `partitioned_sqlite`, snapshot, session begin/resume, batch, finalization, and workspace cleanup always require a durable task publication fence. Their unfenced product entries return stable `InvalidInput` before a shard is opened or a catalog route is published, because a pre-read cannot make independent shard and control WAL writes race-free.

The partitioned catalog's schema compatibility probe must remain separate from its migration writer boundary. An existing control database first validates the complete required-column contract for `storage_repository_shards` and `storage_repository_shard_scopes` through a read-only connection with a bounded read busy timeout. A current shape returns without DDL, `ALTER TABLE`, or `BEGIN IMMEDIATE`. Only a missing database or table, or a missing legacy column, enters the existing immediate transaction to create and migrate the schema atomically. Corrupt or unreadable state fails closed rather than masquerading as an empty catalog. A new catalog migration must extend the required-column contract, migration logic, and concurrent regression tests together; this startup optimization does not alter publication fences, task leases, or shard writer authority.

Generated-source detection is a metadata step, not an indexing skip. The detector combines path patterns such as `.pb.go`, `.pulsar.go`, `.generated.ts`, `.auto.ts`, `.min.js`, `.min.css`, repository-root `dist/` and `build/` outputs, and `target/generated/` with bounded header heuristics such as `Code generated by`, `auto-generated`, `@generated`, and swagger/OpenAPI generator comments. Large text files without a path or header signal remain ordinary source metadata and are handled by the separate large-file degradation policy. Generated files still produce file, symbol, edge, chunk, FTS, and index facts; file rows carry `is_generated`, summaries and reports split handwritten versus generated symbols, representative query seeds ignore generated symbols, and query requests may set `exclude_generated` to remove generated files from structured retrieval and bounded source fallback.

Query-time source fallback follows the same blocking-worker boundary as Git blob reads. The product path uses an internal fixed-string scanner over a temporary tree of bounded indexed blobs, applies path/language/scope filters before search, and returns degraded reasons on candidate-path, candidate-file, or materialized-byte budget issues instead of turning a query hot path into a full repository scan. Developer or agent source inspection can use `rg` or `grep -RIn --exclude-dir=.git --exclude-dir=target ...`, but those commands must stay outside product runtime indexing and query loops.

## 7. Degradation Strategy

Unrecoverable parse errors, grammar panics, capture mismatches, and unsupported languages produce parse-status diagnostics and fall back to text chunks. C/C++ files with error nodes limited to macro expansion, bounded preprocessor directives, or decorator-like export macros may be recorded as parsed when symbol, reference, or import extraction succeeds. Degradation appears in repo status, health, and context pack metadata. Missing external dependency source remains unresolved edge metadata rather than `degraded_reason`. Query-time exact-text source fallback candidate-path or budget degradation appears in code query response metadata, not index state. Manual `rg`/`grep` fallback for agent inspection is documented operational behavior and must not be reported as product index health.

## 8. Acceptance Criteria

- Large repository indexing reports progress and does not replace the previous fresh scope early.
- Incremental updates process changed and affected files; they do not disguise full scans as incremental work.
- Commit advances survive missed watcher hints and restarts through bounded reconciliation and durable task replay.
- Read-only product and harness Git inspection disables optional index locking without weakening durable writer or publication fencing.
- Long commit streams retain recovery bases and repository-set pins without unbounded scope or finished-task history growth.
- Valid syntax does not degrade merely because parser workers are descheduled; parser and tag-query work remains bounded by deterministic callback quanta.
- Compiled tag queries are reused only as immutable language artifacts; per-file cursors and work budgets remain independent, and invalid queries are not cached.
- Mutable parsers are reused only within one thread under a static-language cap and reset before every parse; a cancelled instance must safely parse the next independent document.
- Adjacent bounded documentation blocks populate only the next symbol owner's documentation; C/C++ declaration anchors do not expand symbol ranges, Rust inner blocks do not bind the next symbol, and ordinary or oversized blocks do not become symbol facts.
- Row-budget overflow preserves file order and indivisible single-file facts without rereading or reparsing the same fetched path during a successful plan attempt.
- Durable partial retries resume only from an identity- and prefix-validated checkpoint; invalid or uncommitted progress is never skipped, and first-attempt cold-index cost is unchanged.
- Reopening a current partitioned catalog for CLI/read-only work performs only a bounded read-only required-column check and takes no writer lock; only missing tables or legacy columns enter immediate migration.
- Files that fail parsing remain retrievable through text search.
- Indexing traces explain time spent in candidate narrowing, parsing, writing, and refresh phases.

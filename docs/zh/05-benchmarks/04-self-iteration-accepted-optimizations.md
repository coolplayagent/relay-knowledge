## 候选优化说明：cold-build-safe-bm25-quality-gate

- 根因与证据：多次干净构建或 incremental cache 失效的 evaluation 都在旧 `bm25_hierarchy_suite` 120 秒上限处退出，当时 Cargo 仍在编译或链接，尚未启动任何测试；精确 lib test target 已构建后，50 条测试约 9 秒完成。把冷编译计入 suite 的 30 秒指标还会让算法观测描述构建状态，而不是 BM25 行为。
- 执行边界：所有非 `smoke` profile 先在独立 `bm25_hierarchy_build` stage 执行 `cargo test --lib --all-features --no-run`，使用现有 root Rust gate 的 1,200 秒上界且不设指标预算；该 stage 成功并释放 Cargo build lock 后，下一独立 `bm25_hierarchy_suite` stage 继续使用原有 120 秒执行超时和 30 秒 non-key whole-suite 诊断预算。
- 不变量与风险：具名 test filter、all-features、50 条确定性断言、`BM25_WORK` 与诊断预算均不改变；harness 不做机会式预热、不跳测试、不虚抬 suite budget，也不无限等待。无法在 1,200 秒内编译精确 target 的环境仍会在 preparation 失败；suite 超过 30 秒继续进入诊断/评分，但不会仅因此形成硬 gate 失败。

## 子进程退出事件驱动的命令计时

- 根因与实现：evaluator 过去先调用 `try_wait`，子进程尚未退出时固定休眠 20 ms；短 CLI 查询因此累积固定 polling quantum，延迟观测呈阶梯状。命令完成现在等待操作系统 child-exit 通知，并以“剩余命令超时”和“下一次 15 秒进度心跳”中较早者为等待上界。
- 不变量：超时路径仍会 kill 并 reap 子进程，stdout/stderr reader 与可选 stdin writer 仍在返回结果前收敛，进度日志频率不变；不放宽任何查询、fixture 或 acceptance budget。
- 回归：定向 command test 连续运行 16 个两毫秒子进程，要求报告耗时合计低于 240 ms。该阈值为 CI 调度保留了较宽余量，但旧实现每个子进程至少累积一次 20 ms polling floor，因而会失败。

## 候选优化说明：deterministic-tree-sitter-callback-work-budget

- 根因与证据：`manual-evaluate-1786615931856490793-0-2366669` 的 exhaustive quality gate 在 workload 前运行产品全量测试，结果为 3,237 passed、1 failed、1 ignored；唯一失败是 28,701-byte 的合法深层 JavaScript 回归 `deep_syntax_trees_are_walked_without_recursive_parser_helpers` 被记录为 `Failed`。旧算法仅按字节为 parser 与 tag query 分别分配 129 ms 的 `Instant` wall-clock deadline；同一 test binary 隔离精确重跑约 0.22 秒通过，而把 16 个相同实例绑定到同一 CPU 并发时 16/16 都在约 2.6 秒内以相同 `Failed` 复现，证明调度等待被误计为 syntax work。该 report 的 cases/repositories 均为 0，本记录不把 quality-gate 失败轮描述为 exhaustive case 验收。
- 算法与边界：parser 与 tag-query 原生 progress callback 统一改为确定性的 work-quantum counter；每次 callback 消耗一个 quantum，每阶段基线 4,096，按每 24 source bytes 增加一个，硬上限 32,768。锁定的 Tree-sitter 0.26.9 每 100 个内部 parser/query operation 检查一次 callback；对深层回归的调试计数分别为 430/450 次，因此新基线保留明显余量，同时不受 CPU 抢占时间影响。零预算在第一次 callback 检查时取消，耗尽诊断报告 stage 与 callback-work quanta，不再报告毫秒。
- 不变量与验证范围：C/C++ 顶层 initializer-fragment 预检、parser panic fallback、file status、完整 text chunk、FTS、dependency、feature flag、route、task lease/checkpoint、freshness、ranking 与 self-iteration case 阈值均不改变。Owner unit tests固定字节扩展、最大值、零预算取消与注入 counter 的确定性耗尽；保留原 2,048 层语法树端到端回归。当前只完成源码级、格式与文档检查，必须在后续产品测试和完整 self-iteration 执行通过后才能声称全量验收。

## 候选优化说明：durable-staged-reference-search-pages

- 算法与边界：未发布的 fenced full scope 以 grouped-v2 cleanup/discover/build page 替换逐 occurrence reference FTS document。Discovery 为每个精确 `(name, kind, path, target_hint)` identity 保存一个可检索 owner 与 occurrence count；Kube retained evidence 为 486,702 groups / 2,879,261 occurrences，即 reference FTS document 减少 5.92 倍。每页预留 progress mutation，并受 `min((max_rows_per_batch - 1) / 3, 32768)`、配置 byte budget 与 16 MiB hard cap 共同限制。查询 MATCH 先选受界 group，再通过 exact indexed lookup 展开所有 source range；公平 water filling 防止 hot group 饿死其他 group，固定 VM-step 上限返回可观察 capacity error，而不是静默丢召回。
- 恢复不变量：规范 checkpoint token 只保存 protocol version、stage 与 completed page ordinal；record/reference/group keyset cursor 和冻结 counts 位于 checkpoint-owned progress table。每页在前后 fence 双验下以 CAS 同事务提交 data、progress 与 token；partitioned shard 两侧还必须证明 catalog exact staged owner。Rollback/reopen 重放同一页；畸形状态、stale fence、owner 漂移、count mismatch、超大行、manifest 缺失或 checked `BASE + 3 * references + 4` hard bound 耗尽全部 fail closed。Legacy v1 state 只有在 leased writer 重新校验 durable budget 并钳制 page limit 后，才能从 v2 page zero 重启。
- 证据与采纳：retained Kubernetes candidate 用 61 个 batch 提交全部 30,353 个文件与 2,879,261 个 references，约 296 秒到达 `finalizing:refresh_dependencies`，并在 360 秒 timeout；后续约 64 秒处于很可能的 reference-search phase，但没有更晚 durable token。该结果只用于 phase attribution。采纳仍要求在不调整预算的隔离 release-binary A/B 中，同时通过精确 FTS `MATCH`、metadata count、task terminal、checkpoint 与 freshness 检查；源码级和单测证据不宣称 wall-time 收益。

## Issue #354：Git commit 驱动 Knowledge Loop

- 架构：手动 `repo update` 与受管理的 checked-out-HEAD reconciliation 现在都会解析并固定不可变 base/head/tree，再进入 durable code-index queue。原生 Git ref notification 只是低延迟 hint；默认五秒的受界 reconciliation 兜底 linked worktree、漏报 event 与重启。稳定 per-ref fingerprint 合并重复 hint，已有 attempt-scoped lease 保持每仓库一个 active writer。
- 资源与存储 guardrail：delta 最多 512 个 changed path；task admission 每仓库最多 32 个、全局最多 256 个 unfinished task。发布保留 active 与最近两个成功发布时间窗口的并集（通常重叠），再加最近 incremental predecessor、active-worktree clean-base、未完成 task 和 repository-set pin；它原子退役一个旧 scope，再由 durable GC 每个 maintenance transaction 推进一个 scope-GC phase，该 phase 在受影响的 code/search/software 应用表之间合计最多删除 512 个物理行。完成态 task history 限制为每仓库 128 条 success 与 64 条 failure-class row。
- 回归证据：既有 1024-file fast 与 2048-file full performance fixture 继续执行真实 `repo update` 路径并约束 blob read/parse 计数；focused watcher integration test 覆盖无需显式 update 的 commit task 入队、重复 hint 合并与 reconciliation failure diagnostics。本次 orchestration 变更不宣称新的 wall-time 改善、generic Knowledge Graph publication 或 semantic/vector generation parity；这些结论必须有独立实测证据。

## 候选优化说明：self-iteration-subunit-metric-budget-scoring

- 算法/缺陷：`MetricObservation::score` 原先把 lower-is-better 的分母强制提升到 `1.0`，使 `0.166 <= 0.75` 这类已满足上限的 agent `text_fallback_ratio` 只得到 `0.75` 分，并被 `metric_budget_failures` 误报。现在先按 `value <= budget` 判定完整预算适配；仅在真实超预算时计算有界的 `budget / value`，不修改任何 case 或阈值。
- 不变量与风险：负 observation 与非正 budget 的既有容错语义、高于预算指标的连续惩罚、higher-is-better 方向、历史相对评分和 CI 的严格 JSON budget 检查均保持不变。当前 key metric 预算失败同时成为不可被 weighted score、profile best 或 bug-fix priority 绕过的采纳硬拒绝，并在 `reject_reasons` 中列出 name/value/budget；non-key 超预算仍只影响评分与诊断。边界单测固定 `0`、`0.166/0.75` 与 `0.8/0.5`，决策单测固定 key 超预算拒绝、non-key 不硬拒绝和 key 预算内可继续，防止零除、亚单位假失败或超预算误放行回归。
- 预期影响：agent workflow 四个确定性场景的通过型 fallback ratio 不再产生虚假 key metric failure；真实 `value > budget` 仍以小于 `1.0` 的分数进入失败列表并阻止采纳。本变更只修正 harness 评分归一化与 hard-constraint enforcement，不宣称产品检索、索引或 wall-time 改善。

## 候选优化说明：linux-c-fragment-bounded-syntax-recovery

- 算法/架构：2026-08-03 候选最初为 tree-sitter parse 与 tag-query 阶段按文件字节数分配 100–750 ms 的 wall-clock 预算；2026-08-13 已按本文件顶部 `deterministic-tree-sitter-callback-work-budget` 记录替换为确定性的 callback-work quantum 上限。C/C++ 在进入 grammar 前仍以一次线性扫描识别至少 32 行、且全部有效行都是顶层 designated initializer entry 的无声明容器片段，避免 release 优化后 tree-sitter 在两次 progress callback 之间进入超线性错误恢复。C 文件的 definitions 已由一次 manual tree traversal 覆盖，因而跳过重复 tags query；顶层 struct、union 与 enum tag 也由该遍历显式物化，不能因去重漏失。结构化文档的完整源码改用互不重复的 8 KiB/200-line 有界窗口；高密度代码文件在至少 64 个 symbol 且超过每个源码窗口 4 个 symbol 时也改用完整连续窗口，只额外保留可调用 symbol 的 body-linked chunk，全部 symbol facts 和 symbol FTS 仍写入。symbol upsert、候选查找和 reference dedup 改为文件内 hash index，doc-comment 从声明 byte offset 向前扫描，C-family reference 的 type/value/subscript/qualified/initializer 上下文合并为一次祖先遍历。SQLite search content 仍由原 identifier-aware Rust 投影生成，但每 256 条批量写 FTS/metadata，所有 callsite（包括 Maven effective dependency refresh）必须在提交前 `finish()`；WAL auto-checkpoint 按实际 page size 换算并固定为 256 MiB，cache 上限为 256 MiB。冷库单批次任务在事实写入前建立查询索引，多批次任务在可恢复的 `finalizing:build_query_indexes` 阶段批量构建；每个 batch 先写 durable staging manifest，再由唯一 writer 在发布事务中原子提交事实、FTS、checkpoint 和 `published` 状态；manifest 不提供绕过 freshness 的查询路径。metadata identity 唯一约束、事实主键和 FTS 写入仍在每批事务内生效。512-file parser batch 的相同有界 worker 数改用 atomic next-index 动态领取；parser 与唯一 writer 之间使用容量 2 的 bounded channel。所有决策都不读取仓库、路径、符号或 case id。

## 2026-08-31 已采纳：持久 worktree delta 分批与固定 overlay 查询

- 根因：当 worktree overlay 的完整 base clone 与 dirty mutation 超过一个 SQLite writer quantum 时，storage 返回 `DurableStagingRequired`，而 application fallback 有意只允许 clean incremental mode。既有 durable clone 虽可按 page 复制 immutable base，但 terminal delta 仍是单事务。另一个独立缺陷是 `repo context --ref worktree` 首次查询固定 synthetic overlay identity 后，后续内部查询又错误地把该 identity 送入 Git ref resolution。
- 算法与所有权：worktree 保留 direct-first。遇到类型化超预算准入时，同一 task、attempt-scoped fence、重绑定的 synthetic scope 与冻结 budget 先 clone clean base，再由 `durable_delta` 按 file ownership 确定性划分 dirty fact。每个 worker step 最多提交一个 replay-safe batch；call 计入 owner 的 row budget，并在 finalization 从 call-shaped reference 重建。Terminal transaction 共同准入 affected-owner cleanup、tombstone、固定 control row 与 task-bound 多批 receipt，从完整 target 恢复 `last_path`，再把未发布 scope 交给既有 full finalizer。已解析的 `worktree:<base>:<hash>` selector 现在被识别为 immutable identity，nested query 不再进入 Git ref parsing。
- 不变量：没有增大 queue、file、byte、row、retry 或 lease 上限。Base 缺失/不兼容、orphan fact、snapshot digest 改变、stale generation、terminal-control overflow 或 target mismatch 都 fail closed。Worktree task 绝不重新解释为 clean full index；checkpoint replay、每仓库一个 active writer、query-index repair、reference/import/call finalization、publication、workspace/business/software barrier、freshness 与 synthetic identity 均保留。Auto-workspace overlay 保持显式 fail-closed，不会丢失 manifest。Release 与安装行为不变。
- 回归与预期影响：`code_index_task_` fast/performance filter 现在强制形成两个 dirty batch，在两批之间使 lease 过期并重新 claim，并验证精确两批 receipt、44 次 delta write、总计三批 checkpoint 和真实 terminal path。Planner 测试覆盖确定性 ownership、受全局上限约束的单个不可拆文件和 orphan rejection；owner 测试覆盖 terminal quantum、receipt scaling、worktree identity 互斥与 pinned context selection。预期改进是让大型 dirty-worktree 索引在内存和事务工作量受冻结 batch budget 约束的前提下完成，同时不改变小 overlay direct path。剩余成本是每个 step 会重新读取 immutable in-memory delta plan；采纳证据必须继续通过既有 fast 性能预算，不能把源码级 mechanism test 当成 wall-time 结论。
- 采纳证据：第一轮完整 release-product run 因 release build 184,379 ms 超过未调整的 180,000-ms 预算而保留为 rejected。下一轮 `manual-evaluate-1788148749661647156-0-1647985.json` 通过 368/368 gates、132/132 cases、307/307 command contracts 与全部 performance budgets，score `0.9989406099518459`、`adoption_status=would_accept`。Recovery cases 为 24,438/60,000 ms，many-file incremental index 为 784/3,000 ms，software query p95 为 81/250 ms。[带日期验证记录](../06-verification/15-durable-worktree-delta-and-pinned-query-2026-08-31.md)保留 report/patch digest、全量测试与覆盖率、真实仓库回放、skipped suites 和 auto-workspace 边界。

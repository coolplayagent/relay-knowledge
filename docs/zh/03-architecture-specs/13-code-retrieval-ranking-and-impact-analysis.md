## 1. 设计结论

代码检索的先进性来自结构信号与词法/语义信号的融合。单纯 grep 会漏掉调用关系，单纯向量会弱化精确符号，单纯 AST 会缺少自然语言意图；排序必须同时看 symbol、chunk、edge、path、language、query intent 和 freshness，并且任何降权都不能把唯一有效候选变成删除。

## 2. 查询类型

| 类型 | 重点信号 |
| --- | --- |
| definition | exact symbol、identifier segmentation、path/language filter |
| reference | reference edge、target hint、confidence、callsite excerpt |
| caller/callee | call edge、line containment、fan-out budget |
| import/dependency | import edge、module path、resolution state |
| feature-flags | config source、guards_code/read edge、source range、confidence |
| explanation | doc comment、body chunk、semantic/vector similarity |
| impact | changeset diff、reverse dependency、test edge、risk score |
| context | 有界 hybrid/definition/symbol seed，加 reference、call 和 import 展开 |

## 3. Ranking Signals

排序信号包括：BM25、identifier part match、CamelCase/snake_case segmentation、query-to-symbol name normalized overlap、symbol kind prior、path proximity、language filter、graph edge confidence、call direction、caller/callee 查询的非测试源码路径优先级、查询无 test 意图时对 symbol 和 hybrid chunk test/benchmark 路径的小幅降权、查询无 generated-code 意图时对生成代码降权、qualified method 命中的 class-member excerpt context 与 scoped member identity、import surface/re-export file、已具备 declaration-shape evidence 的 header chunk declaration surface priority、type-surface 查询中紧凑 type-returning body 的优先级、chunk quality、freshness、semantic/vector rank 和 rerank explanation。排序在 lowercased lexical scoring 前保留原始 query 大小写，用于 identifier segmentation 和 intent check。当查询本身明确包含 test 或 benchmark 意图时，test/benchmark path 调整不生效；generated-code intent 必须来自通用 generated/codegen/generator 词，或当前 chunk 生成头中已索引的生成来源词，不能枚举具体生成器名；generated-code demotion 可以由 chunk header 或 path segment 的通用 generated/autogenerated/codegen 形态触发；test/benchmark 或 generated chunk 降权必须保留正分，避免仅有候选被过滤掉；component 或 metadata type 这类 type-surface companion 只以 phrase group 形式加入 FTS 召回，且不作为 compound identifier 输入，避免宽泛单词命中稀释精确 API 意图或阻断紧凑标识符召回。ambiguous callee 的 inferred implementation expansion 只作为歧义调用点的辅助上下文；当 direct call-site row 与推断实现同时存在时，直接调用点证据仍应优先。

自然语言 Hybrid query 可以通过声明所属的持久化文档命中 owner declaration。同一份规范化 `symbol.doc_comment` 同时进入 symbol FTS、lexical scoring 与返回 excerpt，因此紧邻 class、interface、带 Java annotation 的声明或 C/C++ declaration/template owner 的概念说明能够召回该 symbol，不需要仓库、路径、符号或 query 特判。Owner anchor 不改变 symbol range 或 signature，Rust inner block 也不作为下一 symbol 的 context。对于至少 5 个有效 query term 的 broad Hybrid，type declaration 只有在 name/signature 命中至少 2 个 term、owner documentation 命中至少 3 个 term，并且二者联合覆盖至少三分之二 query term 时，才获得固定且有界的 high-coverage type-surface bonus；最多检查 12 个去重 term。该 bonus 不删除或降权 Markdown/chunk 结果，结构化类型与文档继续进入同一最终排序窗口。文档仍是辅助证据：exact symbol 与 resolved edge 保留结构优先级；普通 block comment 在 parser 层即被排除，不能成为 owner context。

Broad Hybrid 的 symbol 召回还会在排序前保守桥接词形变化与 agent-noun 差异。当超过 4 个 term 的查询可由 focused planner 选出恰好 3 个、长度至少 6 且仅含 ASCII 字母的高信号 term 时，规划器最多构造 3 个两两组合的 FTS5 prefix group；每个候选至少需要命中两个 prefix。该补充探针不用于非 Hybrid 或 exact-file 查询，并且在截断前只准入具备非空 owner documentation 的持久化 type kind；它在原有 200 到 800 条 primary exact-symbol 窗口之外最多读取 120 行。两个受界集合在常规 lexical/structural scoring 前按 symbol snapshot identity 去重，因此合并后的 symbol 窗口不超过 920 行。Prefix 召回本身不加分，声明仍必须通过既有 type-surface documentation coverage gate 才能上升；Markdown 与 chunk 结果继续使用未改变的检索层。

Typed query 的补全依据是 evidence coverage，而不是“已有任意命中”。Definition source fallback 只接受剥离常见语言修饰符后的真实 declaration shape，并排除 comment/Javadoc 与 constructor-shaped mention。Exact reference 查询的结构化 edge 未填满请求窗口时，可以补充受界 indexed-chunk usage evidence。准入只扫描已经受界的候选 chunk，并使用其持久化 `language_id`：C/C++ declaration、function definition、仅声明的 typedef alias 与逻辑续行的同名 `#define` definition 不算 usage；Python、Ruby、Bash 和配置语言的 `#` comment、SQL line/block comment、JavaScript/TypeScript template 与 regex literal、Rust raw string、quoted literal 和 block comment 都按语言保守遮罩；Rust lifetime apostrophe 仍按 code 处理，不会误开 character literal。chunk 以 block-comment continuation delimiter 或惯用 `*` continuation shape 开始时，必须保持遮罩直到 closing delimiter；本 chunk 内没有 closing delimiter 时，该 continuation 不贡献 evidence。如果同一 chunk 另有真实 code use，仍保留该候选，包括在 C/C++ macro body 中引用另一个 symbol。窗口已满或自然语言 reference 请求不会触发该补全。Caller 排序把已有 test-context 降权同时用于 test path 与生产文件内嵌 test symbol，显式 test 查询则关闭两种调整。这些规则只调整次序，不删除仍然有效的低位证据，也不扩张 FTS candidate window。

Reference candidate 在受界 FTS limit 前排除文档和配置语言，避免 prose 占满候选窗口并挤出代码 usage evidence。Grouped structured reference 先按同文件同 identity 的重复证据排序受界候选，再在不改变 occurrence budget 的前提下公平展开，并在 hydrate 后施加有上限的对数型重复证据加分。大型且已具备 symbol 的源码文件还必须为 symbol byte range 之外的顶层源码保留受界 uncovered window，使 compile-time relationship assertion 等 file-level fact 可检索，而无需放宽每个 symbol chunk。

这条 reference 准入规则必须是仅覆盖明确文档、数据/配置与模块清单表面的受界 denylist，而不是 code-language allowlist。可执行 build DSL 与 template language 仍可提供真实 usage evidence；未知或新注册语言也默认进入候选，再由既有 language-aware usage validator 校验，避免语言注册演进时静默删除代码证据。

对 exact single-name Hybrid type 查询，declaration role 只作为有界 tie-break：同名 concrete class、record、struct 优先于 interface 或 trait；fake、mock、stub 与 benchmark 通用路径仅在查询没有明确相关意图时降权。该 role signal 不改变候选上限，也不能覆盖更强的非 type 词法证据。

Import projection 必须按语言保留 source-like syntax，例如把 Go alias 呈现为 `import alias "module"`；排序则从规范化的 alias-plus-module 表示提取 local binding。Exact import-path row 与受 path 约束的 target-symbol row 在 broad FTS 合并和最终 top-k 排序前最多保留 700 条 edge；该固定 reserve 让字典序靠后的精确 importer 仍可达，同时不会把查询窗口变成无界。Importer-context FTS sampling 使用一次 grouped scan，并且每个 selected path 最多保留最早和最晚两个 matching chunk。这个公平的两行上限避免前序路径耗尽共享窗口；既有 700-path、2,048-chunk、byte 与 SQLite-work 预算保持不变。

Import 排序从 named import、namespace terminal 和 wildcard binding 的保守单数 companion 中提取本地 binding term；存在与查询匹配的更精确本地 binding 时，namespace prefix、无关候选的 terminal 与较短的 CamelCase fragment 不能成为 importer-context term。Target-symbol match 只有在 matched symbol 与 query-local binding term 真正相交时才能授权 context；仅存在 matched-symbol metadata 不能放行无关 terminal。按 `language_id` 遮罩 comment 与 literal 后的同文件 code-identifier usage 是 importer context 的主要信号。Contextual query 显式携带 importer identity 时，只在存在真实同文件 usage 后提供受界 path-overlap 信号；计算前必须剥离已经由 import module、target hint、matched target symbol 或 target-symbol surface 解释的词项，因此只有 target path 或 FQN 的查询不能获得 importer-identity path bonus。匹配的 non-wildcard production import edge 可以获得最高 0.5 的小幅对数型 source-size 调整；wildcard、generated、test、benchmark 与不匹配 edge 不获得该加分。该受界次级信号可区分有实质内容的 importer surface，但不会把文件大小当作首要语义相关性，也不改变任何候选上限。Importer context 先为每一行计算并缓存 query-local term；没有保留 term 的行不占用最多 700 个 selected importer path 的额度。随后对同 scope chunk FTS read model 执行直接的 `cap + 1` probe，最多使用 128 个不同 usage term 和 8 KiB term bytes；每个 path batch 还会在 1,000 条虚拟机操作触发一次、最多 4,096 次 SQLite progress callback 后取消，并在连接继续执行其他 SQL 前移除临时 handler。只有未饱和且未中断的 probe 才在内存分组，每个 path 最多读取 64 个匹配 chunk，全局最多读取 2,048 个匹配 chunk，并且全局 raw matching chunk bytes 最多为 16 MiB。chunk row 逐条累积；一旦下一行越过 byte 上限，就在分组前停止并关闭这组候选的全部 importer-context scoring，不能先对无界窗口排序再应用 probe。可选 path、term、chunk、byte 或 SQLite-work 窗口饱和时，关闭这组候选的 context scoring，而不是只按有序前缀产生偏置。Importer context 只是可选 enrichment：target-symbol 或 chunk/import FTS read model 不可用时关闭对应 enrichment；已经可用的 direct-path 与 identifier import-edge row 仍可参与结果，不能随可选 FTS 层一起失败。

Target-symbol match 通过授权后，同文件 usage sampling 使用 matched symbol identity，而不是枚举每个 importer alias，因此高 fan-out package 不会在观察到 `alias.Type` 等证据前耗尽 term budget。

Target-symbol import expansion 只允许两类显式 `Imports` 查询：单个非限定 identifier，或一个 import path 加恰好一个首字母大写的明确 type identity。混合形式只有在 symbol 的规范化 target hint 以查询 import path 为精确后缀时才准入，因此与 module path 无关的 importer class name 不会改变 expansion 方向。Hybrid 请求、含多个 identity 的歧义形式，以及包含 `.`, `::`, `/` 或 `\` 的 qualified symbol/FQN 必须留在 import-edge、direct-identifier 与 FTS 路径，不能准备无约束 target-symbol expansion SQL。所有规范化 repository path filter 都保持 exact-or-descendant 语义，不能依据 dot 或扩展名猜测 file/directory。每个 filter 编译为 `BINARY` 范围 `path >= ? AND path < ?`，使用 `filter + "0"` 作为 exclusive upper bound，并以 `substr(path, length(?) + 1, 1) IN ('', '/')` 做边界残余判定；这样既保留 `(source_scope, path)` range seek，也不会放入标点前缀 sibling。Import-edge group enrichment 使用受界 row-value `IN (VALUES (?, ?, ?), ...)` key 与持久化 `(source_scope, path, line_start, line_end)` 索引，不再展开 OR predicate。Leading-wildcard identifier scan 属于可选召回层：每 1,000 条 SQLite virtual-machine operation 回调一次，最多 4,096 次后中断；遇到 `SQLITE_INTERRUPT` 时返回空的可选层，始终移除临时 progress handler，再让受界 FTS/direct layer 继续执行。

业界代码搜索实践要求词法、结构和语义分层：Zoekt/Google Code Search 类 trigram candidate 适合 substring/regex 初筛，BM25 适合自然语言和文档 chunk，Tree-sitter capture 适合 symbol/edge，semantic/vector 适合概念性解释查询。排序不能用语义分数覆盖 exact symbol 或 resolved edge，也不能让宽泛 regex 结果绕过 scope、path、language 和 revision filter。

代码仓库查询采用 AST 优先、精确 source fallback 兜底的内部协作。Definition、reference 和 hybrid 查询先访问版本化 tree-sitter 图和 SQLite FTS 读模型；code-index worker 可以同时解析和 finalize 另一个 scope，但查询执行只通过有界 read path 读取已提交 scope，不能消费 worker 的部分索引状态；当请求 ref 正在 full indexing 且新 scope 尚未 finalize 时，`allow-stale` 查询读取上一个已完成 committed scope 并显式标记 stale/degraded，不能等待 writer 或读取部分索引数据；`wait-until-fresh` 才拒绝未完成的目标 scope。当结构化路径存在明确召回缺口时，允许在同一已索引 revision scope 物化候选文件上执行有界内部精确文本检索。Import/dependency 查询先从 import edge 得到依赖集合；若依赖目标有代码地图或代码图 target，则使用结构化依赖证据；当 dependency library 未作为代码图 target 建立索引时，import 查询才可以用 unresolved external dependency target hint 作为 source fallback 词项。外部依赖源码缺失是 unresolved edge coverage metadata，不写入 `degraded_reason`。对于 C/C++ 预处理 include，unresolved 或 ambiguous `edge_target_hint` 必须保存移除 `#include` 前缀、引号或尖括号后的规范化 include specifier；resolved hint 仍保存唯一的 indexed target path，excerpt 则保留原始 source statement。Source fallback 只属于词法层：它可以恢复精确源码行并提高召回，但不能返回 AST 图没有证明的 resolved edge 或 confidence。

Hybrid source-surface refresh 在为既有 structured symbol range 选择代表 excerpt 时必须保留 declaration strength。声明 query identity 的源码行可以替换普通 summary 或 nested mention；但 declaration 一旦成为代表项，后续更长的 field initializer、logger statement、call 或其他嵌套 identity mention 不能仅因长度更长而覆盖它。长度只能在 declaration strength 相同的 surface 之间作为 tie-break。Score 与 retrieval provenance 仍继续合并，不同源码行的 nested mention 也可以保留为独立 lexical hit；因此 broad top-k 能稳定保留 declaration，同时不会删除辅助证据。

面向 agent 和维护者的源码检查遵循独立工具策略：优先使用 `rg` 做本地仓库搜索；如果本机未安装 `rg`，继续使用有界 `grep -RIn --exclude-dir=.git --exclude-dir=target --exclude-dir=node_modules --exclude-dir=dist <pattern> <authorized-root>`。这条人工 grep 路径只用于调查和自迭代 prompt，不能接入产品查询热路径，也不能绕过已索引 scope、freshness 或 authorization。

## 4. 候选窗口

FTS 和 source-fallback candidate window 必须先应用 scope/path/language filter，再进入有界评分。高 fan-out caller/callee 查询需要按 edge score 和 line containment 截断，避免一条调用边被多个无关 chunk 放大。

分层 Hybrid chunk 检索必须区分 probe precision 与最终 recall：structured、focused、lifecycle、compound 和 strict probe 保持 40 到 120 的窄候选窗口；最后的 broad OR-FTS fallback 使用既有的普通 Chunk 有界窗口 300 到 900，合并结果仍在该 broad 上限内去重、评分和截断。Exact-file filter 只有在查询是真正的 single-symbol identity 时才允许 symbol-only 提前返回；多词或 contextual query 必须执行有界 chunk 层。它们的 exact-path source fallback 只能在两个不同的结构化 identity anchor 共同指向不完整 source surface 时使用，不得只重新搜索一个已覆盖 identity。

当 unresolved external import edge 的 import-graph excerpt 已包含 source-like statement，且解析出的 specifier 与 edge target 一致时，该 edge 已提供完整 source evidence。外部 package 源码缺失不是 source-text recall gap，因此这种完整 surface 不再物化 candidate blob，也不运行内部 grep。Relative import、dynamic-import intent、不完整 excerpt，以及完整/不完整混合结果集仍沿用既有受界 fallback 与授权校验。

内部 exact-text source fallback 与 Git 快照读取一样运行在 blocking-worker 边界之后，并受存储侧候选路径上限、候选文件数、命中数和单行长度预算约束。当前实现的兜底预算是最多 256 个候选文件、8 MiB 物化 blob 和单行 4096 字节。它搜索已索引 commit 内容，而不是脏工作树；对非 Git `filesystem:` commit，兜底在读取文件前必须验证 live source tree 仍解析到同一个 scoped synthetic commit，若不匹配则报告兜底降级，不能读取另一个 live 快照的当前字节来掩盖 stale。显式已存储 `filesystem:` ref 可以按身份进入 storage lookup，但 source-byte materialization 仍必须受 live-tree 校验保护。当兜底需要宽 scope 路径时，存储层必须先用 query、path filter 和 language filter 在已索引 FTS read model 中收敛候选文件，只有 query 没有索引候选时才退回有界 scope 枚举。如果结构化代码搜索过程中 FTS read model 临时不可用，结构化词法层在重试后可以返回空候选集，让有界 source-text fallback 继续执行，而不是让整个查询失败；候选路径查询还可以使用 indexed path 和 chunk content 保持 query-aware，无法产生 query-aware 候选时暴露降级而不是扫描按字典序截断的文件前缀。这样排序靠后的相关文件仍可被召回，但不会扩大全局候选文件预算。候选 blob 应优先通过 `git cat-file --batch-check` 做 size preflight，并在 byte budget 内通过 `git cat-file --batch` 成批读取，batch 不可用或包含异常对象时保留逐路径 skip 回退。物化搜索树必须包含已索引的 dot-path 候选；内部 scanner 按固定字符串逐行匹配、跳过包含 NUL byte 的二进制 blob，并在非 definition 查询命中超长行时返回命中附近的有界 excerpt。超大 blob 超出物化预算时只跳过当前候选，不阻断后续仍能装入预算的小文件；definition 兜底先按定义行过滤，再执行返回命中数上限；import 兜底可以给本地相对导入查询中的可执行 `import(...)` 动态导入源码行 source-line shape bonus，使运行时导入使用可以排在规范化静态 import 摘要之前，但不能提升纯注释命中。候选路径不可用、候选文件预算或物化预算耗尽时，查询仍保持有效，并通过 degraded reason 暴露诊断，不能绕过 freshness 或授权边界。产品运行时不依赖 `rg` 或递归 shell out 到 `grep`；`rg`/`grep -RIn` 只作为 agent/维护者调查 workspace 时的有界搜索工具写入文档。

Repository-set 查询必须把每个 member 视为独立的有界 retrieval workflow：单仓 SQLite 读模型访问仍通过 storage 边界串行化，member 级 structured search、dependency-symbol fallback 与 source-text fallback 可以在小并发上限内异步推进。并发上限是背压合同的一部分，不能随 member 数量无限扩张；Hybrid member 的 source-text fallback 用最终 set limit 判断结构化窗口是否不足，不能因为 per-member fanout 深度更大就自动填充 grep 结果；单仓 Hybrid planner 可以在 symbol+chunk 已用非 text-fallback chunk 充分覆盖多项查询序列时跳过 reference/call/import graph expansion，但必须保留 Definition/References/Imports/Callers/Callees 的显式查询语义；overlay evidence、bridge bonus、dedupe、diversity 和 final top-k 仍在所有 member outcome 汇合后统一执行，以避免跨仓排序语义随调度顺序变化。正 priority member 只有在 member/hit fresh 且存在支持 priority 的 resolved 或 ambiguous overlay evidence 时，才可以因结果 path 或 excerpt 命中 query 的非泛化 domain term 获得有界 domain-affinity bonus；zero-priority member 不获得该提升，且该 bonus 不能绕过 freshness、member fanout、fallback 或最终 top-k 预算。

Codegraph context packing 不引入独立排序模型。Entry points 保留 hybrid、definition 和 symbol 查询的排序；扩展命中继承 references、callers、callees 和 imports 各自查询类型的排序。Packer 只执行去重、多样性和字节预算截断，并记录每项进入 pack 时对应的 retrieval layer 与 score。

候选窗口应输出可观测字段：每个 layer 的 pre-filter count、post-filter count、score count、truncation reason 和耗时。影响分析、caller/callee 和 import 查询必须随 changed path、seed symbol、module hint 和 edge confidence 扩展，而不是随完整 scope table size 扩展。

Feature flag 查询默认枚举 indexed scope 内的结构化开关事实；带 `--query` 时只过滤已索引 flag name、source key、path 和 excerpt。排序优先级为 guarded-code 关系、配置定义、普通读取和 SDK evaluation，再结合 query 命中和路径/language 过滤。该查询不能用 query-time grep 枚举未知开关，不能同步 provider 控制面状态，也不能通过硬编码产品、仓库或 benchmark 中的已知开关名提升排名。

宽 scope 的 source fallback 在最终评分前为每个受界候选路径最多保留两个命中（候选池硬上限 512），scanner 先跨路径分配候选，再复用同一路径；同一路径内优先保留代码形态的 reference，再保留 comment 与仅 import 的 mention，最终 reference 评分还会把明确的文档/配置语言和纯 comment evidence 降到代码 usage 之后。显式窄路径集合可以在同一硬上限内使用请求的结果上限。这样单个命中密集文件或文档 surface 都不能独占召回池，同时最终 top-k 及全部 byte/file 上限保持不变。

## 5. 影响分析

Impact analysis 从 changeset scope 出发：

```text
changed files
  -> changed symbols
  -> direct references/calls/imports
  -> reverse dependency expansion
  -> tests/docs/config affected candidates
  -> risk groups with evidence
```

影响分析输出不是绝对结论，而是带 evidence、path、edge confidence 和 budget truncation 的风险分组。非 Git impact path 枚举必须使用与 indexed scope 相同的 effective filesystem filters，包括显式 opt in 的宽泛目录，不能用默认非 Git policy 重新扫描。

## 6. 验收标准

- 查询 `foo_bar` 能命中 `fooBar`、`FooBar` 和多段符号名，但 typed edge 查询不被过度放宽。
- caller/callee 结果定位到包含调用行的 chunk。
- source fallback 兜底命中必须标记 lexical/text-fallback provenance，且不能携带 resolved edge confidence；hybrid source fallback 只能补齐结果窗口，不能排在已有结构化命中之前。
- unresolved external dependency coverage 通过 edge resolution metadata 表达，除非有界兜底自身失败，否则不设置 `degraded_reason`。
- 自迭代和维护者 prompt 必须同时覆盖产品内部 source fallback 行为与人工 `rg`/`grep -RIn` 检查 fallback，避免本机缺少 ripgrep 时中断源码分析。
- impact 输出说明哪些结果来自 diff、调用、引用、导入或测试信号。
- benchmark 不通过枚举已知 query、path 或 symbol 特例提升排名；优化必须来自通用排序信号、索引结构或候选下推。

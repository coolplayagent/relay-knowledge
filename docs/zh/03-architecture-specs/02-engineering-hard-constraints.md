## 1. 设计结论

本章是第三卷的硬合同。任何实现、文档、测试、发布或运维变更都必须满足这些约束；它们不是建议，也不能用“后续补齐”绕过。

先进性不是靠复杂组件堆叠，而是靠边界清晰、依赖无环、状态可恢复、资源有界和行为可验证。

## 2. 架构硬约束

- **异步优先**：I/O、图数据库访问、索引刷新、摄取和服务编排必须暴露 async API。
- **热路径不阻塞**：CPU 重、磁盘重或阻塞工作必须放入显式 worker、维护任务或 blocking boundary。
- **有界资源**：事件 pipeline、网络入口、索引刷新和后台任务必须有 queue depth、budget、timeout、cancellation、backpressure 和 overload behavior。
- **事实与读模型分离**：GraphStore 是事实真源；BM25、semantic、vector、summary、community 和 code index 都是派生读模型。
- **无环依赖**：crate、module、trait、service、adapter 和 config object 之间不得形成循环依赖。
- **代码源目录权威清晰**：Git 管理的代码仓库必须以 tracked tree 作为索引目录权威，不能只因 `build/`、`dist/`、`vendor/` 或 `third_party/` 等目录名跳过已跟踪源码；非 Git source directory 默认必须使用源码/配置/文档白名单扫描，避免把构建产物、缓存和依赖副本纳入索引，宽泛目录只能通过显式 path opt in 进入对应目录。非 Git `src` 这类窄 path 不能顺带 opt in 兄弟级宽泛目录，也不能在选择前遍历无关 filtered sibling；未带 path filter 的非 Git 扫描不能遍历不会贡献默认白名单内容的目录；`--path .` 是宽泛目录 whole-root opt in。真实 Git metadata 上的探测失败不能静默回退为 filesystem indexing，source fallback 不能为 stale scoped `filesystem:` commit 读取 live 文件。非 Git synthetic hash 必须来自 source-layout discovery 后的有效 indexed scope，非 Git pre-scope hash 不能读取 file preset 排除的文件，除非显式 path filter opt in 到该文件；非 Git ref resolution、source fallback 校验和 impact path collection 必须包含有效 path 和 language filters，排队 synthetic ref、同步 full-snapshot read、full-index batch 以及 delta 读取 live bytes 前都必须校验，非 Git 文件 byte/hash/metadata materialization 必须拒绝最终路径和祖先目录 symlink 替换，显式已存储 `filesystem:` ref 及其 source fallback 校验、impact collection、impact partition 和 deleted-symbol extraction 必须先于动态 source-kind 或 Git 探测走 filesystem scope 身份解析，repository-set 的更窄 filter 成员和 freshness check 必须复用兼容的更宽非 Git scope，显式非 Git incremental `base_ref` 必须加载该已存储 base scope，增量删除必须覆盖上一版 discovered root，active non-Git task matching 必须用 task 的有效 filters 比较更窄 stale read，非 Git impact path 在 scoped base/head ref 相同时必须返回空 changeset，Git ref normalization 和 fresh full-index check 都不能执行 full tree walk。
- **高性能必须泛化**：优化必须来自数据结构、ranking signal、索引策略、query planning、batching、并发边界或存储布局，不能枚举已知 query、path、symbol 或 fixture。

无环依赖由 Rust syntax architecture gate 执行：门禁用 AST 展开 grouped import 与 qualified `crate::` path，生成顶层 module graph，对全部节点运行 SCC 检测，并按 layer policy 报告引用文件和行号。`bootstrap -> interfaces -> application` 是唯一允许的 CLI 生产方向，`interfaces` 不得反向调用 `bootstrap`；1.x 的 `interfaces::cli::{run,run_process}` 只作为 deprecated 兼容入口保留，并使用无反向依赖的实现。`api` 不得依赖 `storage`，公开 cursor、index refresh、file hit/summary 和 health diagnostics contract 归 `domain` 所有，旧 `storage::*` 路径只通过兼容 re-export 保持。Architecture job 必须上传 JSON 与 DOT graph artifact；字符串 token 搜索和 grouped-import 不可见的 substring baseline 不能再作为依赖门禁。

Application 基础设施迁移预算按“文件、目标 module、AST 引用数”精确冻结，只能递减，不能增加。SQLite store 创建、catalog topology probe 与 lazy open 通过 bootstrap 注入的 async `KnowledgeStoreFactory` 完成；embedding 与 external worker outbound HTTP 通过 `ports` 的 async contract 完成，具体 reqwest/QoS adapter 位于外层。每个 remote embedding request 必须先取得共享 QoS 准入；不接收 QoS runtime 的 deprecated provider constructor 可以保留本地 echo 行为，但 remote provider 必须 fail closed，且绝不能调用 `send`。Application 不得构造 SQLite、HTTP client 或直接调用 network transport。大规模目录精确枚举不再承担架构证明；layout gate 验证 foundational owner、非空生产文件和禁止 production `#[path]` redirect，全仓门禁则对每个 tracked UTF-8 文本源码、测试、文档、脚本、配置和 workflow 执行 1000 行上限。二进制文件不适用文本行数指标，`Cargo.lock` 是唯一 tracked-text 例外；依赖方向由 syntax graph 证明。

## 3. 基础模块所有权

| 模块 | 唯一职责 | 禁止事项 |
| --- | --- | --- |
| `env` | 环境变量读取、解析、校验、脱敏诊断 | 其他模块直接读取环境变量 |
| `paths` | 平台路径、运行时目录、数据/日志/缓存目录 | 其他模块拼接运行时路径 |
| `net` | socket、HTTP client/server、listener、网络 loop | 其他模块创建网络能力 |
| `net::http` | 基于成熟 async runtime/library 的 HTTP | blocking socket、thread-per-connection、busy polling |
| `net::qos` | 准入控制、租户/来源限额、优先级、预算、overload metric | 绕过 QoS 消耗无界资源 |

稳定 identity 与 wall-clock primitive 同样只有一个底层 owner。`identity` 独占持久 FNV-1a 算法及其 incremental hasher；domain、application、watcher、paths 和 storage owner 只能消费该合同，不能复制常量。`clock` 独占窄 `Clock` contract、`SystemClock`、Unix-millisecond 转换及 pre-epoch/overflow 错误；调用方可以在自己的边界映射错误，但不能自行读取 `SystemTime::now()`。两者都不得演变为通用 `utils` 桶。

具名的平台进程输入同样必须经过该边界。进程 bootstrap 期间由 `env::windows_system_root_from_process` 捕获 Windows `SystemRoot`，bootstrap 只捕获一次 `std::env::current_exe`，`paths::windows_tasklist_command` 解析 Windows process-list 可执行文件，`RuntimeConfiguration::process` 再把两者注入服务恢复及生命周期 plan/execution。Binary preflight、copy、upgrade、rollback 与 checkpoint recovery 必须复用同一个已捕获 executable path；应用工作流在恢复 worker 或调用 service manager 时既不得直接调用 `std::env`/`current_exe`，也不得自行拼接平台可执行文件路径。

HTTP 基础边界必须完整收敛在 `net/http/`：`mod.rs` 维护已校验配置、server runtime、request context、timeout、cancellation 和 graceful shutdown；`outbound.rs` 独占 reqwest client 构造、有界 raw JSON transport、URL 解析、响应校验与 outbound QoS 计费；`qos_admission.rs` 隔离 inbound request admission；`qos_client.rs` 独占 reqwest permit/body 生命周期与 timeout 计费。`outbound_tests.rs`、`qos_client_tests.rs` 分别直接挂载到 owner，`mod_tests.rs` 只保留配置、server 与跨 client/server request-context integration contract。`net/` 父目录不得重新出现 `http.rs` 或 `http_tests.rs`。

QoS 基础边界必须完整收敛在 `net/qos/`：`mod.rs` 独占已校验 resource budget、admission decision、runtime counter 与 drop 自动释放的 permit，`mod_tests.rs` 是其直接 white-box contract。`net::http::qos_client` 独占 remote embedding transport 准入，并让 permit 与 cancellation guard 持续存活至 response body 被消费或 drop；拒绝必须发生在 socket 工作前，timeout 必须可观测，被取消的 send/body 必须递增 cancellation metric 并释放 permit。任何 remote embedding 路径都不得在该 owner 外直接调用 reqwest `send`。`net/` 父目录只能包含 facade 配对文件与具名 `http/`、`qos/` 子域，不得恢复平铺 `qos.rs` 或 `qos_tests.rs` sibling。

### 3.1 环境变量边界

`env` 内部按数据流保持单向依赖：`variables` 只拥有受支持的变量名，`error` 和 `overrides` 分别拥有稳定错误模型与 typed override 数据，`value_parser` 负责从已归一化 snapshot 提取并校验 path/string/bool/positive integer，`platform` 负责平台检测、大小写归一化、平台目录输入及 `SystemRoot` 进程读取，`config` 才能捕获完整进程环境并装配公开配置。`mod.rs` 仅维持原有 `env::*` facade，不得重新承载解析规则。对应 UT 必须分别放在同级 `config_tests`、`platform_tests` 和 `value_parser_tests` 文件，并由匹配的实现 owner 而非 facade 显式挂载，使配置装配、平台规则和标量校验可以独立定位失败。

依赖方向固定为 `error`/`variables` → `value_parser` → `platform`，`overrides` 只组合这些 typed platform 数据，`config` 作为最外层依赖其余模块；不得让 error、override 或 variable catalog 反向依赖配置装配，也不得把 `std::env` 读取扩散到 `env` 目录外。

### 3.2 代码仓库应用工作流

Knowledge Map 采用窄物理 owner：`map/query.rs` 独占 show、filtered show、route 与读模型加载，`map/validation.rs` 独占 map contract 和 business-glossary route 校验，`map/mod.rs` 只保留稳定 `KnowledgeMapService` facade、命令工作流、迁移与原子发布协调。外部 facade 和 artifact 格式保持兼容；读、校验或发布职责不得重新聚合到单个接近上限的 owner。

进程环境只允许在 bootstrap composition root 捕获一次。CLI update notice 必须由 `bootstrap::cli` 先判定 notice policy，再把 `RuntimeConfiguration` 注入 interface；interface 不得为读取环境反向依赖 bootstrap，application 与 `net` runtime 也不得提供 live-process refresh 捷径。确定性测试通过 `EnvironmentConfig`、`ProcessRuntimeConfig` 和 typed runtime snapshot 注入配置。

`application::code_repository` 按用例划分内部所有权：`repository/` 负责注册、删除、状态、报告、staleness 标注和 worktree overlay 校验，`repository_graph/` 负责 fresh indexed-snapshot 准入、有界 document 加载与 OKF neighborhood response 装配，`indexing/` 负责索引执行、持久任务租约、checkpoint、scope preview 和 worker 管理，`update/` 负责可选 base/head 解析与持久 commit-to-commit update submission，`query/` 负责版本化 scope 检索与特性开关，`impact/` 负责 diff 影响分析，`context/` 负责有界 graph-aware context pack，`freshness/` 负责结果/index 新鲜度协调，`scope/` 负责 indexed-ref 与 filter compatibility，`software_projection/` 负责全域软件读取，`source_surface/` 负责完整声明校验。`indexing/` 内由 `start` 独占准入与 durable-task seed，`worker` 独占 claim/lease/retry/terminal transition，`session` 独占带 checkpoint 的有界 parse/write execution，`preview` 独占 read-only scope preview；有状态 `workflow` 再拆成 `recovery` 负责 fence/checkpoint reconcile，`snapshot` 负责 blocking/lease 边界后的 full/incremental snapshot generation，`publication` 负责 durable clone/finalization/fallback publication，`projection` 负责 workspace 及 business/software 派生投影与终态 status。依赖从 workflow coordinator 单向流入这些阶段；各阶段必须保留每仓库最多一个 active writer、attempt-scoped lease、checkpoint replay/idempotency、有界 retry/backoff 与 publication-fence 校验。物理 `blocking/`、`clock/`、`errors/`、`worktree_ref/` primitive 分别隔离自己的边界策略，不混入含义不清的 support 桶；`blocking` 通过四个全局并发 permit、有界准入等待、响应等待 deadline 与 `spawn_blocking` 隔离 CPU-heavy indexed-document projection，OKF YAML/graph 工作不得在 async runtime worker 上执行。响应 deadline 只停止等待，不能强制取消正在运行的 blocking closure；该 worker 可以在后台完成并在返回前继续持有 permit，因此 projection 活跃并发总数仍有界为四。context、repository graph、scope 与 update 直接挂载 `mod_tests.rs`。根目录只能保留声明 facade 与具名子域，不得恢复平铺实现或 owner 专用测试。这些模块通过同一个 `RelayKnowledgeService` 暴露稳定 API，并只向内依赖 `domain`、`code` 和 `storage` 合同；不得互相复制工作流或反向依赖 CLI、Web、MCP 等 adapter。

在 `application::code_repository::repository_set` 内，物理 `membership/` 独占 create/add/member-scope API，`status/` 独占 required-status lookup、fact-version replacement、moving-ref 检查和 set freshness 聚合，`member_freshness/` 独占 fact-version scope reconciliation，`errors/` 独占 set 专用存储错误映射，`lifecycle/` 独占删除协调，`refresh/` 独占同步 overlay rebuild 及持久化 queue、lease、completion、retry、dead-letter 状态转换；有 UT contract 的聚焦 owner 必须直接挂载 `mod_tests.rs`。物理 `query/` 域独占 set retrieval：`mod.rs` 独占纯 overlay evidence、scoring、deduplication、diversification 与 truncation，`workflow` 独占并发 member retrieval、dependency-symbol fallback、延迟有界 source fallback 和 wait-until-fresh 准入，`plan` 独占有界 dependency API query planning 与 hit merge，`domain_affinity`、`identity_coverage` 独占各自 ranking signal。每个行为 owner 都直接挂载配对同级 UT，`test_support` 只为 ranking owner 构造测试数据。依赖必须保持 `workflow -> query root/plan` 及父级 freshness/error owner、`query root -> domain_affinity/identity_coverage`、`identity_coverage -> plan` 单向，禁止反向依赖。repository-set 根只声明这些物理领域 owner，不得恢复平铺实现、owner `*_tests.rs`、`query_workflow`、`query_test_support`、`domain_affinity`、`identity_coverage` 或 `plan` sibling。不得重新引入同时承载 membership、带存储状态的 member 查询状态机、source-fallback 协调、freshness 状态转换或租约化 refresh workflow 的通用 repository-set service。

`application::update` 是严格的 version-check workflow 边界。根 `mod.rs` 只能声明模块并重导出稳定的 configuration、response、check 与 notice API；`config` 独占 source alias、环境策略、interval 转换和 GitHub repository 校验；`version` 独占 stable/prerelease SemVer 解析与排序；`result` 独占序列化 response/diagnostic contract；`candidate` 独占最高 release 选择和 update-availability 投影；`cache` 独占带 configuration key 的异步 cache 读取、freshness 与写入；`release` 独占 release-metadata session 准备、source iteration 与 dispatch；`workflow` 独占 cache-first check、force refresh、best-effort cache 持久化、时间捕获与用户 notice；`diagnostics` 独占稳定诊断 envelope。以上 owner 必须分别使用职责命名的物理目录，由各自 `mod.rs` 直接挂载 `mod_tests.rs`；update 根不得恢复平铺实现或 `*_tests.rs` sibling。物理 `sources/` 子域由纯声明 `mod.rs` 装配，`github` 与 `crates_io` 独占各自 URL、payload 和 candidate mapping，`metadata` 独占将技术无关 port 结果映射为有界 JSON payload 与稳定 source diagnostic。`ports::release_metadata` 独占 request、session、future 与 failure contract；`adapters::release_metadata` 是唯一具体 release transport owner，并把 client 构造、QoS 准入、timeout、status 校验和有界流式 response 读取委托给 `net::http`/`net::qos`。每个行为 owner 都直接挂载同层 UT。依赖必须保持 `workflow -> cache/release`、`release -> ports/sources/candidate/version`、source payload owner -> `metadata/candidate/version`、`metadata -> ports/diagnostics`、外层 adapter -> `ports/net` 单向；禁止反向依赖，禁止 application 引用 `reqwest` 或 `net`，也禁止在具体 adapter 之外实现 release 专用网络逻辑。

本地文件应用工作流在物理上统一收敛到 `application::knowledge::file_index`：`mod.rs` 独占共享 async service API、request/root 校验、freshness response 装配和 storage error mapping。物理 `scanner/` 域的 `mod.rs` 独占有界 blocking filesystem walk、全局 scan permit、timeout/backpressure 结果与 file-entry workflow，`mod_tests.rs` 是其直接 white-box contract。物理 `content/` 域独占有界正文摄取：纯声明 `mod.rs` 只重导 scanner surface，`budget` 独占 attempted-read byte 记账，`extract` 独占 eligibility、hashing 与 chunking，`read` 独占 capability-root authorization 与 snapshot verification；每个 content owner 直接挂载配对同级 UT。依赖必须保持 `scanner -> content::{budget,extract,read}`、`extract -> read` 单向，禁止反向依赖；`workflow_tests` 因验证 request 校验与 runtime-root 组合而留在 facade。不得恢复 `file_index.rs`、平铺 `scanner.rs`、`scanner_tests.rs`、`file_content_*` sibling、兼容 alias 或生产 path redirect，也不得把 blocking filesystem work 移入 async service method。

`application::knowledge` 根目录只能包含稳定 facade 以及物理 `file_freshness/`、`file_index/`、`index_refresh/`、`ingest/`、`map/` 和 `multimodal/` 子域。各职责命名的 `mod.rs` 独占其工作流并直接挂载 `mod_tests.rs`：freshness 聚合、持久 refresh 编排、request-to-mutation 转换与 evidence identity、文件型 knowledge-map 生命周期、有界 multimodal 转换保持分离。`map/` 内的 `error.rs` 是最低层共享错误 contract，`artifact.rs` 只拥有 v2 manifest/shard/archive 序列化与完整性 contract，`contracts.rs` 拥有公开 request/response contract 和受限的 mutation state，并可单向依赖 `artifact` 与 `error`；`history.rs` 独占有界公开 history page 读取与 archive traversal；`lock.rs` 独占跨进程 writer-lock 的 no-follow 打开、legacy 兼容、prepared inode 持久化、原子发布、崩溃恢复与有界清理协议；`mod.rs` 只保留迁移、有界 show/route 读取、artifact/root 原子发布和 Knowledge Map 生命周期编排，不得重新吸收 writer-lock 实现而突破 1000 行上限。`artifact` 不得反向依赖 `contracts`；两者共享的类型必须下沉到 `error` 等更低层 contract。`map/mod_tests.rs` 将路径隔离以及 history/writer-lock 场景分别委托给同目录的 `path_tests.rs` 和 `history_tests.rs`；`history_tests.rs` 是 history/archive 与 writer-lock 协议的聚焦行为测试 owner，三个 test owner 与所有生产 owner 都必须保持在 1000 行文件上限内。不得删除 `lock.rs` 后把 locking 合回 `mod.rs`，也不得把 writer-lock 场景散落回无职责测试桶。Evidence-identity UT 属于 `ingest`，不得挂在更宽的 application service facade。不得恢复平铺 knowledge 实现或无职责的 `*_tests.rs` sibling，也不得让 `application::service` 仅为承载 UT 而导入 ingest helper。

共享应用服务按工作流收敛到物理 `health/`、`lifecycle_plan/`、`retrieval/`、`service_status/`、`storage_diagnostics/`、`storage_provider/` 和 `watcher/` 子域。`application::service::retrieval` 独占 source-scope validation、freshness/index reconciliation、backend degradation、bounded search/rerank、provenance budget 和 retrieval response assembly；storage-provider 与 watcher owner 直接挂载 `mod_tests.rs`。`lifecycle_plan/mod.rs` 只装配请求、完整 plan、输入规范化与稳定 checksum；`forward_steps` 独占 install/upgrade/uninstall 正向步骤，`rollback_steps` 独占 checkpoint 恢复步骤，`step_policy` 独占步骤构造与平台 registration refresh policy，`execution` 独占 step/rollback 状态机和 runner dispatch，`checkpoint` 独占 attempt-scoped backup、atomic checkpoint publication、validation、restore 与本地文件边界，`process_runner` 独占 timeout、子进程终止及有界 stdout/stderr 排空，`platform_service` 独占平台 definition 和 manager command；八个 owner 分别直接挂载 `mod_tests` 或同名 `*_tests`。依赖保持 execution/rollback plan -> checkpoint/process runner、planning -> platform/step owner 单向；不得把 checkpoint 或 process primitive 反向耦合执行状态机。禁止恢复含正向、回滚、执行和平台渲染的 756 行复合 lifecycle plan、734 行混合 execution、`review_tests` 或 `review_followup_tests`。共享 service 根 `mod.rs` 只负责 service construction、共享状态、稳定 helper contract 和跨工作流组合；根 `*_tests.rs` 只能保留跨多个 owner 或外部 storage/runtime 边界运行的装配型 facade 测试。不得恢复平铺 service 实现、把 owner 专用测试放回 facade，或把 storage/watcher lifecycle 逻辑并入 `mod.rs`。

### 3.3 仓库领域模型职责

仓库领域类型统一按功能收敛在 `domain::code::repository`：`registration` 负责注册、selector、range 和索引请求，`retrieval_request` 负责查询类型、限定词、结果上限和检索层，`indexed_records` 负责持久化文件、符号、引用、关系、诊断及 tombstone 记录，`repository_status` 负责状态、scope preview、汇总和报告，`retrieval_results` 负责查询与特性开关结果，`scope_identity` 是版本化快照 scope 编码的唯一所有者；`validation` 仅作为目录私有校验边界。不得恢复混合职责的 `repository.rs` 或 `repository_helpers.rs`。

Workspace detection 是持久化 Git snapshot identity 的一部分。关闭检测时必须保留兼容格式 `git_snapshot:<16-hex>`；启用后必须追加且仅追加 `:workspace-v1:<canonical-bitmask>`，十进制 mask 规范表示已启用的 pnpm、Go module 与 Cargo workspace format 集合，顺序和重复项不得改变 identity，启用但 format 集合为空也必须与关闭状态区分。中央 scope parser/matcher 必须同时校验 fact-versioned base 与完整可选后缀。非写入式 scope preview 必须根据请求 ref、有效 filters 与请求的 workspace 配置计算 prospective identity，而不能返回当前 active scope。

### 3.5 依赖解析器职责

### 3.6 SQLite 存储边界

Code repository 持久化合同必须按能力拆分为 `RepositoryCatalogStore`、`CodeIndexTaskStore`、`CodeScopeRetentionStore`、`CodeIndexSourceStore`、`CodeIndexPublicationStore`、`CodeQueryReadStore`、`SoftwareProjectionStore` 与 `CodeRepositorySetStore`。`CodeRepositoryStore` 只能是无自有方法的兼容聚合 trait；新应用 helper 必须声明其实际消费的窄 capability，不能仅为便利依赖完整 `KnowledgeStore`。单个 code-storage capability 不得超过 20 个方法；不支持的可选能力必须返回明确 `StorageError::InvalidInput`，不得以空集合、`false` 或成功 no-op 隐藏能力缺失。Architecture gate 必须同时锁定聚合 trait 无方法、capability 方法数与高扇入 repository lookup/checkpoint helper 的窄依赖。

持久状态机必须以 typed phase 解码后再派发。`batch/session/finalization/phase.rs` 独占 checkpoint phase 合同，`query_index.rs` 与 `publication.rs` 分别独占查询索引修复和最终发布 quantum，`finalization.rs` 只维持具名 transaction context、fence 校验与阶段编排；不得恢复字符串分支与事务/发布逻辑混合的大函数。`snapshot/durable_clone/initialization.rs` 独占预算与 checkpoint 初始化，`validation.rs` 独占 identity/counter/phase parity，`delta.rs` 独占 dirty batch 活跃期间 clone-complete owner 的校验，`progress.rs` 只通过 `CodeIncrementalClonePhase` 推进。`snapshot/durable_delta/mod.rs` 每个 worker step 最多提交一个确定性的 dirty batch，`batches.rs` 独占 file-to-batch 规划并拒绝没有 file owner 的 fact。`tasks/retention/task_history.rs` 独占 terminal task audit compaction，`retention_gc` 必须通过受界 `ScopeGcPhase` 推进并把未知 phase 持久化为可观测错误。`schema/migration/index_refresh.rs` 独占 index-refresh table compatibility family，但仍由 migration owner 的单一外层 `BEGIN IMMEDIATE` transaction 调用，禁止子迁移自行提交。

SQLite 与 partitioned adapter 的 capability 实现也必须物理分区：`storage/sqlite/code/repository_set_store.rs` 和 `storage/partitioned/repository_set_store.rs` 分别独占 repository-set trait 适配，根 `mod.rs` 不得重新吸收这些实现。后者必须保留 partitioned topology 对尚不支持的 cross-shard overlay publication 的明确拒绝；不得伪造成功或回落到错误数据库。

技术无关存储边界必须物理收敛在 `storage/contracts/`：根 `storage/mod.rs` 只声明 contracts、partitioned 和 SQLite adapter，并重导稳定 surface。`boundary` 独占异步结果类型与存储错误映射；`topology` 独占运行时拓扑解析和 shard snapshot；`graph` 独占 graph/mutation-log trait 与 mutation record；`search` 独占有界 graph-search request、outcome、trace budget 和结果解引用；`health` 独占 graph/SQLite/聚合健康 snapshot；`index` 独占派生索引与运维持久化 trait、index cursor、持久 refresh-task contract、lag 和 stale diagnostic；`operations` 独占 worker、proposal、audit 与 operator request record；`code_graph` 独占 code-graph 持久化/检索 contract。既有 `canvas`、`code` 与 `file_index` contract owner 同样位于该目录。boundary error、topology parsing、graph default、canvas selection、search budget、health default、index default 与 code-repository default 行为必须由直接同级测试保护；纯数据 request 模块不得为满足形式而制造浅测试 helper。依赖保持 graph → boundary/search/health、health → index/file-index record、index → boundary/operations/file-index record、具体 adapter → 重导 contract 单向；禁止反向依赖 adapter，禁止恢复混合职责的 `storage/mod.rs` 或 `storage/mod_tests.rs`，也禁止通过私有 path 绕过稳定 `storage::*` facade。

SQLite 存储必须把 evidence 与稳定 ID 生成放在 `evidence_identity`，mutation 读取放在 `mutation_log`，提交时有效期归一化放在 `graph::version`，诊断 row count 放在 `table_stats`。存储模块必须导入这些明确边界，不得把无关持久化行为累积到通用 helper 模块。

SQLite adapter 必须完整收敛在 `storage/sqlite/`，根 `mod.rs` 只负责组合具名物理 owner；根层只能包含 `canvas`、`code`、`code_graph`、`connection_runtime`、`evidence_identity`、`file_index`、`graph`、`indexing`、`maven`、`mutation_log`、`operations`、`retrieval`、`schema`、`scope_filters`、`software`、`store`、`table_stats`、`tests` 目录与 `mod.rs`。`store/` 独占 `SqliteGraphStore`、schema-aware open/migration、connection pool、有界 blocking-worker 入口及其 contention 测试，`store/implementations.rs` 只把技术无关 trait 映射到这些具名 owner，不得把 transaction 逻辑恢复到 facade。`evidence_identity`、`mutation_log`、`scope_filters` 与 `table_stats` 必须各自作为直接挂载 `mod_tests.rs` 的物理 owner；跨 owner 的 metadata、graph/retrieval 与 GraphRAG 场景只放入 `tests/`。物理 `graph/` 域独占 graph 持久化：`mod.rs` 独占 inspection 与持久 graph-version 读取，`mutation` 独占 graph-fact transaction、entity/evidence linkage、affected-scope mutation metadata 与 evidence-reference invariant，`version` 独占 commit-time validity normalization。每个 graph owner 都必须直接挂载同级 invariant 测试；禁止 SQLite 根恢复 `graph_mutation`、`graph_state`、`graph_version` sibling 或兼容 alias。物理 `schema/` 模块树必须通过 `schema::{columns, initialization, marker, migration}` 独占 column upgrade、initialization、compatibility marker 与 pre-initialization migration；每个 owner 保留直接同级测试，SQLite 根不得把它们重新平铺成 `schema_*` alias 或 `#[path = "schema/..."]` redirect。`storage/` 父目录不得重新出现 `sqlite.rs`；concrete store lifecycle 或 graph 行为不得返回 `sqlite/mod.rs`，也不得用私有兼容重导隐藏反向依赖。

根 graph-store 行为由同级 `graph_storage_tests.rs` 验证；retrieval schema migration 与 BM25 fallback integration 场景收敛在职责明确的 `graph_retrieval_tests` 目录，并由 graph-storage 测试 owner 声明。不得恢复含糊的 `graph_tests.rs` 加 `graph_tests/` 组合，也不得把这些 graph-store 场景混入 code-graph fact 测试。

Software lifecycle 的候选加载必须先在 SQLite 内按 scope 筛掉普通源码 chunk。`software/lifecycle/document.rs` 的候选谓词必须从 build、IaC 与 design collector 当前支持的 manifest、CI/IaC、Markdown 路径和语言集合推导为语义超集；加载前校验明确的 document/chunk/byte 上限，随后按 path、line 和 chunk identity 的稳定顺序一次只物化一个完整文档。lifecycle 编排对每个文档只遍历一次，三个 fact owner 复用 prepared statement 持久化；结构化诊断必须报告 candidate document、chunk 与 materialized byte 数。正反路径测试与“大量无关 chunk、少量 manifest”回归必须同时证明现有可识别文件不丢失、无关源码字节不跨过物化边界。

Fenced code index 的最终可见性必须经过 software projection publication barrier。单 SQLite 中，code facts 完成后只允许把新 scope 留在 `stale/indexing`，checkpoint 留在 `finalizing:software_projection`，旧 active scope 继续可读；software facts 构建成功并再次校验 attempt fence 后，software status、staged code scope/repository freshness、checkpoint completion 与 publication receipt 才能在同一 SQLite transaction 中激活。投影错误或 stale fence 必须回滚该 transaction，不能产生 fresh scope、completed checkpoint 或 receipt。`storage::sqlite::code::publication/` 是 code-store 根允许的直接 owner，独占这一共享发布决策并直接挂载 rollback/withhold 测试；software 只能沿既有 software → code 方向调用它，不得形成 code → software 的反向依赖。

Partitioned SQLite 不宣称跨数据库原子。它必须按 `fence.repository_id` 路由到已存在的 checkpoint shard，缺失 shard 直接失败且绝不回落 control。Shard transaction 提交 code/software facts 后，目标 catalog route 仍保持 `staged`，记录 durable `staged_task_id` owner，并把 checkpoint 保持在 `finalizing:partitioned_publish`；active-only routing 让旧 active scope 继续可读。只有持有有效 fence 的 owner durable task 才能激活该 staged target。Shard commit 后，一个 control-database transaction 再次校验 fence 及精确 staged owner/target，并在同一事务中把 repository/scope route 改为 `active`、镜像 repository freshness/status、插入 publication receipt；事务回滚时这些 control-plane 改动必须全部不可见。此前 crash 从 staged shard 重试，此后 crash 复用 durable receipt，不得重建或重复发布。

Durable task 的 `succeeded` 转换是 publication 后独立的 fenced completion transaction。完成必须同时验证该 task 的 publication receipt、匹配的 fresh repository/scope，以及目标存在 checkpoint 时的 completed checkpoint；无 checkpoint 的 mode 不会为完成校验虚构 checkpoint。Stale attempt 或 lease generation 不得宣称成功。Receipt ownership 归 task，因此 attempt 过期后可由 reclaim 流程收敛到已发布结果，但旧 attempt 仍不能完成任务。对外 worker 响应必须等待该 task terminal 转换完成。

#### 3.8.1 领域模型职责

`domain` 必须是五个真实 Rust 子领域之上的稳定公开 facade，不能继续用生产 `#[path]` 别名把物理子目录伪装成扁平模块。`core` 拥有校验错误、source scope、graph version、entity identity 与 index state；`graph` 拥有多模态证据、mutation 与 retrieval contract；`code` 拥有 repository record/request、index task、repository set、staleness、view 与 workspace contract；`knowledge` 拥有 knowledge-map contract，包括保留的 code-map-backed `software-model` route 及其冲突校验；`operations` 拥有 worker/service lifecycle 与 software-global projection contract。依赖必须保持无环：graph、code 与 knowledge 建立在 core 之上，code 可以消费 graph retrieval policy，operations 组合 core、graph 与 code contract。根模块保留公开 `domain::*` facade，但不得恢复掩盖物理归属的路径别名。

`domain::graph` 根只能包含稳定 facade 与物理 `multimodal/`、`mutation/`、`retrieval/` 子域。`multimodal/mod.rs` 独占 evidence modality、extraction diagnostic、layout region 与跨字段 metadata 校验；`mutation/mod.rs` 独占 evidence、relation、claim、event、version-range、confidence、fact-status、commit-receipt 与 mutation-batch contract，两者都直接挂载 `mod_tests.rs`。Retrieval 的 policy、backend、diagnostics、evidence、hit、provenance 与 context-pack owner 继续位于 `retrieval/` 下。不得在 retrieval 目录旁恢复平铺 `multimodal.rs`、`multimodal_tests.rs`、`mutation.rs` 或 `mutation_tests.rs`。

`domain::operations` 根只能包含稳定 facade 与物理 `runtime/`、`software/` 子域。`runtime/mod.rs` 独占 worker state/task、proposal/conflict/provenance、audit event、service operator、service definition、lifecycle step、execution report、permission、package-manifest check 与 actor normalization contract，并直接挂载 `mod_tests.rs`；`operations/mod.rs` 只组合低层 domain contract 并重导出两个稳定 surface。不得恢复平铺 `runtime.rs`、`runtime_tests.rs` 或 `software.rs` sibling，也不得把 runtime validation 移入 facade。

`domain::operations::software` contract 必须是物理子域，`mod.rs` 只声明 owner 并重导出稳定公开接口。`request` 独占查询 kind、结果边界与 repository scope；`dependencies` 独占 component、SDK usage 与 dependency usage 证据；`graph` 独占投影 file、topic 与 relationship；`lifecycle` 独占 build、IaC 与 design 事实；`projection` 独占聚合状态与结果 contract；`validation` 独占可选文本归一化、confidence 边界和稳定 software identity。每个 owner 都直接挂载同级测试文件。不得恢复平铺的 `domain/operations/software.rs`、根级 `software_tests.rs`、生产路径别名或 facade 所有的校验行为。

每个带状态或校验行为的 domain 实现必须直接挂载具名同级 `*_tests.rs`。Repository registration、scope identity、retrieval request、repository status 与 repository-index summary 的测试分别留在精确 owner 旁；禁止恢复跨 owner 的 `domain/code/repository_tests.rs` 聚合桶。仅包含序列化 record 的纯数据文件可以不制造无意义测试，但不得以此为由把其他 owner 的断言移入 facade 测试。

`code::config_files` 根只能保留稳定 facade 与物理 `calls/`、`detection/`、`key_values/`、`knowledge_map/`、`languages/`、`model/`、`source/` 子域。调用聚合、语言识别与恢复形状、类型化键值事实、知识地图 topic、规范化 record/range、byte-stable source line 与文本规范化必须由对应 owner 独占并直接挂载 `mod_tests.rs`；`languages/` 继续拥有各格式专属提取器。不得在这些目录旁恢复同名平铺实现文件、把跨格式行为并回 facade，或用生产路径重定向伪装物理分组。

### 3.9 自迭代评估器职责

`tools/self_iteration::evaluator` 必须按评估阶段和证据类型分组：`runtime` 负责一次评估运行的顶层协调、并发限制、合同、报告与结果汇总，`quality` 分别拥有门禁定义和执行，`workloads` 按 repository、repository-set、agent、CLI、file 和 semantic-vector 工作负载划分，`fixtures` 只拥有生成式仓库 fixture 及其写入生命周期，`judge` 负责研究判断的配置、prompt、backend 和结果合同。evaluator 根仅声明模块并暴露 `evaluate_candidate` 与 `EvaluationRun`。runtime 必须分离 `contracts`、`concurrency`、`reporting`、`workdir`、`finish` 与 `orchestration`；`runtime::workdir` 独占带校验的逐次运行 evaluation home 创建、direct-child 检查、保留策略与安全清理；workloads 只能依赖底层 runtime 合同、并发和报告服务，由 orchestration 向上组合 workloads。workload 专属 JSON case 失败映射留在 `workloads::case_scoring`，避免 reporting 反向依赖 workloads。每个有行为的 runtime owner 直接挂载同级测试，覆盖 repository work-plan、有界 parallel-map、finish 序列化与报告不变量。`quality` 子树必须在领域根拥有门禁合同、分离策略与执行，并由两个 owner 直接挂载聚焦 UT；生产门禁装配不得使用 `include!`，quality-policy UT 不得混入 workload 选择断言。`judge` 子树必须在领域根拥有共享 evaluation input，保持 evaluation 到 settings、prompt、backend 与 outcome owner 的单向组合，并为每个 owner 直接挂载同级测试文件。shell 命令解析归 judge settings 而不是 outcome 验证，生产 judge 装配不得使用 `include!` 或跨 owner 的 test-support 片段。`workloads` 子树必须使用真正的 Rust 模块分别拥有 agent、CLI、file、repository、repository-set、selection 与 semantic-vector 行为。Repository workload 内由 `expectation` 独占有界 Git/file-count 观测、scope-preview 身份和 cold/incremental terminal 校验，`isolation` 独占隔离的 product home 与安全清理；两者都直接挂载同级测试。共享 case 失败与 payload 约束归聚焦的 `case_scoring` 模块，而不是 file 或 repository workload；每个有行为的源码文件必须直接挂载同目录 owner 测试文件，生产与测试装配均不得使用 `include!`。`fixtures` 子树必须使用真正的 Rust 模块分别拥有语言/源码族、agent-workflow 源码、仓库装配和共享文件 writer 边界；repository 与 writer UT 必须由对应 owner 直接挂载。生产 fixture 装配不得使用 `include!`，fixture 源码常量不得留在 workload 执行模块。评估器 UT 必须与被验证边界同目录并使用可定位的 `*_tests.rs` 名称；不得恢复 evaluator 根测试装配、`evaluator_tail`、跨职责 `evaluator_tests` 或在 `tools/self_iteration/src` 根目录平铺同一领域的 `evaluator_*` 文件。

### 3.10 自迭代评分职责

Dependency-usage 的 `matching` 独占不可变 component-key 索引、manifest owner 收窄、Cargo alias 证据与有界跨语言 import key 归一化，并拥有匹配测试套件。`mod` 工作流只编排证据、匹配、置信度交集、去重和确定性排序；当没有组件可匹配时必须在读取 import 表前短路。

ACP adapter、prompt-context builder 及其配对测试统一位于纯文件型 `interfaces/agent/acp` 分组，同时保持公开 `interfaces::agent::acp` 路径不变。上层 agent 目录不得再把 ACP session 或 context 实现文件平铺在 MCP、audit 与 policy 领域旁。

共享 agent interface 根目录只能包含稳定 `mod.rs` facade 以及物理 `acp/`、`audit/`、`mcp/` 和 `policy/` 子域。`audit/mod.rs` 独占有界进程内事件保留、单调序号、有界异步 JSONL sink 与直属 `mod_tests.rs`；`policy/mod.rs` 独占 adapter error contract、query/path 校验、scope 归一化与授权、request-limit 授权及直属 `mod_tests.rs`。根模块只声明并重导这些稳定表面。不得恢复平铺 `audit.rs`、`audit_tests.rs`、`policy.rs` 或 `policy_tests.rs` sibling，也不得把其行为移入 agent facade。

ACP 初始化、会话、提示词、进度更新、结果与错误 wire contract 统一归 `acp::protocol` 所有，并由 `protocol_tests` 验证 JSON 字段名、省略规则与状态转换。adapter facade 只重导出这些公开类型并编排会话请求，不得重新内嵌序列化 DTO。

ACP session identity、活动请求 cancellation channel 和自动清理 lease 统一归 `acp::session_registry` 所有。该 owner 必须规范化不可信客户端元数据，并由配对测试覆盖 session lookup、取消通知、显式 release 与 drop 清理；adapter facade 不得直接维护共享 map 或 mutex。

ACP prompt 的 scope authorization、freshness parsing、资源 limit/context-byte 校验及 domain request 构造统一归 `acp::prompt_mapping` 所有。`prompt_context` 只执行已验证的 graph 或 codegraph 请求并汇总结果；依赖方向必须保持 `prompt_context -> prompt_mapping`，禁止反向依赖形成环。

Worktree-overlay 索引实现统一位于物理 `code/index/worktree_overlay/` 目录。根 `mod.rs` 只能声明并重导具名物理子域；`snapshot/` 独占 filesystem/Git 选择、overlay identity、plan、workspace-entry 对账与 snapshot 装配；`change_recording/` 独占 changed-path 路由和普通文件/目录分类；`directories/` 独占有界目录递归与 nested-repository 排除；`overlay_plan/` 独占稳定 clean/dirty identity；`overlay_scope/` 独占 effective filter 与有界 change 准入；`recording/` 独占普通文件/删除替换；`untracked/` 独占宽目录显式 opt-in。每个行为 owner 直接挂载 `mod_tests.rs`，`gitlinks/` 保持聚焦子树。不得恢复平铺实现或 owner 测试，不得把编排恢复到根 `mod.rs`，不得在 `code/index` 根目录恢复 `worktree_overlay_*` 前缀文件，也不得改变 overlay 的有界变更、Gitlink 展开或 scope 过滤合同。

Worktree-overlay 的 hash marker、删除集合、待解析文件集合和同内容跳过判定归 `worktree_overlay::recording` 所有，并由同级 UT 固定二进制 framing 与删除后重建语义。`snapshot`、`change_recording` 和 `gitlinks` 只能复用该记录边界，不得各自实现不同的 overlay hash 输入协议。

Worktree-overlay 的 Gitlink 行为必须物理收敛在 `worktree_overlay/gitlinks/`：`mod.rs` 独占 staged/unstaged/deleted/dirty-submodule 状态转换、有界 child 展开与 base-child 对账；`recorder` 独占输出聚合、子路径删除回放与 scope-aware recording；`state` 独占 staged-index 分类、submodule HEAD 读取、base-object 存在性和 parent-path 组合，三个 owner 都直接挂载同层 UT。依赖必须从 Gitlink 状态机单向流向 `recorder`、`state`、`directories`、共享 `recording`、source Gitlink contract 与 overlay scope；任何下层都不得反向依赖 `snapshot` 或 `change_recording`，不得复制 recorder，也不得直接发明新 marker。

Source-layout 能力必须收敛在 `code/source/layout/`。有界 source-root 推导、宽依赖目录拒绝、discovered-root 上限和 effective filter 扩展/交集只归配对 UT 的 `layout/discovery` 所有。归一化 path-filter 合并与交集、边界感知的准入与重叠、submodule child-scope 投影只归 `layout/path_scope` 所有，并由同级 UT 直接覆盖归一化、无交集、父 scope 覆盖、child 投影以及 registration/selector 交集。Git/filesystem 路径准入、language/preset 拒绝、显式 exclusion opt-in 和稳定 exclusion reason 归配对 UT 的 `layout/selection` 所有；调用者不得复制 source-kind 相关的选择顺序。source 解析、selected-entry 物化、effective scope filter、filesystem 内容 hash 与 synthetic-ref 一致性只归配对 UT 的 `layout/scoped_snapshot` 所有。受界 exclusion/largest-file 样本、language/byte 分布、generated/heavy 分类和 degraded 单次计数只归配对 UT 的 `layout/preview` 所有；顶层 code facade 不得拥有这些聚合测试。source-kind-aware changed-path 分组、空输入不读取仓库和稳定排序去重只归配对 UT 的 `layout/impact_partition` 所有。impact 和 overlay 工作流只能通过纯声明/重导出的 `layout` facade 消费这些 owner，不得复制 root 推导、路径匹配、规范化、选择、scoped-snapshot、preview 或 partition 规则。

Tracked-entry 路径规范化、entry/submodule 准入和 Git pathspec 投影统一归 `code/source/changes/scope` 所有，并由同级 UT 直接覆盖 empty、nested、whole-entry、ancestor 与 child-path 行为。有界递归 worktree/git-dir 枚举、环路阻断、blob 大小收集和 expanded/unavailable submodule 状态报告归 `changes/tracked_entries` 所有，并由同级 UT 直接覆盖 record 构造、lookup 错误分类与 empty-scope 命令抑制。该 owner 只能通过窄方法消费 `scope`，不得复制匹配规则或读取其内部表示。经校验的双 ref Git name-status 加载与 rename 检测归配对 UT 的 `changes/diff` 所有；调用者不得拼装分叉的 diff 命令或绕过 option-shaped ref 拒绝。`changes/submodule_repository` 独占 submodule worktree-root 校验、config 与 `.gitmodules` 名称发现、安全 nested-name 校验、worktree/gitdir 定位及目标 commit 可用性，并直接挂载 parser 与安全 UT。worktree 与显式 git-dir 命令执行及 Git 失败映射统一归直接挂载 UT 的 `code/source/git` owner；`changes` 与 Gitlink 模块只能消费这些下层边界，不得复制 repository 解析或自行持有进程执行。

源码 Gitlink/submodule 能力必须收敛在 `code/source/gitlink/`。`entries` 独占 tree gitlink commit 判定、child-filtered tracked entry 枚举、初始化/反初始化 submodule blob 读取与 worktree root 解析，并直接挂载 `entries_tests`；上层 incremental/worktree-overlay 只能调用该 owner，不得复制 worktree/git-dir fallback。`diff` 独占双侧 submodule change 分类、nested gitlink 有界递归、worktree/git-dir diff fallback、scope-aware entry expansion 与共享预算检查，并直接挂载 `diff_tests`。`impact` 独占 `GitlinkImpactExpander`、双侧路径展开与 fallback 合并、稳定去重及预算校验，并直接挂载 `impact_tests`；`gitlink::mod` 只能声明模块和重导出边界。依赖必须保持 `impact -> diff -> entries/commands/paths/selector` 的单向关系，禁止下层反向依赖 impact 或 facade。

顶层 `code` facade 由 `mod.rs` 与同级 `mod_tests.rs` 一一配对；源码发现、布局、submodule、filesystem 和 worktree-overlay 场景测试继续收敛在 `code/tests/source`，可复用 fixture 由 `code/tests/fixtures.rs` 维护。不得在场景测试目录旁恢复同名 `tests.rs`，也不得把 facade 不变量混入源码场景测试。

其余同级测试挂载必须全部显式：runtime、service、repository/source-fallback/view 工作流、code feature/search 边界，以及 SQLite Maven、view、schema、batch、graph、workspace、operation、indexing、retrieval、snapshot 和根 adapter 都必须通过 test-only `#[path]` 声明具体测试文件。禁止依赖隐式 `#[cfg(test)] mod name;` 文件解析，避免 rename 或同名目录掩盖物理 owner。

自迭代的 config、scoring 和 history facade 必须把 facade 合同装配留在同级 `mod_tests.rs`。evaluator 根不含行为，因此不设置 facade 测试桶；runtime、quality、judge、fixture 与 workload 测试直接由精确 owner 挂载，其中 repository-set workload 自行挂载同级 `repository_set_tests.rs` provenance UT 合同。不得把测试体写回生产文件或恢复跨 owner 的 evaluator 测试装配。

自迭代 Codex adapter 的 `command_tests`、`execution_tests`、`history_context_tests`、`prompt_tests`、`unattended_prompt_tests` 与 `result_mapping_tests` 必须由各自精确的生产 owner 通过显式 test-only `#[path]` 挂载，测试文件本身直接包含测试项。禁止生产期 `include!` 展开、facade 代管行为测试或在配对文件中再嵌套同名 test module。

## 4. HTTP 与 QoS

HTTP 必须建立在非阻塞 OS event mechanism 之上，例如 epoll、kqueue 或 IOCP 经由成熟 async runtime 暴露。所有 inbound/outbound 网络工作在消耗资源前都必须经过 QoS policy。

网络入口必须支持：连接预算、请求预算、body 大小限制、timeout、cancellation、graceful shutdown、rate limit、queue depth metric、drop metric 和 overload response。

## 5. 代码质量硬约束

- tracked source、test、documentation、script 或 workflow 文件不得超过 1000 行。locked build 必需的生成式 release lockfile 例外，当前为 `Cargo.lock`，且必须保持机器生成。
- 根 README 是简洁的入口与导航面；详细实现所有权和运维合同必须放入 README 所链接的职责型 architecture、capability 或 user-guide 文档中，README 增长同样不得绕过 1000 行上限。
- 不添加 shallow function；函数必须负责校验、转换、外部边界、资源生命周期、错误映射、观测或真实编排。
- 不保留 dead code、TODO stub、无调用公共 API、无测试 speculative extension point 或注释掉的实现。单元测试不等于生产调用者：共享 retrieval term normalization 只保留 rerank 实际消费的操作，不得把 identifier classifier、stemmer 或 public data shape 隐藏在 `#[allow(dead_code)]` 后。
- 项目身份常量集中在 `project` 模块；模块局部运行默认值留在所属模块。
- `unsafe` 默认禁止，除非有明确边界、理由和测试。

## 5.1 文件监听 (fs.watch) 约束

- 文件监听通过 `notify` crate 实现跨平台支持（Linux inotify、macOS FSEvents、Windows ReadDirectoryChangesW）。
- 监听事件必须经过 debounce 窗口合并，防止高频文件变更产生无界任务。
- 内容哈希过滤（`ContentHashCache`）必须过滤无实际内容变化的保存操作。
- `max_watch_dirs` 必须限制最大监听目录数，防止 fd/inotify watch 资源耗尽。
- 监听失败时必须自动降级（`Degraded` 状态），不得影响查询热路径或 async runtime。
- Watcher 配置必须通过 `env` 模块的环境变量覆盖机制加载，不得在其他模块直接读取。
- Watcher 状态和诊断信息必须通过 `service status` API 暴露。
- 增量索引任务（`CodeIndexTaskSeed`）必须进入持久化任务队列，不得跳过 durable task lease、checkpoint 和 bounded retry。

- 大仓库索引不得把 180 秒历史基线当作所有规模的固定硬超时。系统默认启用 `index_budget_mode=elastic`；除非显式选择固定/严格模式，预算必须基于授权 Git 文件数和已记录吞吐基线计算，并受显式 `max_index_budget_ms` 上限约束；注册开销必须单独有界。弹性等待不能绕过 durable staging、唯一 writer、lease、checkpoint、edge/FTS finalization 或 freshness 状态。计算公式、观测字段和运维判读见[大仓库索引弹性长预算模型](../05-benchmarks/12-elastic-index-budgets.md)。
- Watcher 根只能包含 facade 与物理 `config/`、`event_filter/`、`hash_cache/`、`task_seed/`、`engine/` 子域。前四个 owner 分别独占 typed runtime configuration、path/language event admission、有界 content-hash observation 与 durable overlay task-seed 构造，并各自直接挂载 `mod_tests.rs`；task-seed invariant 不得漂移到 engine integration test。真实 `watcher::engine` 子树继续由 `mod.rs` 独占公共 handle 与启动，`event_loop`、`repository_registry`、`index_queue` 和 `diagnostics` 分别独占 OS event、动态 watch root、durable-task 投影与状态更新。依赖从 engine 单向进入四个聚焦根 owner，不得反向。跨 owner 异步行为由同目录 engine integration harness 保护；不得恢复平铺 `config.rs`、`event_filter.rs`、`hash_cache.rs`、`task_seed.rs`，也不得重新压平 engine responsibility。

## 6. 文档与测试硬约束

- 任何代码、配置、行为、测试、workflow、benchmark、安装或运维变更都必须同时刷新对应文档。
- Unit test、Rust integration、benchmark、browser integration 与 architecture gate 分离；architecture gate 的 graph/report artifact 在失败时也必须保留用于定位。
- Rust 行覆盖率必须保持 90% 以上，覆盖 invariant、错误分支、边界值、async cancellation 和 backpressure。
- Browser integration gate 必须安装 Playwright Chromium，例如 `uv run --extra dev python -m playwright install --with-deps chromium`。
- 文档本身需要检查链接、编号、行数上限和过期状态。
- Knowledge Map writer schema 采用 staged rollout：CI 总是要求当前源码 CLI 通过 `knowledge/knowledge-map.yaml` 与 `codespec/codespec-map.yaml`，并安装 crates.io 最新 stable CLI 复验。若 stable 低于声明的最小 v3 reader `1.1.15`，只有源码版本更高时，不兼容结果才可报告为 `staged_pending_reader_release` artifact；源码与 stable 同版本却不兼容必须以 `incompatible_same_version` 硬失败。stable 达到最小 reader 版本后，任何不兼容都必须使门禁失败。不得在没有兼容 reader release 的情况下继续提升默认 writer schema。

## 7. 验收标准

- 新模块能说明它属于哪个所有权边界，以及为什么不会形成循环依赖。
- 新 background 或 network 行为能说明资源预算、失败模式、取消和观测指标。
- 新检索或性能优化能说明泛化机制，而不是只解释某个样例为什么通过。

Knowledge Map v2 的 archived history lookup 必须使用根 manifest 授权、SHA-256 内容寻址、fanout 与深度均有硬上限的 range index；任何公开 history page 的 I/O、内存和节点读取预算不得随总 archive 数线性增长。Index range 必须连续、无重叠并覆盖完整 archived checkpoint；缺 index 的早期 v2 只能通过受 writer lock 保护的显式表示层迁移补齐，读取路径不得回退 reverse-chain scan。迁移和 append 必须先发布 immutable nodes，再原子发布 root；崩溃前的 root 始终可读且重试对同一内容幂等。

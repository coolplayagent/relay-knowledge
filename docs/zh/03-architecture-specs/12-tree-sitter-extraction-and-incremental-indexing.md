## 1. 设计结论

Tree-sitter 是代码结构入口，但不是全能语义分析器。架构必须把 grammar、query capture、错误降级、增量候选缩小和索引刷新串成可恢复 pipeline，使 unsupported language 或不可恢复 parse error 只降级局部能力，不破坏整体检索；C/C++ macro、preprocessor 和 decorator 区域的可恢复 parse error 在抽取仍可靠时应继续保留结构化事实。

## 2. 语言注册

每个语言注册项包含：language id、file extensions、tree-sitter grammar、capture queries、comment rules、identifier segmentation 和 fallback chunker。缺失 grammar 时，文件仍进入 text chunk 和 BM25 路径。查询时的 source fallback 不是 grammar 替代品；它只能在已索引源码候选上补充精确文本证据，不能创建图事实。

配置、构建和模板 grammar 注册在代码配置模块下，而不是运行时配置模块。支持面包括 Markdown、XML、Bazel/Starlark、Make、CMake、Dockerfile/Containerfile、Java properties、TOML、INI/`.conf`、YAML、JSON、Go module、Ninja、Jinja2 和 Go template。这些格式写入普通 file、symbol、reference、import、dependency、feature-flag 和 chunk facts，查询 API 不需要为配置检索引入独立 schema。SQL 作为 `.sql` 文件的代码 grammar 注册，会在同一套仓库代码图表中写入 table、view/materialized view、function/procedure、trigger、type 等 schema object 符号，以及 SQL 对象引用和调用引用。层级配置格式必须写入稳定的点分路径；数组和数组表使用 `[]` 而不是数字下标，例如 `server.port`、`containers[].name` 和 `bin[].name`。

结构化文档和配置文件采用 Tree-sitter AST 加产品规则的组合。Tree-sitter 负责识别 Markdown 标题、链接定义、inline link、JSON pair/array 和 INI section/setting 的语法节点、range 与 error node；产品规则负责把 JSON 数组折叠成 `[]` 路径、把 INI section 和 setting 合成点分名称、过滤 Markdown 外部 URL 或 anchor-only 链接，并把本地 Markdown 链接写成 unresolved import metadata。Markdown 和配置文件即使存在 symbol 级 chunk，也必须保留文件级 chunk，保证正文、配置值和局部 parse failure 仍可通过 BM25/hybrid 召回。

Parser 实现必须把语言专属规则放在高内聚的语言目录中。Node kind 分类、语言专属 import 抽取、C/C++ 手工恢复逻辑归入 `src/relay_knowledge/code/parser/languages/<language>/`；通用解析流程、syntax helper、文本校验、依赖清单解析和 chunk 构建保留在 parser 层共享模块。

Bash import 抽取把 shell 转义后的 dot builtin `\.` 视为与 `.` 相同的语义。识别边界只接受完整 command token，后面必须是空白和非空 operand，因此 `\.helper` 之类的前缀不是 import。Parser 保留原始源码拼写与 range，本地 target resolution 则复用普通 dot builtin 的同一套有界路径规则。

Rust trait implementation item 使用语言内聚的结构化补充规则：`impl Trait for Type` 产生一个以目标 type 命名、覆盖完整 implementation item 的 `implementation` symbol。Inherent `impl Type` block 不产生这条补充 symbol，因为其内部 method 已提供结构化事实；对每个 inherent block 再制造候选会扩大 definition 候选集，却不会增加 trait relationship surface。

## 3. Capture Contract

Query captures 输出统一结构：definition、reference、call、import、feature flag/config usage、doc comment、symbol span、body span 和 chunk span。Capture 结果在写入前必须经过 scope、path、line/column 和 content hash 校验。

Symbol documentation 同时接受既有的语言特定 line-doc 形式和与声明直接相邻的 documentation block。`/** ... */` 是 symbol-level block 形式；`/*! ... */` 只在其语义确属 owner documentation 的语言中接受。Rust 的 `/*! ... */` 属于 module/crate inner doc；在尚未建模 module owner fact 时，明确不把它绑定到下一声明。Block 规范化会移除定界符、CRLF 残留、首尾空行和每行 leading `*`；普通 `/* ... */` 绝不能提升为文档。普通 symbol 的 owner lookback 仍限制为 4,096 bytes；class、interface、struct、trait 等 type declaration 可以在 UTF-8 边界内使用最多 16,384 bytes 的 scan window，以覆盖合法但较长的类型级 Javadoc。查找窗口与持久化预算必须分离：无论 scan window 多大，只保留文档开头最多 4,096 bytes、64 行的 UTF-8 安全摘要。Block 与 owner 之间的空白消耗同一 scan budget，更早的 block 不能伪装成相邻文档，并且摘要只绑定到紧随其后的一个声明。

Documentation owner 与 symbol extent 是两项独立 capture fact。C/C++ tag 可能只暴露 `function_declarator`，因此 documentation anchor 必须上溯到所属 declaration 或 function definition，再穿过外层 template declaration；Java annotation 则继续属于其 declaration owner。该 anchor 只用于寻找相邻文档，不能扩大 symbol byte/line range、signature 或 stable identity；同一 symbol 后续被更宽的 manual representation 替换时，也必须保留已经抽取的 owner documentation。这组语义以 `doc-block-owner-anchor-v2` 和 `bounded-type-doc-summary-v1` code-fact component 持久化，必须通过可恢复 full index 重建事实。

## 4. 全量构建

```text
resolve snapshot
  -> enumerate authorized files
  -> batch parse and chunk
  -> write file/symbol/reference/feature-flag/chunk facts
  -> finalize cross-batch edges
  -> refresh scoped code search document 与 software projection
  -> mark scope fresh
```

全量构建过程中旧 fresh scope 继续服务查询；新 scope 只有 finalize 成功后才成为 fresh。

fresh full-index 复用是只读 eligibility path，不是 derived-index refresh path。只有 exact content/workspace scope 的兼容 checkpoint 不存在或已是终态 `completed`、同 repository/scope 的 software projection 明确存在且非 stale，并且 disabled workspace request 不再有该仓库拥有的 automatic workspace state 需要删除时，才能立即返回 completed；不得拿 projection 与无关的全局 graph version 比较。checkpoint 仍为非终态、projection 缺失或 stale，或者 disabled-workspace cleanup 仍有实际状态要清理时，必须进入普通 durable code-index task，由 live attempt fence 覆盖 cleanup、projection rebuild、receipt publication 与 partitioned catalog handoff。真正 fresh 的 scope 复用不产生 SQLite 写入，并如实报告零写入进度。

SQLite finalization 以持久 writer quantum 推进。Query-index 构建现在格式化 `finalizing:build_query_indexes:v3:N`，其中 `N` 是 17-slot version-3 plan 最后完成 slot 的 ordinal。Version 2 曾保持 version-1 ordinal 0 到 15 不变并追加 ordinal 16；version 3 继续冻结全部 ordinal identity，只退役 ordinal 1 `code_repository_symbols_lookup (source_scope, name, qualified_name, path)` 的创建动作。该 retired slot 不再新建，也不自动删除；若同名索引存在，startup、cursor 校验、repair 与 publication 仍严格要求其 owner、非 unique/partial 形态、有序列、升序方向和 `BINARY` collation 完全一致。只有 version-3 cursor 或 current-plan coarse scan 才能把缺失 unit 1 视为 stable skip。规范 version-1/version-2 token 继续可读，并在每个 writer quantum 保留原 version：legacy cursor 只有在该物理索引精确存在时才能越过 unit 1，因此 completed prefix 与后续 suffix 都不会被重新解释。畸形、越界和未知版本 token 全部 fail closed。

单个事务校验完整 file prefix 与 fence、最多创建一个 required index、以 CAS 推进 checkpoint、再次校验 fence后提交；crash 后 index 与 token 要么同时存在，要么同时不存在。未完成的 current plan 写 version-3 ordinal，完成时写 coarse `finalizing:build_query_indexes`。任何 retained 非终态 coarse state 都必须在后续工作或 Ready 前重新校验 current plan。每事务最多修复一个缺失 required descriptor，并写 `finalizing:query_index_repair:v3:N:resume:P`；version-2 repair 与 reference-search wrapper token 继续可读，并保持 legacy-prefix strictness。稳定 `P` code 跨 reopen 保存 exact coarse phase。终态 `completed` 仍只校验既有 shape、允许 required descriptor 缺失且不做机会式改写；自动终态修复必须另建 durable leased migration task。未来若重新解释 ordinal，必须再次提升 plan version并提供显式恢复规则。

终态例外只适用于 catalog 已 active 的历史 `completed` checkpoint。若 inactive staged partition 保留遗留 raw `completed` token，而 public projection 仍为 `finalizing:partitioned_publish` 且 current query plan 不完整，exact begin 只能在当前 task fence 下重新打开它：单个 shard transaction 对完整 raw token 做 CAS，锁定并校验 control authority，证明 catalog route 仍由该 task staged，再把 raw state 恢复为 `finalizing:partitioned_publish`；随后才进入普通的 durable one-index repair。已有 receipt 不能绕过该 eligibility gate。

Version-3 query-index plan 包含 17 个稳定 slot：16 个 required descriptor 与 retired ordinal 1。Database startup 不创建也不删除 descriptor，只严格校验已经存在的同名索引。Fresh `Restart` 清理目标 scope 后统一采用保守策略，不再根据 path count 推断 single/multi-batch，也不受后续 byte/row 分批影响：仅当共享的 `code_repository_chunks` owner 全局为空时预建 ordinal 13/14，即 `(source_scope, path)` 与 `(source_scope, symbol_snapshot_id)`；这样 content-bearing chunk row 不会在 finalization 再承受整表 CREATE INDEX 扫描。其他 populated-heavy required index 仍全部延后，chunks owner 已有任意 row 时两个索引都不提前创建。Resume session 不预建任何索引。Snapshot/import publication 只能在 fact mutation 前预建 required empty-owner index，随后要求所有 required slot 完整；populated owner 缺 required index 时 fail closed，旧 active scope 保持不变。Retired slot 缺失即视为完整，但同名索引若存在仍必须是 exact legacy shape。

Reference-search finalization 使用 staged-only grouped v2 协议 `finalizing:rebuild_reference_search:v2:{cleanup|discover|build}:N`。Cleanup 通过 `(source_scope, document_kind, record_id)` 对 metadata owner 做 keyset，并删除对应 group、FTS 与 metadata；discovery 按 `reference_id` 对基础事实做 keyset，为每个精确 `(name, kind, path, coalesce(target_hint, ''))` identity UPSERT 一个 durable owner，保存 `MIN(reference_id)` 与 occurrence count；build 按 group ID 做 keyset，并对规范化 reference 字段调用 canonical search-document encoder，不执行一次性全 scope `DISTINCT`。每页同时预留 progress CAS 与 checkpoint CAS，因此按每条输入保守计三个 owner mutation 时，最多接纳 `min((max_rows_per_batch - 2) / 3, 32768)` 个输入行。Byte limit 是整个 writer quantum 的 `min(max_bytes_per_batch, 16 MiB)`，包括 owner、progress、checkpoint 与 EOF manifest 的完整记录保守上界。单条 lazy 主键 scan 只暴露整数 lookup key、cursor 长度与 owner byte 上界；Rust 遇到第一个超预算候选即停止，并只在准入后获取 cursor 文本。Build sizing 用各字段长度代数计算，不预先拼接任意大的 search document。EOF 由每个受界页维护的冻结计数证明，然后原子发布 v2 manifest 并删除 progress。每页校验 live lease/fence、未发布 route、exact query-index plan、checkpoint token 与 partitioned `staged_task_id`；query-index v3 repair wrapper 保留 inner protocol version 与精确 page。保留的 v1 cleanup/build row 只用于 leased recovery：同一事务校验 v1 token 与冻结 checkpoint count，从 durable resource budget 重新派生更严格的 v2 row/byte limit，并从 v2 cleanup page zero 重启。Publication 与 fresh serving 都要求 current manifest；畸形或已越过 v1 progress 的旧 scope fail closed，由新的 fact-versioned full task 替换。

对 fenced、尚未发布的 full-replacement scope，普通 reference resolution 使用 `finalizing:resolve_references:v1:resolve:{completed_page_ordinal}:{completed_reference_count}:{cursor_digest}`。Progress row 持久化 exact cursor 与 limits；每次 reopen 都要求 token 的 page/count/digest、checkpoint 冻结的 `committed_reference_count`、progress count 与 cursor identity 完全一致。Page zero 不得有 cursor；续页用索引点查证明 cursor row；completed count 不得超过 `page * page_document_limit`；zero-count 初始化证明 fact 表确实为空；EOF 无需 prefix count scan，而是同时证明 frozen total 与 exact 最大 reference ID。每页先为 progress/checkpoint 两次 CAS mutation 留位，最多扫描 `min(max_rows_per_batch - 2, 32768)` 个 reference 位置。Lazy keyset scan 先读取 row identity 与长度，仅对非 call reference 获取受界 path/name；每页 name 与 `(name,path)` cache 对 owner 只做至多两条索引 length probe，ambiguous symbol ID 不进入缓存。Call reference 仍计入 durable cursor 与 frozen total，但本阶段不获取其 payload、也不更新它；stale binding 校验与 callable resolution 全部由专属 call-target phase 负责。已接纳的非 call range 通过分别静态的首条页或续页 UPDATE 一次处理并保留页内去重，每页只点查最后一个已接纳 cursor。Byte admission 在 mutation 前计入完整 owner mutation、progress 与 checkpoint 记录的保守上界。Direct token 与 nested query-index-repair token 在完整进程重开后都会跳过 blob fetch/parser restart。Queryable/unfenced 与 direct-incremental scope 继续采用既有受界 coarse admission，不能进入 staged protocol；coarse normalization 遵循同一 call-target ownership 边界。合并后的 checked finalization bound 仍保守保持 `CODE_INDEX_FINALIZATION_MAX_STEPS + 4 * committed_reference_count + 6`；row、byte、timeout、lease、FTS 与 freshness budget 均不放宽。

Reference-search 初始化只做常量工作：冻结 checkpoint reference count 并创建空 progress row，不扫描 facts 或 FTS。Transactional search persistence 在每次受界 INSERT 后推导新增 FTS interval，不再对虚表执行 `max(rowid)` 扫描，并使用 non-replacing metadata insert，因此每个已提交 group document 都有一个 exact owner，否则整页回滚。Database open 绝不扫描 runtime facts 来 backfill group。Exact schema validation 要求 group primary/unique key、binary text identity、path index、manifest/progress `NOT NULL` 与 `CHECK` constraint，以及 owner capability marker；空的畸形 owner 会在事务内重建，非空不兼容 owner fail closed。Metadata 是枚举权威；durable staged writer、受界 direct copy 与显式 recovery import 从 indexed owner 枚举，绝不通过 FTS 的 `UNINDEXED` scope/kind 列反向 COUNT。没有 metadata 的 raw FTS row 不复制、不服务，并留给受界 `search_orphans` GC；metadata row 缺少 exact FTS peer 时 fail closed。Direct full snapshot 只接纳既无 scope、也无 checkpoint reservation 的 target；它先按全部 fact 与 search 双写做 row-count 拒绝，再用不分配整包的 bounded serializer 在 byte budget 处短路。Direct incremental snapshot 会先证明 base fresh、非 retiring、属于当前 fact version 且没有 GC job。任何 mutation 前，它只通过 `source_scope` 前导索引枚举 base facts/group owner，通过 metadata rowid exact ownership 枚举 FTS，并把 clone、最坏 path replacement、新 facts、search owner 与 publication bookkeeping 一起计入同一个 row/byte quantum。只有通过 admission 的 snapshot 才能原子 clone exact owned rows 并替换 changed paths。超预算增量会在 target 零写入时返回类型化 `DurableStagingRequired`；既有 target 与 workspace projection 也必须进入 checkpointed pipeline。Serving 先用 manifest 对整个 fresh scope 做 gate，再对受界 group candidate 集合执行 MATCH，并按 capped water-filling quota 展开 occurrence。代表 occurrence 必须保留，其余成员按 reference ID 确定性排序；固定 SQLite VM-step guard 返回可观察的 `CapacityExceeded`，而不是对 hot 或 residual-heavy group 静默截断，并且 connection 复用前始终清除 handler。

增量 base selection 是 fail-closed storage boundary。Queue admission 会在解析前证明 clean base，single-SQLite writer 又会在 publication transaction 内复验 freshness、retirement、GC、filters、fact version、index shape 与 projection ownership。带 fence 的 clean incremental 始终使用 durable clone 协议。没有 auto-workspace projection 的 worktree overlay 仅在完整 clone/delete/insert surface 装得进 authoritative budget 时先走 direct transaction；一旦超限，同一 task 与 fence 会建立 content-addressed overlay、按有界 page 克隆 immutable clean base，再把完全相同的 dirty delta 按确定性的 file-owned batch 写入。该路径保留 synthetic worktree identity，绝不把请求转换成语义不同的 clean full index。在持久、受界的 workspace manifest 能跨 clone/finalization recovery 前，带 auto-workspace projection 的 worktree request 仍是显式 fail-closed boundary。Application 只会为带 lease、且 built target 与 task fence 完全一致的 clean `Incremental` 请求捕获 `DurableStagingRequired`，随后以同一 task、fence、target scope 与 resource budget 转入 durable full pipeline。已有 clone 或 batch checkpoint 会立即 resume。Worktree base 缺失或不兼容、unfenced authority conflict 与 target mismatch 都 fail closed。Partitioned control-to-shard 同步只复制 canonical repository row 与当前 alias，不在无 budget 时导入 scope fact；shard 缺少 base 时会在 fact publication 前返回同一 typed staging signal。

每次 buffered search-document flush 都以 pending-document count 为权威值。FTS mutation 前先用一次带索引的 rowid equality point probe 拒绝 `INT64_MAX`；SQLite 在该边界会把自动 rowid 分配切换为非连续的随机查找。受界 INSERT 后，以 `last_insert_rowid - pending_count` 推导 exclusive interval start，并要求 FTS affected-row count、interval count 与 metadata affected-row count 都等于 pending count。Flush 前已经存在的高位或同事务 raw FTS row 位于新推导 interval 之外，保持 unowned，不会被扫描或误认领。

## 5. 增量更新

增量算法先缩小工作集：

1. 使用 Git diff/status 和 blob hash 找 changed files。
2. 加入 deleted/renamed/moved files。
3. 用反向依赖和 import/call/reference edge 扩散 affected files。
4. 只刷新受影响的 code facts、chunks 和 index families。

手动 `repo update` 与常驻 commit reconciliation 都会先把所选 base/head ref 解析为不可变 commit，再把 `Incremental` request 提交到 durable code-index task queue。手动省略 base 时选择最近发布的 clean snapshot，包括 worktree-overlay identity 内的 clean commit；省略 head 时选择 `HEAD`。仓库没有该 base 时必须先完成 full index。Git diff 在应用注册 path filter 前按整个 commit pair 计算，最多接受 512 个 changed path；超过上限明确要求 full index，不能借此把 queue、parse set 或 write transaction 变成无界。

常驻 FileWatcher 把 `.git/HEAD`、ref、packed-ref 和 HEAD log event 作为低延迟 hint。启动时及受界 periodic interval（默认 5000 ms）会独立解析 checked-out HEAD/tree，因此 linked worktree 与漏报/合并 event 仍可恢复。HEAD 推进后，将最近发布 clean base 与新 head 固定进 durable task。每个 repository、checked-out ref 与 filter set 使用稳定 fingerprint，在任务槽未完成时合并重复 hint；queue admission 每仓库限制 32 个、全局限制 256 个未完成 task。Attempt-scoped lease 与单调递增的 publication generation 共同构成 single-writer authority；snapshot、batch、workspace 与 software-projection transaction 都在 commit 前校验 live generation，因此 commit event 或 lease 过期后的游离 attempt 不能绕过有界 retry/backoff、recovery 或 dead-letter。full rebuild 保留 batch checkpoint；clean incremental request 会在任何 direct fact write 之前，以同一 task 与 fence 转入该 checkpointed full pipeline。

产品 source boundary 与 self-iteration file-count observer 的只读 Git subprocess 必须设置 `GIT_OPTIONAL_LOCKS=0`，避免 ref、status、diff、tree 与 blob 检查触发可选 index refresh 及伴随的 `.git/index.lock`。该环境变量不会把写命令变成只读，也不能替代 durable task lease、publication fence 或 fixture writer coordination；任何有意修改 ref、index 或 worktree 的流程都必须拥有独立、显式的 mutation boundary。

Import 依赖扩散必须优先使用已索引代码地图和版本化 import edge。若 import 指向的外部依赖或跨仓库目标没有代码地图，索引器只记录 unresolved target hint、resolution reason 和受影响的本仓库事实，不为了补齐该依赖而触发未授权全仓扫描；这个 coverage gap 不是 parser、file、scope 或 response 降级。查询层可在同一 scope 内用该 hint 触发受限内部 source fallback。

本地配置关系只在同一 indexed source scope 内解析。Finalize 可以在该 scope 的全部文件写入后解析确定性的本地文件引用、模板 include 和构建目标引用。有歧义的本地匹配以及外部 image、package、remote label 或 template 继续保留为 unresolved 或 ambiguous metadata，而不是 parser degraded state。

Feature flag 抽取属于索引阶段。运行时配置读取、布尔配置声明和 guarded-code 关系必须随文件 scope 写入版本化事实；查询层只能读这些事实和对应 FTS 文档。TOML、YAML、JSON、INI、Java properties 等配置格式中的布尔声明复用 configuration 抽取器产出的结构化 config-key fact，而不是维护第二套 feature-flag 来源。更新抽取规则、配置文件或 guarded 分支后，必须通过 full 或 incremental index 刷新相关 scope。

只有新 scope 及其 software projection 完成后才运行有界 retention。protected set 是 active scope 与最近两个成功发布时间窗口的并集（窗口通常已包含 active）、最近一次成功增量的 predecessor、active worktree overlay 的 clean base，再加所有未完成 task 的 target/base 和 repository-set pin。清理先原子地把一个旧 scope 标为 `retiring`，使它退出 read/base resolution，并持久化可恢复 job。之后每个 maintenance transaction 最多推进一个 scope-GC phase，该 phase 在受影响的应用表之间合计最多删除 512 个物理行，包括 facts、code FTS/search document、software projection、checkpoint、workspace state 或 scope metadata。同一 pass 另行最多删除 512 条 succeeded task audit、512 条 failure-class task audit 和 512 条 commit alias，使主清理合计最多 2,048 个物理行，另加最多一个终态 GC-job bookkeeping 行。同 tree commit 复用内容图，并使用每仓 256 条的 commit alias 窗口。在分区 SQLite 中，已经激活的 shard 仍把原始 checkpoint 保持为 `finalizing:partitioned_publish`，由 catalog 支持的对外 checkpoint 投影报告 `completed`。即使 catalog scope 已 active，raw query-index repair token 仍是 pending，绝不能投影为 `completed`；只有 repair 恢复 exact raw partitioned-publication state 后，catalog activation 或 completed-state materialization 才能继续。同 tree adoption 可以更新本地 `completed` checkpoint 或该原始分区状态中的 commit metadata，但必须保留原始状态，使 control catalog 与 publication receipt 继续作为跨数据库 authority。完成态 task history 限制为每仓库 128 条 successful 与 64 条 failed/dead-letter/cancelled，同时为每个 retained scope 保存最新 success。状态报告 pending/job phase/deleted rows/error，常驻 maintenance worker 在失败后续跑。被淘汰 commit 必须 full reindex。这里不是 generic Knowledge Graph 或独立 semantic/vector generation 的原子发布声明。

Search retention 先按每页最多 256 个 metadata owner 删除成对 FTS/metadata row，使物理删除总数不超过 512；随后进入 `search_orphans`，按 FTS 内建 rowid 递增对全局表做每页最多 512 行的 keyset 扫描，而不是用 `UNINDEXED` scope 列做全表过滤。页内只删除已经 `retiring` 的目标 scope 中没有 exact metadata owner 的剩余 FTS row；exact owner 必须同时匹配 rowid、scope、kind、record 与 path。若目标 row 仍有任意 metadata owner，该页保留两侧并在推进前 fail closed，不能制造 metadata-to-FTS orphan。即使交错页没有目标行，nullable `search_rowid_cursor` 也必须在同一事务推进；rollback 或 reopen 会重放同一页，EOF 切换到下一 phase 时则原子清空 cursor。

每个显式或隐式解析 scope 的 code read，必须从初始 scope/`retiring` resolution 到后续所有相依 SELECT 全程使用同一个 SQLite deferred read snapshot。该承诺包括 code fact/search read、repository status/list/scope-status/latest-scope-status 以及 repository-set status/cross-edge read，但不泛化到无关的单 SELECT reporting。并发分阶段清理只能让该请求看到完整旧快照，或让后续请求明确收到 retiring 错误，不能返回混合的部分 scope state。

## 6. 高性能边界

Grouped reference-search cleanup、discovery 与 build 的每一种 range 都为首条页和续页使用不同的静态 SQL。续页直接表达可用索引的 `id > cursor` 边界，不再使用 nullable parameter `OR`；首条页则完全省略 cursor predicate。Length-only lazy scan 遇到首个超出 byte budget 的候选即停止，只保留最后一个已接纳 lookup key；每页只点查这一个 durable cursor，不再获取每个已接纳 cursor 的 payload。Discovery page 的 grouped UPSERT 返回最终 group ID，并直接从返回结果派生 page-group 与 newly-created-group count，不再对同一页额外执行一次 grouped count scan。由于 `reference_id` keyset 单调递增，`returned_group_id > previous_group_cursor` 是精确的新 owner 判定。该 plan 变更不扩大 page row/byte limit、progress mutation count、writer quantum 或 replay surface。

Grouped build page 通过既有 row/byte 上限后，使用一条有序 `INSERT ... SELECT` 把全部已接纳 group 直接投影到 FTS owner，不再在 Rust 中为每个 group 物化六个字符串并反复执行 `VALUES` statement。该投影保持规范 reference content 的 field 顺序和空字段规则；写入前拒绝既有 `INT64_MAX` rowid，再由 `last_insert_rowid` 推导新增连续 interval，精确校验该 interval，并用一条带 scope 约束的 `INSERT ... SELECT` 建立 metadata owner。FTS、metadata、page progress、checkpoint CAS 与 fence validation 继续位于同一事务。Named performance gate 要求 1,025-group page 恰好执行一条主 FTS insert 与一条 metadata insert，另有 regression 覆盖空字段和 maximum-rowid 拒绝。这些是 statement amplification 与原子性保证，不构成真实仓库 wall-time 证据。

12 列 `code_repository_chunks` 基础事实采用受界 multi-values statement，每条最多包含按输入顺序排列的 1,024 行、12,288 个 bind，低于 bundled SQLite 的 32,766-variable 上限。Runtime SQLite variable limit 会进一步收窄分组，并在低于 inclusive 12-variable 单行边界时 fail closed。固定满组 SQL 只初始化一次并使用 connection statement cache；每次调用最多另行 prepare 一个更小的 tail shape。基础分组完成后，chunk search document 仍按原始顺序传给 `SearchDocumentInserter`。基础事实、FTS ownership、checkpoint advancement、staging publication 与 fence validation 保持在同一个 caller-owned transaction 中，因此 tail failure 会回滚此前的完整分组，并让 durable staged manifest 保持可 replay。

代码索引采用 Sourcegraph/Zoekt、GitHub Code Search、ripgrep 和 Tree-sitter 类系统的共同原则：先用路径、语言、trigram、symbol name 和 blob hash 缩小候选，再做 AST capture、edge resolution 和语义/向量刷新。AST chunk 应沿函数、类型、模块、doc comment 和 import block 边界切分；fallback text chunk 只在结构解析不可用时接管。

对于无法用单个 file chunk 保存、但未进入 dense-window 模式的 symbolized source file，索引可以保留 symbol byte range 之外 gap 的 source window，使顶层 relationship fact 仍可检索。每个 window 继续遵守 8,000-byte 与 200-line 上限，每个文件最多新增 64 个 uncovered-source chunk。因此非 dense 结果严格受 `symbol_chunk_count + min(uncovered_window_count, 64)` 约束；该上限属于写放大与 FTS footprint 合同，不能为修复仓库特定召回而放宽。

全量 cold index、语义 embedding、跨 batch edge finalization、large file skip/hash 和 parser-heavy work 都属于 master 监督的后台 worker 或 maintenance 边界，不能阻塞查询热路径。Code-index worker 必须通过 application service claim durable task，持有 attempt-scoped lease，并执行有界 parse/write batch；接口层和查询路径不能直接调用 tree-sitter full indexing。增量索引必须记录 changed file count、affected file count、parse throughput、write batch count、candidate window 和 stale lag，便于区分真正增量和隐藏全仓扫描。

Tree-sitter parse 与 tag-query extraction 使用确定性的 progress-callback 工作预算，不使用 wall-clock deadline。每次 callback 消耗一个 work quantum；每个阶段获得 4,096 个基础 quantum，并按每 24 个源码字节增加一个，最多 32,768 个。Tree-sitter 0.26.9 每完成一组 100 个内部 operation 检查一次 callback；合法的 28,701-byte、2,048 层 JavaScript 回归分别消耗 430 次 parser callback 与 450 次 query callback，基础预算仍保留一个数量级的余量；24-byte 扩展率约在旧预算达到上限的 688 KiB 区间触及硬上限。零预算在第一次 callback 检查时取消。该约束既能硬性限制异常 grammar 或高成本错误恢复，又不会把 worker 被调度器抢占的等待时间误算为 parser 工作。预算耗尽时，file diagnostic 记录阶段和 callback-work 上限，syntax parse 标记为 failed，并保留原有 text-chunk fallback。

已编译 tag query 是进程级不可变 parser artifact。Parser 按静态 language id、language factory identity 与 query identity 最多缓存 64 个 query，编译失败不会写入缓存。Cache miss 在全局 cache lock 外完成编译，之后重新持锁并 double-check，再执行受界写入；grammar 或 query 构造 panic 因而只影响当前文件，不会 poison 其他语言。若 guard 曾被 poison，也只在不运行 grammar callback 或 query 编译的 lookup 与受界 insert 临界区内恢复。每个文件仍独立创建 `QueryCursor`、callback budget、capture collection 与 diagnostic context，因此缓存复用不会共享可变遍历状态，也不会削弱 cancellation。显式上限高于当前静态 grammar 注册面，同时防止测试注入或未来注册错误让 parser 内存无界增长。

可变 Tree-sitter `Parser` 实例只允许在当前 OS parser worker thread 内复用，按静态 language id 与 language factory identity 隔离，每线程最多缓存 64 个实例；达到上限后的新 identity 使用单次临时实例，不扩大缓存。每次 parse 前必须调用 `Parser::reset`，包括新实例、成功后的复用以及 callback 取消或错误后的复用，防止 Tree-sitter 从前一文档的暂停状态继续。实例在一次 parse 期间独占借用，不跨线程共享，也不改变 per-file work quantum、parse status、facts、batch/checkpoint 或路径顺序。该复用用于减少同一 worker 连续处理多文件时反复 `Parser::new`/`set_language` 的固定开销；端到端 wall time 仍必须由 release-binary performance evaluation 实测，不能由直属单测推断。

全量索引批次必须同时受文件数、字节数和写入 row 数约束；为了提升大仓库 cold index 吞吐，可以扩大有界批次、并行 parser worker、减少空 scope 上的冗余 SQLite 探测、复用 prepared statement、使用可索引 FTS metadata 清理或增加分阶段 finalization checkpoint，但不得跳过 FTS/search-document 写入、edge finalization、checkpoint、freshness 校验或 degraded/status 上报。任何注册后索引性能优化都必须在 self-iteration `fast` 或 `--categories performance` 中留下可回归的 `index_ms`、`register_index_ms` 和 finalization 后 ref 可查询性的预算或 guardrail。

Batch-persistence owner 对 16 列 `code_repository_references` 基础事实采用受界 multi-values 写入：每条 statement 最多包含按输入顺序排列的 1,024 行、16,384 个 bind parameter，低于 bundled SQLite 的 32,766-variable 上限；若 connection 暴露更低的变量上限，实际行分组还会继续收窄，小于单行 bind 数时直接拒绝。SQLite 的最大 host-parameter 编号是 inclusive。参数通过 `ToSql` 借用既有 record field，不再逐 reference clone 字符串。固定满组 SQL 只初始化一次并使用 connection statement cache，单个 tail shape 另行 prepare。所有分组仍位于 durable staging 之后、checkpoint、staging-state 与 fence 校验提交之前的既有 fact transaction 内；任一分组失败都会把 file facts、此前全部 reference 分组和 intermediate search documents 一起回滚，而已经持久化的 `staged` manifest 继续可 replay。Active scope 的 `SearchDocumentInserter` 仍按原始 reference 顺序接收输入。该批处理不改变任何其他 fact owner，也不改变 reference-search finalizer。

同一 owner 对 17 列 `code_repository_symbols` 基础事实采用按输入顺序排列的受界 multi-values 分组，每组最多 1,024 行、17,408 个 bind parameter，低于 bundled SQLite 上限。Runtime variable limit 会继续钳制分组；它可以等于单行所需的 17 个 bind，小于该值时 fail closed。Bind parameter 直接借用既有 symbol record field；只有 optional role JSON 在当前受界分组内物化一次，再由该 statement 借用。固定满组 SQL 只初始化一次并使用 connection statement cache，单个受界 tail shape 另行 prepare。Symbol search document 继续通过既有 `SearchDocumentInserter` 保持原内容和输入顺序。所有 fact 分组和 search document 仍位于 caller 持有的 transaction、fence 与 checkpoint 边界内，任一分组错误或 caller rollback 都会将其一起移除。该批处理不改变 reference persistence 或 finalization。

`SearchDocumentInserter` 对六列 FTS projection 使用同样的受界 statement 复用策略。完整 flush 由 runtime SQLite variable limit 钳制，最多包含按输入顺序排列的 1,024 个 document 和 6,144 个 bind；默认 full-shape SQL text 在进程内只初始化一次并通过 connection cache prepare，较低 runtime full shape 也进入 connection cache。较小的最终 tail 每次 flush 只 prepare 一次，且不会进入按 row count 扩张的 cache；可用 variable 少于六个时在任何写入前拒绝。固定的 maximum-rowid 点查、rowid interval count 与 metadata `INSERT ... SELECT` statement 也使用 connection cache。构造器不执行 FTS aggregate。每次 flush 在 INSERT 前拒绝既有 `INT64_MAX` row，再以 `last_insert_rowid - pending_count` 推导 exclusive interval start；FTS affected rows、interval rows 与 metadata affected rows 都必须等于 pending count。高位 unowned orphan 以及此前的同事务 raw write 都位于该 interval 之外。任何 owner conflict 或 interval mismatch 仍在 caller transaction 内报错，rollback 会同时移除先前的完整 flush 与 tail。Fast performance gate 以高位 orphan 跨越 1,024-document 边界，要求恰好两次主 FTS insert、两次 equality point probe、零 `max(rowid)` statement，并验证 FTS virtual-table 的 equality-constrained plan。这些 guard 只固定 statement amplification 与恢复语义；wall-time 仍以 release-binary performance evaluation 为准。

一次 source fetch/parse 全部成功后，plan 的 fetch cursor 只对完整受界 group 前进一次。若 write-row 上限使本批只能接纳该 group 的一部分，剩余逐文件 parsed build 留在有序 FIFO 中，由后续批次直接消费，不再读取 blob 或重新解析。FIFO 最多保留一个 fetch group，并继续受配置的 file/byte 上限约束；单个文件仍不可拆分，和原语义一样可以使一个批次超过 row 上限。Group 尚未完成读取、校验和解析时发生错误不会推进 cursor。Crash recovery 可以从 durable checkpoint 重放尚未提交的工作，但一次成功的内存 plan attempt 对每个 selected path 只读、只解析一次。

durable partial-index retry 可以让新准备的 plan 把 parser cursor 恢复到已提交文件前缀，并从 `batch_count + 1` 继续。worker 使用 claimed task 持久化的 resource budget，receipt shortcut 的响应 metadata 也报告该值；只有没有 task 的直接调用才使用默认值。恢复采用 fail-closed 校验：repository、source scope、resolved commit、tree、filters、total path count、resource budget、可恢复 state、parsed/committed 计数相等、计数边界、batch count 与精确 last path 必须全部匹配确定性 plan；finalizing 或 completed checkpoint 还必须覆盖完整路径前缀，内存 parsed overflow 必须为空。只读校验会捕获完整 checkpoint 或其不存在状态，`begin` 在写事务内、任何 repository/checkpoint 修改前比较该 expected token。missing-to-present、token changed race 与普通损坏都属于内部一致性故障，不映射成用户 `InvalidArgument`；已 claim task 会立即进入持久 `checkpoint_invariant` dead-letter。恢复必须显式分类已校验 token：resolved commit 相同走 `Resume`；只有 checkpoint 已是 `completed`，且 repository、内容寻址 scope、tree、filters、path count 与 resource budget 均一致而 resolved commit 不同，才允许走 `ContentEquivalentRestart`。后者绝不复用旧 completed cursor：storage 先按完整 completed token 做 CAS，再替换为绑定新 commit 的 `indexing` checkpoint，其 file/fact/batch 计数必须全为零且 last path 必须为空；application 在开始解析前还要校验该返回值。indexing/finalizing 状态的 commit mismatch，以及任何其他 identity、budget、progress 或 token mismatch，仍属于 invariant，并沿用立即 dead-letter 路径。Batch 发布只接受精确 next index，并在 staging 前拒绝跳号；checkpoint 已覆盖的 index 只执行 fence 校验并安全 no-op，因此 conflicting duplicate 内容不能修改其 manifest、facts、计数或 last path。checkpoint 一旦离开 `indexing`，任何尚未覆盖的新 batch 都必须在 staging 之前被拒绝，其中包括已经存在 durable reference-search page 或 query-index repair cursor 的阶段。Checkpoint 前进必须在 `indexing` 状态对精确 prior batch count 做 CAS，manifest 发布也必须对恰好一条 `staged` row 做 CAS；转换失败会回滚全部 fact 与 FTS 变更，同时保留既有已提交 progress。该机制只避免 retry 时重新解析已经提交的前缀，不会加速首次 cold-index attempt，也不会跳过任何索引阶段。

所有带 fence 的 clean incremental snapshot，以及 direct admission 超限且不带 workspace projection 的 worktree overlay，都使用同一 durable clone 协议。首次写 target 前，task 冻结 repository/base/target/tree/filter identity、affected-path 集合、row/byte limits、精确 grouped-reference totals，以及 base checkpoint 中非零的 `committed_fact_row_count`。缺少 checkpoint 或 legacy proof 为零时，系统在 target progress 零写入的前提下返回类型化 full-staging fallback；worktree task 不得把该 fallback 重新解释成 clean snapshot。该 proof 是实际累计 batch fact count；部分升级的 legacy session 会一直保持零；Maven dependency refresh 通过精确 delete/insert delta 调整它，并导出 checked clone bound `5F + table_count + 4`；当前 row/byte quantum 不得小于 immutable base 已冻结的 quantum。每个 clone transaction 只推进一个 metadata-indexed keyset page，并在 mutation 前后执行 progress/checkpoint CAS 与 fence 校验。Affected owner 会被跳过，但仍消耗 scan budget 并推进 cursor。Search copy 以 exact metadata owner 枚举，先按长度准入再获取 payload，准入后验证 canonical content，并批量写入一个连续 FTS/metadata interval；不得反向扫描未索引的 FTS scope 字段。Dirty delta 按 file ownership 和冻结的 file/byte/row budget 确定性分批，每个 worker step 最多提交一个 replay-safe batch；call 会计入所属文件的 batch，并在 finalization 从 call-shaped reference 重建。Terminal control transaction 另行把 affected-owner cascade cleanup、tombstone、fence/checkpoint bookkeeping 与 task-bound 多批收据共同纳入预算，并在交接完整但尚未发布的 target 到 `indexing` 前，把 `last_path` 恢复为整个 scope 的真实最大路径。Delta batch 之间发生 lease takeover 时，会从精确 batch count 续跑，不重放已提交 work。随后复用既有 full finalizer，依次完成 query-index repair、reference/import/call resolution、按 `F' = F - D + I` 更新 proof 的 Maven effective dependency refresh、grouped reference search、call rebuild、publication、workspace 与 software projection；不得跳过任一 phase。响应丢失时从 checkpoint 继续，不重新 clone 或 parse。Partitioned storage 必须在第一个 shard page 前持久化由 task 持有的 staged catalog route，使每个已提交 shard checkpoint 在 crash 后都能重新定位。

Writer authority 属于同一 checkpoint protocol。在 `single_sqlite` 中，unfenced snapshot、checkpoint 或 automatic-workspace cleanup transaction 会先对已注册 repository authority row 做一次精确 no-op update，从而在检查 `queued`、`running`、`retrying` task 之前取得同库 writer lock。未完成的 direct checkpoint 会阻止另一个 target 入队，除非已有未完成 task 持有该 checkpoint；同 scope task 可以接管，接管后每个 unfenced batch-staging transaction、fact transaction、finalization quantum 与 workspace-cleanup transaction 都重新检查 authority，并在写入前 fail closed。Terminal task 及其保留的审计 fence row 不会误阻止新的 direct snapshot 或 workspace cleanup。在 `partitioned_sqlite` 中，snapshot、session begin/resume、batch、finalization 与 workspace cleanup 一律要求 durable task publication fence。对应 unfenced 产品入口会在打开 shard 或发布 catalog route 之前返回稳定 `InvalidInput`，因为预读无法消除独立 shard/control WAL 写入之间的竞态。

Partitioned catalog 的 schema compatibility probe 与 migration writer boundary 必须分离。已有 control database 先通过带受界 read busy timeout 的只读连接校验 `storage_repository_shards` 与 `storage_repository_shard_scopes` 的完整 required-column contract；当前 shape 直接返回，不执行 DDL、`ALTER TABLE` 或 `BEGIN IMMEDIATE`。只有 database/table 不存在或 legacy column 缺失时才进入既有 immediate transaction，原子完成建表与迁移。损坏或不可读状态必须 fail closed，不能伪装为空 catalog。新增 catalog migration 时必须同时扩展 required-column contract、迁移逻辑和并发回归测试；该启动优化不改变 publication fence、task lease 或 shard writer authority。

生成源码检测是 metadata 步骤，不是索引跳过规则。检测器同时使用 `.pb.go`、`.pulsar.go`、`.generated.ts`、`.auto.ts`、`.min.js`、`.min.css`、仓库根层 `dist/`/`build/` output、`target/generated/` 等路径形态，以及 `Code generated by`、`auto-generated`、`@generated`、swagger/OpenAPI generator 注释等有界文件头 heuristic。没有路径或文件头生成信号的超大文本文件仍属于普通源码 metadata，并由独立 large-file degraded policy 处理。生成文件仍要写入 file、symbol、edge、chunk、FTS 和 index facts；file row 携带 `is_generated`，summary/report 拆分 handwritten 与 generated symbol 数，representative query seed 忽略 generated symbol，查询可设置 `exclude_generated` 从结构化检索和有界 source fallback 中移除生成文件。

Query-time source fallback 与 Git blob 读取一样必须进入 blocking-worker 边界。产品路径使用内部 fixed-string scanner 搜索临时物化的有界已索引 blob，先应用 path/language/scope 过滤，并在候选路径、候选文件预算或物化字节预算触发时返回 degraded reason，而不是把查询热路径退化成全仓扫描。开发者或 agent 检查源码时，可以使用 `rg` 或 `grep -RIn --exclude-dir=.git --exclude-dir=target ...`，但这些命令必须留在产品运行时索引和查询循环之外。

## 7. 降级策略

不可恢复 parse error、grammar panic、capture mismatch 或 unsupported language 生成 parse status 诊断，并回退到 text chunk。C/C++ 文件如果 error node 局限在 macro expansion、有界 preprocessor directive 或 decorator-like export macro，且 symbol、reference 或 import 抽取成功，可以记录为 parsed。降级结果必须出现在 repo status、health 和 context pack metadata 中。外部依赖源码缺失保持 unresolved edge metadata，不写成 `degraded_reason`。查询时 exact-text source fallback 的候选路径或预算降级应出现在 code query 响应 metadata 中，而不是写入索引状态。人工 `rg`/`grep` fallback 是 agent 检查源码的操作说明，不应作为产品 index health 上报。

## 8. 验收标准

- 大仓库索引能报告 progress，不替换旧 fresh scope。
- 增量更新只处理 changed 和 affected files，不能全仓扫描伪装为增量。
- commit 推进可通过受界 reconciliation 与 durable task replay 从 watcher 漏报和服务重启中恢复。
- 产品与 harness 的只读 Git 检查会关闭 optional index lock，同时不削弱 durable writer 或 publication fence。
- 持续 commit 会保留 recovery base 与 repository-set pin，同时限制 scope 和完成态 task history 的增长。
- 合法语法不会仅因 parser worker 被调度器抢占而降级；parser 与 tag-query 工作仍受确定性 callback quantum 硬上限约束。
- 已编译 tag query 只作为不可变语言 artifact 复用；逐文件 cursor 与工作预算保持独立，非法 query 不进入缓存。
- 可变 Parser 只能在线程内按静态语言 identity 有界复用，每次 parse 前 reset；取消后的实例必须能安全解析下一份独立文档。
- 相邻的有界 documentation block 只写入下一个 symbol owner；C/C++ declaration anchor 不扩大 symbol range，Rust inner block 不绑定下一 symbol，普通或超限 block 不生成 symbol doc fact。
- Row-budget overflow 保持文件顺序与不可拆分的单文件事实，一次成功 plan attempt 内不会重复读取或解析同一 fetched path。
- Durable partial retry 只从通过 identity 与 prefix 校验的 checkpoint 继续；无效或未提交进度绝不跳过，首次 cold-index 成本不变。
- 当前 partitioned catalog 的 CLI/read-only 重开只执行受界只读 required-column 校验，不取得 writer lock；只有缺表或 legacy 列时才进入 immediate migration。
- 解析失败文件仍能通过文本检索召回。
- 索引 trace 能说明候选缩小、parse、写入和刷新各阶段耗时。

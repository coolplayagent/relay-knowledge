relay-knowledge 1.1.14 新特性

1.1.14 把“仓库里的知识、代码图和 Git 历史”收敛为一个可验证的开发闭环。 这一版重点升级 Knowledge Map 的存储与兼容能力，引入业务知识到技术实现的映射， 并让大型仓库索引更快、更稳定、更容易恢复。

发布日期：2026 年 8 月 27 日。CLI、JSON、HTTP、MCP、数据库目录和服务管理方式保持兼容。

查看发布与下载 crates.io

快速升级

cargo install relay-knowledge --version 1.1.14 --locked
relay-knowledge version --format json
relay-knowledge map init --format json
relay-knowledge map validate --format json

如果仓库已经写入 Knowledge Map v2，请先把所有读写该仓库的 CLI 升级到 1.1.14。 1.1.13 及更早版本不能读取 v2；较早的 v2 归档若还没有历史索引，运行 map init 会在 writer lock 保护下补齐索引，不会覆盖已有知识内容。

Knowledge Map v2：知识按需加载，历史有界读取

Knowledge Map 从单文件演进为根 manifest 加内容寻址分片的结构。 根文件只保留稳定导航、当前 topic 摘要和最近 16 条变更；topic 内容位于 .knowledge/topics/，更早历史位于 .knowledge/history/。

  • map route <topic> 只读取根文件和目标分片，agent 不必加载整张知识地图。
  • map history 按页读取历史，单页最多 256 条；B+ tree 索引保证定位成本有界。
  • 写入过程先发布不可变 artifact，最后原子切换根 manifest，并提供异常恢复状态。
  • 路径穿越、绝对路径和符号链接逃逸会被拒绝，分片与历史内容通过 SHA-256 校验。
relay-knowledge map route business-knowledge --format json
relay-knowledge map history --from 1 --limit 64 --format json
relay-knowledge map validate --format json

业务知识与代码实现进入同一张图

新增 Git 管理的 .knowledge/business-glossary.yaml，用于声明规范业务术语、 别名、缩写、语义冲突，以及术语到代码符号、文件和配置的技术映射。 查询读取已经提交的投影，不会在热路径扫描 YAML，也不会猜测歧义术语。

  • CLI 新增 repo business，可查询术语、映射或两者。
  • repo context 会把业务术语解析结果作为有界技术检索 seed，并返回 business_context。
  • HTTP、MCP 与 Web 共用同一服务；MCP 工具名为 relay_business_query。
  • 授权范围外的技术目标保留为 unresolved metadata，不会错误地把仓库标记为 degraded。
relay-knowledge repo business <alias> \
  --kind all --query MRR --domain revenue \
  --ref <commit> --freshness wait-until-fresh --format json

relay-knowledge repo context <alias> \
  --query "MRR 的计算与调用链" --ref <commit> --format json

以 Git commit 为事实锚的开发闭环

1.1.14 将业务知识、软件投影、代码图、影响分析和 context pack 固定到同一个 resolved commit。 从理解需求到检查变更，不同接口不再各自读取漂移中的工作区状态。

  1. 用 Knowledge Map 找到权威业务、架构和运行文档。
  2. 在指定 commit 上完成或复用代码索引。
  3. 读取同一 ref 的 business、software、view 和 context 结果。
  4. 用 base/head 影响分析检查变更，再验证 Knowledge Map 与索引 freshness。
relay-knowledge repo update <alias> --base <base> --head <head> --format json
relay-knowledge repo impact <alias> --base <base> --head <head> --format json

大型仓库索引：历史复用、持久任务与分阶段回收

代码索引继续遵守单仓库最多一个 active writer 的约束，并强化了 durable task、lease、checkpoint、 重试退避和发布 fence。初始化索引现在可以显式复用兼容的历史 commit scope， 进程退出后也能从持久 checkpoint 恢复，而不是重新开始。

  • repo index --reuse-historical 最多检查目标 commit 的 10 个第一父链祖先。
  • 兼容基线且 diff 不超过 100 个 changed path 时转为增量任务，否则安全回退到 full index。
  • active、最近使用、增量前驱、worktree base、未完成任务和 repo-set pin 会被保留。
  • 旧 scope 先进入 retiring，再由有界 maintenance 分批删除，避免无界清理阻塞查询。
  • 大规模 impact seed 改为分批处理，降低 SQLite 变量上限与内存峰值风险。
relay-knowledge repo index <alias> --reuse-historical --format json
relay-knowledge repo status <alias> --format json

检索升级：有界 OKF 图与分层 BM25 路由

新版检索为大型候选集加入有界 OKF repository graph，并使用 SimHash 分组进行分层 BM25 路由。 近似只用于选择候选分组，最终排序仍使用现有检索信号；当数据规模、召回门槛或路由条件不满足时， 系统自动回退到 flat BM25，避免以性能换取不可见的准确率下降。

  • 关键词 BM25、semantic 与 vector 三层检索继续共享最新图状态和 provenance。
  • 所有候选窗口、队列、批次与上下文字节数保持有界。
  • 索引 freshness、stale、degraded 和失败状态继续显式暴露，不用文本 fallback 掩盖缺失依赖。

架构、质量与发布

  • 架构门禁改用 Rust 语法生成 module/import graph，并通过 SCC 检测环依赖和分层违规。
  • CLI 生产路径收敛为 bootstrap → interfaces → application，存储和出站网络通过 ports 注入。
  • API DTO 与存储类型解耦，旧公开路径通过 re-export 保持 1.x 兼容。
  • 修复 telemetry 与 XML 依赖中的安全问题，并保持 Rust 1.98 Clippy 检查通过。
  • GitHub Release 提供跨平台预编译产物、校验和与构建证明；cargo install 路径保持可用。

兼容性说明

  • 没有改变 CLI 命令结构、JSON/streaming JSON、HTTP、MCP、数据库位置或服务定义。
  • Knowledge Map v1 可由 1.1.14 的 map init 幂等迁移到 v2。
  • 一旦默认 writer 已写出 v2，旧于 1.1.14 的 reader 必须升级后再访问该仓库。
  • 历史索引复用是显式 opt-in；不传 --reuse-historical 时仍执行原有 full index。
